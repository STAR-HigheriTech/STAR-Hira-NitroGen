# 扫码器插件设计（QR Code 扫描器）

> 目标：点一下出现一个**可拖动的取景框**，把它拖到屏幕上二维码的位置，套住就自动认出来。
> 就像手机扫码时移动取景框去对准——只不过这里动的不是手机，是框。
> **不是摄像头，也不是粘贴截图。**

## 1. 一句话架构

**框在核心（窗口设施），像素在引擎插件（抓屏能力），解码在共享内核，界面在面板插件。**

```
主进程                                        渲染层
┌────────────────────────────────────┐        ┌─────────────────────────────────┐
│ window-config.js                   │        │ renderer/qr-scan-frame/         │ 取景框页
│   WINDOW_TYPES.QR_SCAN_FRAME       │        │   （透明置顶窗口，整窗可拖）      │
│   （透明 / 置顶 / 无边框 / 不可聚焦）│        ├─────────────────────────────────┤
│ main.js qrScanFrame 端口            │        │ shared/qr-scan/scan-window.js    │ 引擎接口
│   open / close / drag ← 拖与缩放    │        │   （开框/收框/等放下/抓一帧）      │
│   bounds ← 框在哪（几何唯一权威）    │        │        ▲              ▲          │
│ plugins/qr-scanner.cjs              │        │        │              │          │
│   能力 qr.captureScreen             │◀─IPC──▶│ qr-scanner.model  panel-totp.model│
│   （「扫码器引擎」插件，无界面）      │        │  （扫码器面板）    （验证器面板）   │
└────────────────────────────────────┘        │        └── 同一份 decoder/detector│
                                               └─────────────────────────────────┘
```

**`scan-window.js` 是"引擎"对外的那一个面**：「扫码器」面板与「验证器」面板都是它的
**调用方**（`open / close / rescan` + `onText / onScan / onError / onClosed / onCapture`）。
验证器面板点「扫描屏幕二维码」就能直接调起取景框扫屏幕导入 2FA，**不需要**用户先打开
扫码器面板 —— 面板只是消费者，取景框与抓屏能力都在核心/插件那边，与"哪个面板开着"无关。

### 1.1 引擎与面板是**两个插件**（本仓库的插件形态范本）

第一版把"抓屏能力 + 侧栏面板"塞在同一个插件里，于是只有一个开关：
**关掉面板 = 抓屏能力也没了**，验证器面板的「扫码」跟着一起失效 —— 可是那两件事本来无关。

| 插件 | 类型 | 提供什么 | 关掉它的后果 |
| --- | --- | --- | --- |
| `qr-scanner`（扫码器引擎） | `feature-plugin` | 能力 `qr.captureScreen`，**无界面** | 屏幕扫码真没了：所有面板的扫码入口都不给了 |
| `qr-scanner-panel`（扫码器面板） | `ui-panel-plugin` | 侧栏面板 UI（`render` 入口） | 只是没有那个侧栏面板；验证器面板照样能扫码 |

`qr-scanner-panel` 的 `dependsOn` 里含 `qr-scanner`：从面板选择器里打开它时，
`enableWithPrerequisites` 会**一并把引擎启用**（一次点击就装好，与验证器面板同一套机制）。

**引擎可用性有唯一判据**：功能面 `qrScan`（`feature-map.js` 里声明它由 `qr-scanner` 提供）。
渲染层用 `isFeatureAvailable('qrScan')` 决定给不给入口、用 `onFeaturesChanged` 在
插件管理里关掉引擎的那一刻立刻收回入口并收掉开着的取景框 —— 不给"点了必然失败"的按钮，
也不留"已经扫不出东西却还挂在那儿"的框。

## 2. 取景框是什么（以及为什么是独立窗口，不是面板里的浮层）

**一个透明、置顶、无边框的窗口**（`WINDOW_TYPES.QR_SCAN_FRAME`，默认 300×346）：
上半是取景框（四角角标 + 流动虚线），下方 46px 是提示条（脉冲点 + 提示 + ✕）。

三种交互，各自只有一处实现：

| 交互 | 命中区 | 行为 |
| --- | --- | --- |
| 移动 | **整窗**（框内与提示条都行） | 抓哪儿都能拖走整个取景框 |
| 缩放 | 四角角标 | 拖四角改大小，对角保持不动，最小 160（再小裁剪区就没几个像素了） |
| 关闭 | 提示条上的 ✕ | 关框 → 主进程发 `screen:frame-closed` → 面板停止扫描 |

为什么不用面板内的浮层视图（`findbar-overlay` 那一族）：浮层视图被困在浏览器窗口里，
而"屏幕内"的二维码可能在别的应用上。置顶窗口能拖到任何地方，`getBounds()` 又直接给出
屏幕坐标 —— 裁剪区不需要任何坐标换算，也不会因为窗口移动而漂移。

**为什么不用 CSS 的 `-webkit-app-region: drag`**：那是 OS 级拖拽，最省事，但在
**透明 + 无边框**窗口上并不总是可靠，而"能拖动"是取景框的唯一交互 —— 不能压在一个
平台特性上（它一失效，整个功能就是一块钉在屏幕上的装饰）。所以拖动走鼠标事件自己算。

**矩形由主进程算，渲染层只报"意图"**（`{ mode, edge, dx, dy }`）。这条是踩过坑之后
定下来的，不能改回去：

- 渲染层量到的矩形（`window.screenX` / `window.innerWidth`）与 `setBounds` 用的坐标系
  在缩放的显示器上并不总是同一个数。一旦不一致，**第一次落位**就会把窗口"跳"到一个
  偏大的尺寸 —— 用户看到的就是**"按住一下就自己变大"**。位移没有这个问题：它只是个差值，
  与矩形无关。
- 主进程在按下那一刻记一次基准矩形，之后一律 `基准 + 总位移` 重算。用总位移而不是增量 ——
  增量会因丢帧/舍入一路漂移；用"按下时的矩形 + 总位移"则永远与光标对齐、与帧率无关。
- 下限（160）也只在主进程夹一处，渲染层不参与几何。

配套的两道闸（都在取景框页里）：

- **起拖阈值 3px**：按住不动时手也会抖一两像素，没有阈值时"长按"本身就会被当成一次
  拖动/缩放，窗口自己动一下；
- **`pointermove` 里判 `e.buttons === 0` + 指针捕获**：按键已经抬起却没收到 `pointerup`
  时（我们自己 `setBounds` 会让 OS 偶尔吞掉那一次抬起），动作会一直"上膛"，之后**任何一次
  悬停移动**都会拿着陈旧位移去落位。取景框是 `showOnReadyMode:'inactive'` 显示的（可能
  从未获得过焦点），所以 `blur` 兜不住这条路径 —— `buttons === 0` 那道判断才是管用的。

## 3. 几何：三个数字，一处定义

```
shared-types/src/qr-scan-frame.mjs
  QR_SCAN_BOX  = 300   取景框边长
  QR_SCAN_PAD  = 18    四周装饰带（角标/边框画在这里，**裁剪区从它里面开始**）
  QR_SCAN_BAR  = 46    底部提示条
  qrScanCropRect(bounds) → 真正要解码的矩形（300-36 = 264 见方）
```

**为什么必须共用一份**：渲染层用它画框，主进程用它裁剪。两边各写一份必然漂移，
而漂移的表现是"框里明明有码却扫不到"——既看不见也说不清。

**为什么装饰带要 18px**：浮框自己在屏幕上，抓屏会**连它一起抓**。落在裁剪区里的每一笔
都会变成解码输入 —— 一条穿过二维码的亮线足以让它解不出来。所以框内（裁剪区）
**一个像素都不画**：角标、边框、流动虚线全在 PAD 圈里。（也因此没有"扫描线扫过框内"——
那是最常见的取景框动效，但在这里它会在抓帧那一刻压在二维码上。）

## 4. 抓屏：为什么在主进程，为什么是插件的能力

渲染层拿不到桌面画面 —— 平台边界。关键的归属选择：

| 方案 | 问题 |
| --- | --- |
| 核心直接实现 desktopCapturer | 「扫码器」是可选、出厂默认关闭的插件，抓屏却会变成核心能力 —— 关了插件功能还在（§9"开关假生效"） |
| 渲染层 `getDisplayMedia`（**光靠它**） | 面板跑在 `file://` 下，权限层按域名存权限、`file://` 归不出域名；静默放行又等于让**第三方插件的面板**也能抓屏。所以它**只能作为主进程放行后的快路径**（§4.5），不能是唯一那条路 |
| **做成插件能力**（本方案） | 插件禁用 → `isCapabilityBlocked('qr.captureScreen')` → 通道**直接抛**；禁用 = 功能真的没了 |

三种东西的归属写死在 `main/ipc/screen.js` 里：**框**是核心的窗口设施，**像素**是插件的
能力，**"扫哪一块"**由核心把这两者接起来（读框的矩形 → 连同请求交给能力）。
插件因此完全不需要知道"窗口"这个概念，它只收到一个矩形。

## 4.5 两条抓屏路径：**流式优先，IPC 回退**（"拖框卡一下"的根治）

只有一条路时是死路：`desktopCapturer.getSources()` 在主进程生成**整屏缩略图**
（1080p = 8MB）→ `crop()`（第二次位图拷贝）→ `toBitmap()`（第三次）→ 8MB 序列化过 IPC。
整段都在**主进程的唯一 JS 线程**上，这几十毫秒里窗口落位 / IPC / 网页输入全部排队 ——
用户看到的就是「**一按住取景框就卡一下**」「**开着扫码器，网页也跟着卡**」。
把间隔调大救不了：触发式已经把次数压到最低，问题在每一次的**代价**。

| | 路径 A：屏幕流（首选） | 路径 B：IPC 抓帧（回退） |
| --- | --- | --- |
| 谁持有像素 | **渲染进程**（`video` 纹理 + canvas） | 主进程（回读 → 裁 → 拷贝） |
| 主进程每帧负担 | 两个矩形（`screen:frame-geometry`） | 整屏 8MB ×3 次拷贝 |
| 实现 | `getDisplayMedia()` → `drawImage` 裁框内 → 解码 | 插件能力 `qr.captureScreen` |
| 失败时 | **自动回退到 B**，用户无感 | 报 `ok:false + reason` |

要点（每条都是踩出来的）：

1. **准入门槛是"取景框开着"，或刚请求过开框**（`qrScanFrame.allowCapture()`，
   `setPermissionRequestHandler` / `CheckHandler` / `setDisplayMediaRequestHandler` 三处同一判据）。
   框是用户自己点出来、看得见的置顶窗口 —— 这是**可见的用户意图**，而不是某个页面在后台偷偷开流；
   框一关，通道立刻关闭。`thumbnailSize: {width:0, height:0}` 是官方写法（不生成缩略图 = 不抓内容），只取 `id`。
   - **"刚请求过开框"那段宽限是必需的**（`QR_SCAN_CAPTURE_ARM_MS = 4s`）：见下面第 3 条的顺序约束，
     请求流时框还没建好，只认"框开着"的话这条流**每次都会被拒** → 每次回退到路径 B →
     用户看到的就是"**老是报错：无法获取屏幕画面**"+"照样卡"。宽限只是把开框那几毫秒算进来，
     不是放宽成"谁都能抓"。
   - **源选择这里还会等框出现**（`CAPTURE_WAIT_MS = 1.5s`，40ms 一跳）：等的是同一个用户动作的另一半。
   - **只认我们自己的界面**（请求页 URL 是 `file:` / `hira:`）：少了这条，宽限期就成了
     "任意网页趁用户扫码时 `getDisplayMedia` 就能拿整屏"的窗口 —— 判据必须同时回答"谁在问"。
     （用 URL 而不是 origin：`file://` 页的 origin 是 `null`，白名单写不出来也认不出。）
2. **取景框要 `setContentProtection(true)`**：流抓的是合成后的整屏，框若被算进去，
   透明区在部分驱动下会被拍成黑色（＝框里什么都扫不到），而且是自己拍自己。
3. **`getDisplayMedia` 要瞬时用户激活**，所以它在 `open()` 的**同一个同步片段**里发起
   （用户点「扫描屏幕二维码」那一下），解码器的准备与流的建立并行 —— 不能先 `await` 再发。
   ⚠ 这条与"框得先开着"是矛盾的（激活等不了 `await`），只能靠上面第 1 条那个宽限化解。
4. **一条流、多次取帧**：流的生命周期 = 一次扫码会话。每次扫描只是从在跑的流里取一帧，
   再 `stop()` 逐 track 收掉；系统层"停止共享"（`track.ended`）也当会话结束处理。
5. **几何只有一处算法**：流是整屏的，渲染层要知道"框在流里的哪一块" —— 这个矩形仍由主进程
   用 `qrScanCropRect()` 算（`screen:frame-geometry`）。两条路扫的必须是**同一块区域**，
   否则"框里明明有码却扫不到"会变成随机现象。
6. **给捕获限帧**（`MAX_STREAM_FPS = 12`）：捕获管线默认按刷新率出帧（60fps 的整屏纹理），
   而我们**只在"框放下"那一刻要一帧** —— 不限帧就是开着扫码器一直在烧 CPU/GPU。
   分辨率**不能降**：框内只有 264 DIP，降采样等于把二维码本身缩小（同 MAX_CROP_SIDE 的理由）。

## 4.6 取景框自身：条上给「重新扫描」、装饰全静态（性能）

三条一起定的（都是"这窗口是长时间开着的工具"这个前提推出来的）：

1. **「重新扫描」放取景框的提示条上**，不放面板：扫描时用户的眼睛就在这个框上，
   让他回侧栏找按钮是反的。实现上**复用 `setFrameInteracting(false)`** ——
   那条通道的语义本来就是"交互结束，静默一拍后请面板抓一帧"，
   点一下按钮与"把框放下"对扫描是同一件事（不新增平行通道，也就少一处要同步的规则）。
   面板侧的 `rescanScreen()` 随之删除（死代码清零）。
2. **条上只留一句话**（"对准二维码"）：窄条 + ✕ + 重新扫描已经很满，
   原来那句"拖动移动 · 拖四角缩放 · 放下即识别"是给新用户看的说明书，看一次就永远碍事。
3. **三个无限动画全删**（流动虚线 / 呼吸角标 / 脉冲点）：它们叠在一个**透明置顶窗口**上，
   等于让合成器一刻不停重绘整窗 —— 而取景框正是"一直开着"的那种窗口。
   加上 `.frame { contain: layout paint }` 收敛绘制范围，静止时成本降到 ≈ 0。
4. **主进程落位去重**：`setBounds` 是同步窗口操作（Windows 上触发整窗 resize/重绘），
   而按住不动时 pointermove 仍在派发 —— 矩形没变就**不碰窗口**，手感立刻不发涩。

## 5. **触发式**扫描：静止时一帧都不抓（这条是"卡死"的根治）

抓一帧整屏要主进程回读 8MB，再把它塞过 IPC。第一版每 600ms 来一次，
结果是**主进程被这件事一直占着**：界面卡死、拖动没反应、鼠标都动不了。
这不是"把间隔调大"能解决的 —— 只要它还在持续跑，主进程就一直有重活。

所以改成**只用事件触发**，只在三个时机抓**一帧**（时序封在 `scan-window.js` 里，
两个面板共用）：开框落位后一拍、放下取景框、手动「重新扫描」。

```
取景框 mousedown ──► screen:frame-interact { active:true }
                     └─ 主进程记 interacting → screen:capture 入口**直接短路**（连抓屏都不碰）

取景框 mouseup   ──► screen:frame-interact { active:false }
                     └─ 静默 260ms（用户拖到位常会再微调）
                        └─ 主进程 emit `screen:frame-settled`
                           └─ 会话抓**一帧** → 解码 → 出结果

开框落位后一拍   ──► 会话自己排的一帧（用户很可能一放就对上了，不该还要他再动一下）

「重新扫描」     ──► 同样的"抓一帧"（用户可能刚滚动过页面 / 码是刚加载出来的）

用户点 ✕        ──► main emit `screen:frame-closed` → 会话收摊 → 面板停止扫描
                     （触发式下面板平时不发请求，没有这条事件它会一直显示"扫描中"）
```

静止时：**零抓屏、零解码、零 IPC**。代价只发生在用户真正放下取景框的那一刻，
而那一刻本来就没有别的事在做。这也正是扫码这个动作的语义 —— 对准了才看。

## 6. 三个必须写在代码里的取舍

1. **按框裁剪，payload 从 8MB 掉到 200KB 量级**。这既省掉绝大部分 IPC 与解码量，
   也是"扫哪儿"的语义：框内是唯一会被解码的区域。
2. **有框时按显示器原生分辨率抓**（整屏那档才缩到 1920）。框内只有 264 DIP 见方，
   再缩放一次就等于把二维码本身缩小 —— 那是"框里明明有码却扫不到"的根源。
3. **不逐像素翻 R/B**。Windows 原生位图是 BGRA，`ImageData` 要 RGBA；二维码是单色
   （R=G=B），灰度化对通道顺序不敏感。翻一遍 200 万像素是白烧主进程时间。
   这条假设写在契约上（`infra-ipc/contracts/screen.js`），不靠"看起来颜色不对"去发现。

## 7. 框没了要自己知道（`framed` 回传）

用户可以直接点框上的 ✕。主进程如实回传 `framed:false`，面板据此**自动停止扫描**，
而不是让用户对着一个不存在的框继续等。

配套的一个细节：框是 `showOnReady` 之后才可见的，开的头几拍 `framed` 还是 false。
若不区分"还没出现"与"已被关掉"，扫描会在刚启动时自己停掉 —— 所以会话里记
`frameSeen`：**先见过、再消失**才算用户关了框（见 `scan-window.js`）。

## 8. 两条渲染信号（流畅的关键）

| 信号 | 触发 | 视图做什么 |
| --- | --- | --- |
| `onChange` | 结构变化（开关扫描、记录增删、复制反馈） | 重建 |
| `onHit` | 扫到一个 | 只改状态条文字 + 新记录插到列表顶部 |

命中走 `onChange` 会重建整块列表，用户滚在中间时位置会跳。

## 8.1 面板 UI：**少即是多**（第三版返工）

用户原话：「这两个面板中的界面都太复杂了，不需要那么多详细解释小字！而且这么拥挤的界面根本不适合小的面板！」
侧栏只有两三百像素宽，**每一行小字都是从内容里抢来的**。所以定了几条硬规矩：

1. **不写解释段落**。静态说明（"点一下会出现一个取景框……识别到的内容会按类型给出对应动作……"）
   一律删掉：用户要的是内容与操作，不是产品介绍。必须保留的细节塞进 `title`（悬停才看）。
2. **常显按钮越少越好**。工具条只留唯一的主动作（扫描／停止）+「⋯」；
   每条记录只留一个主动作（打开 / 存入验证器）+「⋯」。低频动作（重新扫描、清空、复制、移除）
   全部进**原生菜单**（与标签行菜单同一套端口），一行按钮挤没内容的版面从此不存在。
3. **长文本压成一行**。记录的原始内容改为单行省略、全文进 `title`；多行会让列表变成一屏一条。
4. **提示只在三种时刻出现**：出错、要用户做决定、要用户操作。其余时候安静。
   一旦出现就必须显眼（见 §8 的命中高亮）——**"安静"与"跳出来"是同一枚硬币的两面**。
5. **提示卡只有一行**（第五版返工，用户原话"又不显眼又杂乱"）：实心高对比色 + 一条文案
   + 就地动作。"命中"与"平时"是**两套完全不同的文案**，不拼在一起 ——
   拼起来就是"对准二维码 · 放下即识别 ✓ 已扫到「网址」"，一长串，重点全被稀释。
   具体内容（扫到哪些条目）挂 `title`，悬停即见。
6. **"最新扫到的那一条记录"要强力高亮**（第六版返工，用户原话"新弹出的项不够显眼"）：
   状态条只在命中那一瞬亮一下，而用户的目光还在取景框上；等他回到面板，
   **唯一能指出"刚进来的是哪条"的就是列表里的那一行**。所以对它下重手：
   染绿底 + 整圈绿描边（用 `outline`，不挤内边距，与其它行严丝合缝对齐）+ 左侧 4px 粗绿条
   + 标题转深绿；插入时从右侧滑入一次（`is-pop` 一次性类，重建列表不重播）。
   高亮**保留到下一次命中**（同时只有一条最新）。
   注意：状态条那条"已扫到"的绿色**不要动** —— 它已经够显眼了，返工要打在正确的地方。

同一个原则也适用于「验证器」面板：删掉导入屏那段格式清单长文案（改由输入框 placeholder 承担）、
删掉空态解释段、导出框标题从"（含密钥，请勿截图外传）"砍到"（含密钥）"。

## 9. 去重与"本次会话"

框里的二维码会连续几十帧都在画面里，所以按文本去重并计 `count`（显示 `×N`）——
既压住噪音，用户也能看出"它一直在框里"。

历史**只存本次会话**：没有 domain / 表 / IPC 持久化链路，状态在内存里，
面板视图销毁即消失。也顺带省掉一处要保护的数据 —— 扫到的东西常含一次性口令与 Wi-Fi 密码。

## 10. 停止扫描的四条路径（收敛到 `stopScan`，幂等）

1. 用户点「停止扫描」；
2. **面板被隐藏**（切到别的面板 / 面板收起）→ `visibilitychange`。
   面板看不见了还留着一个置顶框、还想着继续扫，都说不通；
3. **用户关掉了取景框**（✕ → 主进程 emit `screen:frame-closed`，见 §5）；
4. 面板视图销毁 → `pagehide` → `model.stop()`（把框一起带走，不留孤儿置顶窗口）。

## 11. 智能动作

| 内容 | 动作 |
| --- | --- |
| 网址（含裸域名补 `https://`） | 打开 · 复制 · 删除 |
| `mailto:` / `tel:` | 打开 · 复制 · 删除 |
| `otpauth://` | **存入验证器**（软依赖可用时）· 复制 · 删除 |
| Wi-Fi / 纯文本 / 其它 | 复制 · 删除 |

「复制」永远复制**扫码那一刻的原始文本**，不是我们补全过的 `href`。
与「验证器」的联动是**软依赖**（`optionalDependsOn`）：引擎不在就**不给**那个按钮。

## 14. 已知边界

- 浮框置顶于**所有**窗口之上（含其它应用）—— 这是"能拖到任何地方"的代价。
  它是临时工具（关掉即消失），但确实会在扫描期间压在其它窗口上。
- 它**吃鼠标**（取景框范围内点击/滚轮不会落到下面的页面上）。曾经做过"只有边框收鼠标、
  其余穿透"，但那是靠 `setIgnoreMouseEvents(true, {forward:true})` 实现的，实测代价是
  整机输入都被拖累（鼠标都动不了），所以撤掉了：宁可挡住一小块，也不能让整个界面卡。
- 二维码必须是**静态**的（触发式扫描只在放下取景框的那一刻看一眼）。旋转/刷新的动态码
  可以点「重新扫描」再抓一帧；确实需要连续跟踪的话，得另开一条"低帧率实时预览"的路子
  （那必然带来持续抓屏开销，与"不卡"直接冲突，要做就得先想清楚代价）。
