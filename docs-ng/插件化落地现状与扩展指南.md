## 1. 四件核心机制：各管什么，边界在哪

Harness 的插件化由**四件互相独立的东西**组成。它们最容易混，混了就必然写出错代码，
所以第一件事就是把边界钉死：

| 机制                       | 文件                                          | 管什么                                                                                        | 典型用途                                                                        | 不该用它做什么                              |
| -------------------------- | --------------------------------------------- | --------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------- | ------------------------------------------- |
| **ProviderRegistry**       | `infra/infra-plugin/src/provider-registry.js` | 「**能力**」——一个可调用的实现，带 `before / validate / around / after` 四级 hook（洋葱模型） | 域服务插件（tabs / bookmark / download…）导出可调用能力；需要在调用前后拦截改写 | 传递纯声明数据；做多实现聚合                |
| **ContributionRegistry**   | `infra/infra-plugin/src/contributions.js`     | 「**声明式数据**」——插件往界面/宿主填的数据，按 `kind` 收集                                   | 面板目录（`panels`）、内部页（`pages`）、搜索指令（`bangs`）、菜单项（`menus`）、用户脚本（`userscripts`，§4.7） | 执行逻辑（它没有执行语义，只排序收集）      |
| **ExtensionPointRegistry** | `infra/infra-plugin/src/extension-points.js`  | 「**插槽执行**」——官方预定义的可挂载位置，四种执行模式，**宿主主动点名调用**                  | 主题 CSS 注入、标签右键菜单项、搜索结果过滤、导航钩子                           | 替代 ProviderRegistry（插槽不参与洋葱拦截） |
| **PanelCatalog**           | `apps/app-main/src/main/panel-catalog.js`     | 「**面板集合**」——`ContributionRegistry.panels` 的业务视图                                    | rail / navbar / 按钮编辑浮层 / 面板宿主**四处共用同一份**面板清单               | 存放图标函数（过不了 IPC，只能传名字）      |

### ⚠ 命名陷阱（踩过一次，务必记住）

`PluginRegistryV2` 上有两个名字极易混的方法：

| 方法                   | 返回                                      | 真实语义                                                                   |
| ---------------------- | ----------------------------------------- | -------------------------------------------------------------------------- |
| `getExtensionPoints()` | `{ [name]: [{pluginId, name, service}] }` | **服务出口表** —— 插件导出了哪些服务，供 provider 解析。**没有执行模式。** |
| `getSlotRegistry()`    | 调度器实例                                | **插槽调度器** —— PART7 §7.3 所说的那个东西                                |

`getExtensionPoints()` 的名字是历史遗留（改名会波及既有插件与测试），
已加 `getServiceExports()` 作为语义化别名。**新代码一律用 `getSlotRegistry()`。**

## 2. 从 manifest 到界面的完整装配链路

```
① apps/app-main/plugins/*.hira-plugin.json          ← 声明（唯一事实源）
        │  PluginRegistryV2.discover()
        ▼
② PluginRegistryV2.enable(pluginId)                 ← 生命周期：install → enable → disable → uninstall
        │     · contributes         → ContributionRegistry
        │     · extensionPoints 声明 → SlotRegistry.define()
        │     · 模块 hook extensionPoints() → 声明插槽 + 挂实现
        │     · registerExtensionPoints() → 服务出口表
        │     · providers           → ProviderRegistry
        ▼
③ 消费方（都在 APPS 侧，infra 不认识业务）
        · panel-catalog.js  ← contributions.list('panels')
        · plugin-surfaces.js ← contributions.list('pages' | 'bangs' | 'menus' | 'userscripts')（§4.7）
        · ThemeManager      ← slots.call('theme.token-provider')
        ▼
④ IPC 出口
        · panel:catalog / panel:list    （渲染层面板目录）
        · plugins:list / plugins:set-enabled / plugins:changed
        · slots:render / slots:dispatch （渲染侧插槽宿主：描述符下行、key 上行派发）
        ▼
⑤ 渲染层（全部由同一份目录驱动）
        · app-shell  → NAVBAR_CATALOG = buildCatalog(entries)
        · rail       → 就地更新 RAIL_ICONS + 追加 side-panel.rail-icon-slot 的插件图标
        · buttons-edit-overlay → refreshCatalog()
        · panels 宿主 → hira-plugin:// 统一加载 panelDefinition + 挂 side-panel.toolbar-action-slot
```

**关键不变量**：③④⑤ 全部**只读**①②产物，没有一个地方自己维护第二份清单。
这就是"禁用插件立刻全链路生效"能成立的原因。

## 3. 扩展点调度器（PART7 §7.3）使用说明

### 四种模式与调用签名

| 模式     | 语义                               | 调用签名                  | 聚合结果             |
| -------- | ---------------------------------- | ------------------------- | -------------------- |
| `SINGLE` | 只能一个生效，**后注册覆盖先注册** | `impl(payload, ctx)`      | 最后一个实现的返回值 |
| `MULTI`  | 全部执行，收集返回值               | `impl(payload, ctx)`      | `[r1, r2, …]`        |
| `REDUCE` | 流水线，前一个返回值喂给后一个     | `impl(acc, payload, ctx)` | 最终 `acc`           |
| `EVENT`  | 全部收到通知，忽略返回值           | `impl(payload, ctx)`      | `undefined`          |

**REDUCE 初值**：取 `spec.initialValue`，未声明则取 `payload` 本身。
所以「过滤一串数据」可写成 `(acc) => acc.filter(...)`，不必为初值再包一层。

**SINGLE 为什么保留全部实现只取最后一个**：这样最后一个实现被禁用时会**自动回落到上一个**，
而不是整个插槽突然变空。

### 三条硬规则（都是踩过坑才定下来的）

1. **先声明后实现**：往未声明的插槽里 `implement()` 直接抛错，并在错误里列出已声明的插槽名
   （Mod 作者最常犯的错是拼错插槽名，只说"未定义"会让人翻半天文档）。
2. **契约校验先于"有没有实现"**：契约约束的是**这次调用**，不是实现集合。
   若放在空实现短路之后，写错入参的调用方会因为"恰好还没人挂实现"而静默通过，
   等有人挂上实现的那天才突然炸 —— 那种延迟爆炸最难查。
3. **错误分流**：
   - 插件实现抛错 → **隔离并跳过**（一个 Mod 写坏了不该拖垮整条链）
   - 同步插槽里塞了异步实现 → **致命**，直接抛给调用方。
     这不是"运行时意外"，是用错了插槽类型；吞掉它只会表现为"菜单项莫名少了一个"。

**同步 vs 异步**：`callSync()` 用于渲染路径与事件钩子；`call()` 允许实现返回 Promise，
且 REDUCE 会**顺序**等待每一步（Pipeline 语义，不能并行）。

### 3.5 菜单类插槽的通用接法（已落地的范式）

`bookmark.context-menu` / `webview.context-menu.item` 这两个走的是同一条范式，
以后接任何「往菜单里加一项」的插槽都照这个来：

```
插件实现（主进程）
  impl(payload, ctx) → { label, enabled?, accelerator?, onSelect?(payload) } | 该数组
        │
        ▼  ① 主进程执行插槽（callSync —— 菜单模板必须同 tick 建好）
  main/slot-menu.js 的 createSlotMenuAdapter().items(slotId, payload)
        │     · 展平一层（MULTI 聚合 + 实现自己返回数组 = 嵌套，见该文件头）
        │     · 非法项丢弃并告警（缺 label / 缺 onSelect）
        │     · 点击时 try/catch，一个坏项不影响其它项
        ▼  ② 编译成原生菜单项，onSelect 直接挂在 click 上
  宿主把结果接到自己的菜单里
```

**关键设计：onSelect 在主进程内派发，不过 IPC。** 菜单本来就是主进程弹的、
实现本来就在主进程跑 —— 让描述符过 IPC 到渲染层再点回来是纯自找麻烦，
而且函数本来也无法序列化。

两个宿主各自的接法：

| 插槽                        | 宿主                                              | 接入方式                                                                                                                                                                  |
| --------------------------- | ------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `webview.context-menu.item` | `browser-window-runtime.js#getExtensionMenuItems` | 与 Chrome 扩展的菜单项**合并**（对用户而言两者是同一件事：页面右键多出来的项）。链路：`tabEvents` → `context-menu.js#compileTemplate` 已预留 `getExtensionMenuItems` 钩子 |
| `bookmark.context-menu`     | `main/ipc/window.js` 的 `ui:popup-menu`           | 渲染层在 `popupMenu({ items, x, y, context })` 里传 `context.kind='bookmark'`；主进程按 `MENU_SLOT_BY_KIND` 白名单映射到插槽，把结果追加到模板尾部                        |

**为什么渲染层只传 `kind` 而不是插槽 id**：插槽 id 若由调用方自由指定，
渲染层（含内部页）就能触发任意插槽（如 `db.schema.migration`）。
`MENU_SLOT_BY_KIND` 相当于给"谁能调用哪个插槽"设了白名单 —— 新增一种可扩展菜单就在那里加一行。

**注意**：插槽贡献的项**不会**经 `ui:popup-menu-selected` 回传 action，
所以调用方的 `switch (action)` 里不需要（也不应该）为它们加分支。

### 3.6 渲染侧插槽（跨进程那一半，`side-panel.*`）

有些插槽的**产出面在渲染层**（面板工具栏按钮、rail 图标），而实现永远是主进程的
`.cjs`（`onSelect` 是闭包）—— 函数过不了 IPC。于是分工必须切成两半，
`key` 是两半之间的唯一凭据：

```
渲染层  slots:render   →  主进程执行插槽 → 剥掉函数 → 回 [{ key, descriptor }]
渲染层  画（只用 descriptor 里的纯数据）
渲染层  slots:dispatch(key) → 主进程按 key 重新执行插槽、找到那个实现 → 调它的 onSelect
```

**为什么 dispatch 是「重新执行插槽」而不是「缓存描述符」**：缓存会引入失效问题
（插件被禁用 / 面板换了 / 数据变了，缓存里还是旧闭包与旧 payload，于是点了一个
已经不存在的项）。重新执行虽然多跑一次实现，但实现的语义就是「描述 + 带一个 onSelect」，
执行它本来就该是纯的、廉价的 —— 这条约束同时也让作者不敢在描述阶段做重活。

**关键约束**：

| 约束                          | 原因                                                                                                          |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------- |
| 渲染层**不能**自由指定 slotId | 白名单 `RENDERER_HOSTED_SLOTS`（`main/slot-render.js`）。否则内部页能触发任意插槽（如 `db.schema.migration`） |
| 渲染侧插槽的实现**必须同步**  | 描述符要在一次 IPC 内取回；实现返回 Promise 会被判为插槽类型用错并降级为空                                    |
| 实现返回数组 = 多个项         | 与菜单同一个坑：MULTI 聚合后是嵌套的，适配器统一展平一层                                                      |
| 实现必须**稳定排序**          | key 是 `<实现键>#<序号>`，序号取自描述符顺序。顺序变了，第 0 项就会在不同调用间指向不同按钮                   |
| 描述符只带纯数据              | 函数 / symbol / bigint 在过 IPC 前被剥掉，限深 6 层                                                           |

已接的两个渲染侧宿主：

| 插槽                             | 宿主                      | 说明                                                                                                                                          |
| -------------------------------- | ------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| `side-panel.toolbar-action-slot` | `renderer/panels/main.js` | 面板头部工具栏。落点是 `ui-common#createPanelShell` 返回的 `actions` 容器（`margin-left:auto`，为空时视觉与改动前逐像素一致）                 |
| `side-panel.rail-icon-slot`      | `renderer/rail/main.js`   | rail 图标列。插件图标是**动作**而非可开关面板，因此不进 `CATALOG`、不参与 `app.rail_buttons` 排序、恒排在面板图标之后，id 用 `slot:` 前缀隔离 |

### 3.7 导航生命周期插槽（`webview.lifecycle.*`）

宿主在 `infra/infra-window/src/tabEvents.js`，策略在 `main/slot-lifecycle.js`（APPS 层）：

| 插槽              | 模式   | 实现签名                | 语义                                                                    |
| ----------------- | ------ | ----------------------- | ----------------------------------------------------------------------- |
| `will-navigate`   | REDUCE | `(acc, payload) => acc` | `return acc` 只观察；`{...acc, url}` 改写；`{...acc, cancel:true}` 取消 |
| `did-navigate`    | EVENT  | `(payload) => void`     | 跳转后通知                                                              |
| `did-finish-load` | EVENT  | `(payload) => void`     | 页面加载完成通知                                                        |

**`will-navigate` 必须同步**：`preventDefault()` 只在原生回调栈内有效，任何 await 都会
让取消失效。因此适配器一律 `callSync`，并把「同步插槽塞了异步实现」当作降级条件
（而不是让导航失效）。

顺序上，PDF 分流（内核行为）**先于**插槽执行 —— 插件不该被迫自己判一遍 `.pdf`。
`did-finish-load` 与新绑的监听分开于 `did-stop-loading`：后者承载的是「标签忙不忙」，
两者在重定向 / 子资源失败时会错开，合成一条会让 Mod 收到错误时机。

### 3.8 渲染侧插槽的第二条路：**同进程直接调用**（`plugin-slots.js`）

§3.6 那条路（`slots:render` / `slots:dispatch`）解决的是「**实现在主进程**、产出面在
渲染层」的插槽。但有一类插槽**天生就在渲染层**：

| 插槽                                                 | 为什么过不了 IPC             |
| ---------------------------------------------------- | ---------------------------- |
| `omnibar.result-item-renderer`                       | 产出物是 DOM 节点            |
| `settings.custom-widget`                             | 产出物是控件 DOM 与事件      |
| `tabbar.item-renderer` / `tabbar.tab-stack-renderer` | 产出物是 DOM                 |
| `bookmark.tree-renderer-item`                        | 同上（REDUCE，逐层包裹 DOM） |
| `download.state-badge-renderer`                      | 同上                         |

硬走描述符只会把它们降级成「只能传纯数据的阉割版」。所以给了第二条路：
**插件的 `.renderer.js` 直接在本进程注册实现，宿主组件直接调用** ——
闭包、DOM、事件都在手，零往返、零降级。

```
插件的 manifest
  "render": "./xxx.renderer.js",
  "contributes": { "rendererSlots": ["omnibar.result-item-renderer"] }
插件的 .renderer.js
  export const rendererPlugin = {
    slots: { 'omnibar.result-item-renderer': (payload, ctx) => HTMLElement }
  }
        │  ① 宿主进程启动时 defineRendererSlots([...]) 声明自己要宿主哪些槽
        │  ② activateRendererSlots() 拉已启用插件清单 → 只 import「manifest 声明了
        │     contributes.rendererSlots、且与本窗口宿主相交」的渲染模块
        │     （面板窗口另加 contributes.panels 的插件；未声明的槽告警忽略）
        ▼  ③ 宿主在渲染时直接调：callRendererSlot / callRendererSlotMulti / reduceRendererSlot
```

> **为什么要声明 `contributes.rendererSlots`**：每个渲染进程都有独立宿主清单，而插件的
> `.renderer.js` 可能是整块面板。没有这份登记就只能「先全量 import、再按宿主过滤」——
> 浮层窗口会白拉笔记 / 扫码器的整块面板代码，还会把「本窗口不宿主」误报成「无人宿主」。
> 登记之后，import 之前就能筛掉不相干的插件（见 `renderer/shared/plugin-slots.js`
> 的 `wantsRendererModule`）。漏写不会崩，而是"在非面板窗口里你的槽静默不生效"——
> 所以面板窗口加载到该插件时会点名告警。

**与主进程调度器同构但不共库**：SINGLE / MULTI / REDUCE / EVENT 的模式语义、
调用签名、错误策略（只告警不上抛）刻意保持一致，`reduceRendererSlot` 的 acc 初值
同样是 payload —— 插件作者不必学第二套心智模型。实现各自独立是必然的：
渲染侧的注册表**不可能**用主进程那份（跨进程），而把调度器整个搬进渲染包
会为一个几十行的容器引入一大片无关依赖。

**生命周期：每个渲染进程一份注册表。** 外壳 / 浮层 / 面板 / rail 各跑各的，
各自 `defineRendererSlots` 自己关心的那几个。这恰好解决了
「一条插槽要在多个渲染进程里各激活一次」的问题 —— 不需要"全局激活"，
谁宿主谁激活。插件启停后宿主再调一次 `activateRendererSlots()`，
注册表整体重建，于是「禁用插件 → 它的实现立刻消失」天然成立，无需增量摘除。

**约束**：

| 约束                               | 原因                                                                                                                                                                                                                                                                                                                                                               |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 宿主必须先 `defineRendererSlots`   | 未声明的槽会被丢弃并告警 —— 静默收下会让插件作者完全无从查起                                                                                                                                                                                                                                                                                                       |
| 内置实现的文件命名必须守 `.renderer.ts` | `scripts/build-plugins.ts` 只把该后缀编译为独立 ESM；主进程 `.cts` 与渲染代码因此天然分树。运行时安装的第三方模块可写 `.js/.mjs/.cjs` |
| 静态内部页可做宿主 | 渲染入口统一走 `hira-plugin://` 动态加载，不再依赖 `import.meta.glob`。页面若需要 `renderer/shared`，将其登记到 `SOURCE_BUNDLED_PAGES`，只打包入口模块；协议层无需页面特例。设置页即参考实现（§15.11） |
| 交互机制由宿主统一接管             | 例如下拉行的「点击提交 / 悬停改选中 / 键盘高亮」仍由 `searchbar-overlay` 实现 —— 交给每个插件各写一份必然漂移                                                                                                                                                                                                                                                      |

已接的同进程渲染侧宿主：

| 插槽                                                 | 宿主                                                          | 契约                                                                                                                                                                     |
| ---------------------------------------------------- | ------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `omnibar.input-transformer`                          | `app-shell/main.js`                                           | REDUCE，`(acc, payload) => string`。**只改写输入的含义，绝不回写输入框**（回写会表现为"打着打着字自己变了"）。建议 / 搜索地址 / 搜索历史**同源**使用转换后的文本         |
| `omnibar.result-item-renderer`                       | `searchbar-overlay/main.js`                                   | SINGLE，返回一个 `HTMLElement`（非 Element 一律回落默认行）。选中 / 提交 / 悬停由宿主统一接管                                                                            |
| `tabbar.item-renderer` / `tabbar.tab-stack-renderer` | `app-shell/main.js` → `ui/ui-tabbar`                          | SINGLE，**装饰层**语义（不是替换行，见 §3.9）。返回元素被追加到标签行 / 芯片尾部；非 Element 一律忽略                                                                    |
| `tabbar.drop-target`                                 | `app-shell/main.js` → `ui/ui-tabbar`                          | MULTI，`(payload) => truthy?`。**抢答**：任一实现返回真值即认领这次拖放，宿主内置语义（插入排序 / 与目标堆叠 / 并入标签组）不再执行                                      |
| `side-panel.panel-render-slot`                       | `panels/main.js`                                              | MULTI，`(payload) => HTMLElement`。往面板**内容区**追加一块主体（接在面板本体之后）；返回元素会被加上 `side-panel__plugin-body`                                          |
| `side-panel.panel-header-renderer`                   | `panels/main.js`（消费方在 `ui-common#createPanelShell`）     | REDUCE，`(acc) => acc`。`acc` 是头部描述符 `{ panelId, title, titleElement, className }` —— 改文案 / 换成自己的节点 / 加类名，改哪个字段落在哪一格是确定的               |
| `download.state-badge-renderer`                      | `panels/main.js` 端口注入 → `ui-panel-downloads`              | SINGLE，返回元素替换内置状态文字；非 Element → 回落内置文案。payload 里给的是**宿主已经算好的量**（`percent / speed / eta / stateText`）                                 |
| `bookmark.tree-renderer-item`                        | `panels/main.js` 端口注入 → `ui-panel-favorites`              | REDUCE，`(acc) => acc`。`acc` 是 `{ node, depth, isFolder, element }` —— **行的外层包装**语义（行本身仍是宿主的，见 §3.9）                                               |
| `layout.root-slot`                                   | `app-shell/main.js`                                           | MULTI，`(payload) => HTMLElement`。落在 chrome 根图层；**默认不吃指针**（要交互请自己写 `pointerEvents = 'auto'`）                                                       |
| `settings.custom-widget`                             | `pages/settings/custom-widgets.ts`                          | MULTI，`(payload) => HTMLElement \| { title?, blurb?, element } \| null`（`null` = 这个分区不参与，最常用）。**每插件一张卡**；切分区整体重建，摘除前派发 `hira:dispose` |

**关键机制：ui 包怎么用插槽却又不认识插件系统。**

`ui-panel-downloads` / `-favorites` 这两块的调用方在 `ui/` 包里，而 ui 不得 import `apps/**`
（CONTRACT-11）。做法是**端口反向注入**：`panels/main.js` 把三个通用函数
`ctx.slots = { call, callMulti, reduce }` 交给面板，面板只知道"按 id 调一个函数"。
于是 ui 包对"谁实现、怎么注册、启用没启用"零知识，同时也不必为每一个新插槽
在包之间加一条依赖边 —— 加插槽仍然只是"宿主多声明一个 id + 面板多调一次"。

### 3.9 三个"看起来能替换、实际只能追加"的插槽（为什么）

`tabbar.item-renderer` / `tabbar.tab-stack-renderer` / `bookmark.tree-renderer-item`
在官方表里的措辞都是「渲染器」。按字面做成"插件返回什么就显示什么"是**能跑通**的，
但会把这套界面里最贵的两套机制作废：

| 宿主                          | 它自己掌握着什么                                                                                                                                              | 换掉节点会失去什么                                                                                                    |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| `ui-tabbar` 的标签行          | keyed 复用（`nodeRecords` 按 `tab:<id>` 复用节点）、字段级 diff（只对变化字段调 `update`）、开合两阶段动效（`is-tab-entering` / `is-tab-closing`）、FLIP 让位 | "切个标签整条栏闪一下"、拖拽重排错位、关闭动效丢帧。而标签条是界面**最热**的渲染路径（每次切标签 / 收标签都重画一遍） |
| `ui-panel-favorites` 的书签行 | `data-row` / `data-id` / `data-url` / `data-folder-id` 被**容器上的事件委托**读取（点击 / 右键 / 拖拽落点三分带全靠它们）                                     | 插件必须逐个复刻这套属性契约；漏一个的症状是「这一行拖不动了 / 点不动了」，而原因在插件里，宿主连线索都没有           |

所以这三个的契约统一定为 **追加 / 包裹，不替换**：

| 插槽                                                 | 插件能做的                                                             | 插件不能做的                                                                                               |
| ---------------------------------------------------- | ---------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| `tabbar.item-renderer` / `tabbar.tab-stack-renderer` | 往行的**尾部**追加一块自己的 DOM（角标、额外图标、小段文字、进度指示） | 换掉整行 —— 那需要一个以"整行替换"为前提重写状态机的插槽（现在没有，也不该为一个插槽把最热路径的机制拆掉） |
| `bookmark.tree-renderer-item`                        | 在行**外面套一层**自己的容器（想加什么加在那层里）                     | 换掉行本身 —— 见上表第二行                                                                                 |

两条硬约束（`ui-tabbar/src/components/decoration.js`，装饰层）：

1. **装饰层不可拦截指针**（`.tab-decoration { pointer-events: none }`）。标签条最不可让步的
   性质是"标签始终可点"；一个能吃掉点击的装饰层会让"点了标签没反应"这种最难归因的问题变得可能。
   需要可交互装饰的场景应当走新的插槽语义（"行内按钮"），而不是放宽这一条。
2. **插件抛错不能拖垮标签条**。装饰没了，标签还得在。

`layout.root-slot` 的另一条边界（容易误解，所以写清楚）：本项目的网页是叠在 chrome 之上的
**原生 WebContentsView**，DOM 的 z-index 对原生视图无效 —— 这个槽的可见范围就是 chrome
（navbar 与侧栏之间的区域），**盖不住网页**。默认 `pointer-events: none`：根级图层若默认吃指针，
一次插件写坏就是"整个浏览器点不动"。

### 3.10 域宿主插槽的契约速查（主进程）

「域宿主」= 插槽被接进一条**真实数据流**（搜索 / 历史 / 空间切换 / 快捷键 / 数据库 /
语言包 / 导入 / 设置），而不是只往界面贴东西。这些槽统一用 `slot-call.js` 调
（错误只告警、绝不上抛），契约如下：

| 插槽                         | 模式   | 实现签名                                            | 语义与坑                                                                                                                                |
| ---------------------------- | ------ | --------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| `search.suggestion-provider` | REDUCE | `(acc, payload) => acc`                             | `payload` 是建议数组，`acc` 初值即它 → 直接 `acc.concat(...)` / `acc.filter(...)`。第二参 `ctx` 才是 `{ query, limit }`                 |
| `history.search-filter`      | REDUCE | `(acc, payload) => acc`                             | 同上，`acc` 是历史行数组                                                                                                                |
| `profile.on-before-switch`   | REDUCE | `(acc, payload) => acc \| null`                     | `acc` 初值是 `{ from, to }`。返回 `null`/`{ cancel: true }` **拦截切换**                                                                |
| `profile.on-after-switch`    | EVENT  | `(payload) => void`                                 | 只通知，返回值被忽略                                                                                                                    |
| `shortcut.binding`           | MULTI  | `(combo) => ({ run }) \| null`                      | **每次按键现问一次**（不做缓存合并，见 `keybindings.js` 的说明）。只在**内置绑定未命中**时才问 —— 插件抢不走 Ctrl+T                     |
| `db.schema.migration`        | MULTI  | `() => { id, up(sqlite) } \| 该数组`                | `id` 按字典序执行（用 `001-` 前缀自排）；靠 `_schema_migrations` 记账表**幂等**。宿主在「插件启动完成」与「运行期启用插件」两处都会补跑 |
| `l10n.bundle-provider`       | MULTI  | `() => ({ messages: { key: text } })`               | **内建优先**：官方语言包已有的键插件覆盖不了。返回数组（多 bundle）也认                                                                 |
| `bookmark.import-format`     | MULTI  | `() => ({ format, label?, toHtml(content) })`       | 产出**Netscape HTML**，再走既有 `importHtml` 入库 —— 插件不碰数据层。格式清单另走 `contributes.importFormats`（声明侧，不必执行插件）   |
| `settings.section-renderer`  | MULTI  | `() => { id, label, icon?, blurb?, fields: [...] }` | 与**内建分区同形**，于是设置页（纯通用渲染器）零改动即可画出插件分区。入口处会剪成"能画"的最小合法形态                                  |

> ⚠ **「只搬实现、不搬副作用」是最容易踩的坑**（已在 `ipc/space.js` 上真实发生过）：
> `invoke(capability, fallback)` 的第二参**只在没有 provider 时**执行。把
> `notifyChanged` / 建表 / 广播这类**副作用**写在 fallback 里，插件一上线副作用就静默消失。
> 副作用必须写在 handler 本体里，fallback 只负责"没有插件时返回什么"。

### 契约（Zod）怎么接

`infra-plugin` **不依赖 zod**（PART3 §3.5 分层要求）。契约以鸭子类型为准：任何有
`safeParse` 的对象都能当 schema 用。APPS 侧通过 `registerOfficialExtensionPoints(registry, { schemas })`
注入 zod schema，键为插槽 id。

## 4. 操作手册：怎么加新东西

### 4.1 加一个侧栏面板（零核心改动）

**推荐做法：面板由插件自带**（`entry.render`）。面板的**声明**与**实现**放在同一个插件里，
插件目录即完整资产 —— 删掉它，面板彻底消失，不用动宿主一行。

1. 建 manifest `apps/app-main/plugins/panel-xxx.hira-plugin.json`：
   ```json
   {
     "id": "panel-xxx",
     "name": "XXX 面板",
     "version": "0.0.1",
     "type": "ui-panel-plugin",
     "trustLevel": "internal",
     "description": "……",
     "main": "./panel-generic.cjs",
     "render": "./panel-xxx.renderer.js",
     "contributes": {
       "panels": [
         {
           "id": "xxx-panel",
           "title": "XXX",
           "icon": "Star",
           "order": 200,
           "segment": "panel"
         }
       ]
     },
     "dependsOn": ["side-panel-skeleton"]
   }
   ```
2. 建 `apps/app-main/plugins/panel-xxx.renderer.js`：
   ```js
   import { injectPanelStyles } from '@hira-ng/ui-common';

   export const rendererPlugin = {
     panels: [
       {
         id: 'xxx-panel', // 必须与 manifest 的 contributes.panels[].id 一致
         injectStyles(doc) {
           injectPanelStyles(doc);
         }, // 可选
         mount(doc, ctx) {
           return { element };
         }, // ctx 见 4.6
       },
     ],
   };
   ```
3. 完成。rail 图标、navbar 按钮、按钮编辑浮层、面板本体**四处同时生效**；
   禁用该插件则四处同时消失。

**两条硬约束**（都由 `pnpm plugin:coverage` 把关）：

- 内置实现的文件名**必须**以 `.renderer.js` 结尾。构建脚本只把 `.renderer.ts` 编译成
  独立渲染模块；这样 `plugins/` 里的主进程 `.cjs`（`require('fs')` 那类）绝不会被误装。
  名字写错时产物不存在，门禁会直接拦下。
- `render` 指向的文件必须真实存在。
- `render` 是**可执行模块**，扩展名只认 `.js` / `.mjs` / `.cjs`。写成 `panel.html` 不是
  "渲染入口"，而是声明式 UI 面（见 §4.1.1）—— 注册中心会自动改判并置空 `render`
  （`plugin-ui.mjs#isRenderModulePath`），否则渲染层会把 HTML 当模块 `import()`，
  永远失败且**挡住**后面本来能成功的 `ui` 路径。
- 声明式 UI 的字段别名（`ui` / `uiEntry` / `entry` / `html` / `view` / `src` / `path` / `render`）
  与**顶层继承**（manifest 顶层写一次 `ui`，`contributes.panels[]` 里的每块面板都能用）
  都是运行期自愈的一部分，真源 `plugin-ui.mjs`。
- `render` 缺省但目录里存在 `render.js` / `<id>.renderer.js` 等候选时，注册中心会自动补上
  （候选顺序真源 `plugin-ui.mjs#renderEntryCandidates`）；自查口 `plugin_list` / `studio_list`
  会回传 `render` / `uiEntry` / `panels[].implementation`。

> **为什么 `.renderer.js` 而不是把 UI 代码放进 `ui/` 包**：后者是历史形态 ——
> 那时 manifest 只能声明 id，实现必须先在 `ui/` 下存在一个包，于是
> **第三方插件插不进来**（它无法往仓库里加包）。`entry.render` 才让"插件声明面板"
> 成为完整机制。`ui/ui-panel-*` 那一路仍然工作（其余 10 个面板还在用），
> 但**优先级低于插件自带的实现**：两边同时存在会告警并以插件为准。
> `panel-notes` 已迁到 `render` 形态作为参考实现。

**图标名**取自 `packages/shared-types/src/icon-names.mjs`（与
`ui/ui-common/src/icons.ts#ICON_REGISTRY` 逐一对应，构建时自检）。写名字时允许别名与
大小写 / 分隔符差异；也可以直接写 `data:image/…` / `hira-plugin://<id>/…` /
`http(s)://…` / `<svg>…</svg>` 原文。无法识别的名字**不再导致空白按钮** ——
统一回落 `Puzzle`（见 `icons.js#resolveIcon`）。

**所有渲染入口**（`renderer/shared/plugin-renderer.js`）都走同一条运行时协议，
按形态依次尝试，全部失败才回落 `ui` 面 / `ui-panel-*`：

1. `import(hira-plugin://<id>/<render>?v=<mtime>)`（ESM，第一方与第三方同路）；
2. `fetch` 源码后按 CommonJS 求值（`.cjs` 也能用，但**不能 `require()`**，须自包含）；
3. 再退到 Blob URL `import()`。

模块缓存键包含版本化 `renderUrl`，插件热重载后不会继续执行旧模块。

导出形状也放宽：`rendererPlugin` / `default` / `panels[]` / 单面板 `{ id, mount }` 都认；
`mount(doc, ctx)` 与 `mount(input)` 两种签名会自动适配
（`input` 提供 `element/doc/container/root/bridge/hira`）。加载失败时面板不再是笼统的
「尚未实现」，而是具体到阶段：`no-manifest` / `no-entry` / `load` / `no-panel`
（见 `panel-resolve.js#getPanelResolveError`），失败原因同时打控制台。

**两条实现路径并存，别混用**：

| 面板实现                                     | 加载时机                                                                                  | 适合什么                                                                      |
| -------------------------------------------- | ----------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| `entry.render`（`plugins/*.renderer.js`）     | 构建为独立 ESM，再由 `hira-plugin://` 按需 `import()`；第三方同路（§15）                  | 要直接操作 DOM、复用 `ui/` 组件、或拿面板 `ctx` 的**全部**能力（§4.6）        |
| `contributes.panels[].ui`（`.html` / `.xaml`） | **始终运行时**按需 `fetch` 文件（`hira-plugin://<id>/<相对路径>`）                        | 只要一块界面 + `hira.*` 能力；零构建、零渲染代码、改完刷新即见（见 §4.1.1）    |

渲染侧 JS 与声明式 UI 面都已是**运行时路径**；第一方只是多一步独立构建，
监听器与加载规则始终只有 `renderer/shared/plugin-renderer.js` 一份。

#### ② 一次渲染发生了什么

```

    → panels/host.js#resolvePanelDefinition（优先级：entry.render > panelUi[] > ui/ui-panel-*）
      → panel-ui-frame.js#createPanelUiDefinition
```

**面板视图永远不 `loadURL` 插件 HTML**：插件界面只能以「内嵌沙箱 iframe + srcdoc」出现，
能力走消息桥。面板 `WebContentsView` 的 preload 里那份未沙箱的 `window.hira`
永远不会交给插件文档 —— 这是整条路能"彻底开放"的前提。

#### ③ 安全模型（作者必须知道的边界）

| 机制             | 具体做法                                                                                                       | 对作者的含义                                                                 |
| ---------------- | -------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| 沙箱             | `sandbox="allow-scripts allow-forms"`，**永不含 `allow-same-origin`**                                            | 文档停在 opaque origin：读不到父页面 DOM，也没有 localStorage/cookie/IndexedDB |
| CSP              | 宿主派生 `default-src 'none'`；`style-src`/`script-src` 仅自身 + 内联；图片仅自身/`data:`/`blob:`                 | 别引 CDN；要出网必须在 manifest 申请 `network` / `full`，否则 `connect-src` 只有自身 |
| 基址             | `<base href="hira-plugin://<id>/">` + `base-uri` 只允许自身                                                     | 相对路径只能落在自己包里；自己写 `<base>` 会被 CSP 拦掉                       |
| 入口体积         | 单文件 ≤ **2 MiB**                                                                                              | 大资源拆文件，别把 base64 塞进入口                                            |
| 扩展名白名单     | 只有 `.html` / `.htm` / `.xaml` 能当 UI 入口                                                                     | 想复用 `.md` / `.json` 得自己 fetch（受 CSP 限制）                             |
| 目录穿越         | 相对路径、无 `..`、协议层再做一次根目录前缀校验                                                                  | 不可能读到别的插件或系统文件                                                  |
| 表单             | `allow-forms` 只让输入控件可用，`form-action 'none'` 禁止提交到外部                                              | 表单当"本地输入"用，提交走 `hira.*`                                           |
| 桥限流           | 令牌桶 240 次 / 10 s、并发 64、单次参数 256 KiB                                                                  | 别在 `requestAnimationFrame` 里调宿主                                         |
| 消息校验         | 父侧只认 `event.source === iframe.contentWindow` 且 `event.origin` 为 opaque，且必须带 `__hira_panel_ui__` 标记   | 页面里其它 `postMessage` 无法冒充桥                                           |

由此得出**三条硬约束**（写成注释贴在文件头，示例里都标注了）：

1. **没有 Web Storage**：持久化只能用 `hira.storage.*`（按 profile + 插件隔离的 SQLite 表）。
2. **不引外部资源**：字体、图标、脚本全部打包进插件目录；图片用相对路径或 `data:`。
3. **`window.hira` 是唯一能力入口**，且被 `defineProperty` 钉死（不可写、不可配置）；
   别去猜有什么方法 —— 用 `hira.capabilities()` 现问，宿主加能力不必改文档。

#### ④ `hira.*` 能力表（就是 `hira.capabilities()` 的返回值）

所有能力的 `minLevel` 都是 `ui` —— 界面面本身不与网络/进程打交道，**差异只在 `scope`**。

> `#PANEL_UI_EVENTS`（5 条）。桥按 `method` 合并实现并双向校验（缺实现 / 缺元信息都启动抛错），
> 所以「文档有、代码没有」或反过来都不可能发生。AI 侧入口：结构化数据取 `studio.capabilities().panelUi`，

**事件订阅**走 `hira.on(channel, fn)`，返回退订函数；通道是**白名单**，不是任意 IPC 事件名：

| 通道                | scope            | 触发时机           |
| ------------------- | ---------------- | ------------------ |
| `theme:changed`     | —                | 主题 / 深浅色切换  |
| `tabs:changed`      | `tabs:read`      | 标签增删改、激活   |
| `bookmarks:changed` | `bookmarks:read` | 书签变更           |
| `plugins:changed`   | —                | 插件启停 / 重载    |

补充：主题切换时宿主会**主动**把新的 `:root{…}` 推给面板 iframe 并**只替换样式表**，
不重渲文档 —— 纯声明式 XAML 也会立即换色，且滚动位置、输入焦点不丢。面板 JS 若需要
做逻辑响应（例如换主题后重画 canvas），仍然用 `hira.on('theme:changed', …)`。

调用是 Promise：宿主返回 `ok:false` 时**直接 reject**（`error.message` 就是原因），
所以 `try/catch` 或 `await` 就够了，不必解析信封。

#### ⑤ XAML 三条硬规则

1. **只认元素表**（`packages/shared-types/src/xaml.mjs#ELEMENTS`）：
   - 布局：`Grid` `StackPanel` `DockPanel` `WrapPanel` `Canvas` `Border` `ScrollViewer` `Viewbox` `ContentControl` `UserControl` `Page` `Window`
   - 文本：`TextBlock` `Run` `Span` `Hyperlink` `Separator`
   - 输入：`Button` `TextBox` `PasswordBox` `CheckBox` `RadioButton` `ComboBox`（+ `ComboBoxItem`）`Slider` `ProgressBar` `ToggleSwitch`
   - 列表/容器：`ListView`（+ `ListViewItem`）`ListBox`（+ `ListBoxItem`）`Expander` `TabControl`（+ `TabItem`）
   - 媒体：`Image`

   表外的标签**不会报错**，会退化成一个带 `data-hira-xaml-tag` 的容器（内容照常显示）——
   所以"整块空白"通常不是标签问题，而是入口没取到（看宿主控制台的 `[panel-ui:<id>]` 报错）。
2. **事件只写名字，不写调用**：`Click="Refresh"` / `Change="OnNoteChanged"`。
   编译器把它翻成 `data-hira-click` / `data-hira-change`，由固定运行时派发 `hira-xaml`
   CustomEvent（`detail = { handler, element, event, value?, checked? }`，冒泡到 root）。
   属性值**永远不会被 eval** —— 攻击面收敛在这里，能力不减。
3. **绑定只能声明**：`Text="{Binding Plugin}"`（也认 `{Binding Path=User.name}` 与 `{x:Bind …}`），
   再由脚本调 `window.__hiraXaml.bind({ Plugin: 'x' })`。绑定不会求值表达式，也不会写 HTML。
   - 绑定目标是**按控件类型**写的：输入框 / 下拉写 `value`、勾选写 `checked`、进度写 `value`、其余写 `textContent`
     —— 所以 `TextBox Text="{Binding Note}"` 会真的显示内容（旧实现只写 `textContent`，永远空白）。
   - 支持嵌套路径（`User.name`）与**局部更新**：`__hiraXaml.set('User.name', 'x')` 只改这一个键，
     不需要为改一个字重新 `bind()` 整份状态；`__hiraXaml.get(key)` 读当前值。
   - 用户正在聚焦的输入框不会被 `bind()` 覆盖（否则打字打到一半会被旧值顶回去）。
4. **大段脚本可以外置**：`<Script src="panel.js" />` —— 相对路径经 `<base>`
   落回插件目录（协议层带 ETag/版本缓存）。绝对路径、`..`、`http(s):` 等一律拒绝，
   仍按内联文本处理。

```xml
<Page Title="示例">
  <StackPanel Spacing="8">
    <TextBlock Text="插件：{Binding Plugin}" />
    <Button Content="刷新" Click="Refresh" />
    <TextBox x:Name="note" PlaceholderText="备注" Change="OnNoteChanged" />
    <ProgressBar x:Name="gauge" Maximum="100" Value="42" />
  </StackPanel>
  <Script><![CDATA[
    var root = document.querySelector('[data-hira-xaml-root]');
    root.addEventListener('hira-xaml', function (e) {
      if (e.detail.handler === 'Refresh') refreshAll();
      if (e.detail.handler === 'OnNoteChanged') console.log(e.detail.value);
    });
    window.__hiraXaml.bind({ Plugin: 'demo' });
  ]]></Script>
</Page>
```

其余要点：

- **元素名大小写不敏感**（`<TextBlock>` / `<textblock>` 等价，内部按小写查表）；
  **属性名大小写敏感**（`Click` ≠ `click`，精确匹配）。`Grid.Row` / `Grid.Column` / `Grid.RowSpan`
  这类带点的**属性名**合法；带点的**元素名**（如 `<Grid.RowDefinitions>`）是"属性元素"，
  由父容器消费，漏到渲染层会被丢弃。
- `x:Name="note"` 直接映射成 `id="note"`，可 `document.getElementById`。
- `RowDefinitions="Auto,*,120"` 与 `<Grid.RowDefinitions><RowDefinition Height="*"/></Grid.RowDefinitions>` 两种都行。
- `Background` / `Foreground` / `BorderBrush` 接受任意 CSS 颜色和 `var(--hira-*)`；
  `url(` / `expression(` / `javascript:` / `@import` 会被 `safeCssValue` 拒掉。
- 控件默认皮肤已内置（`.hira-xaml-*` 类，颜色全走 `--hira-*`），作者只写声明；
  内联 `style` 优先级更高，想覆盖就写属性。
- `<Script>` 会被收集到产物**末尾**（在运行时脚本之后），所以 `window.__hiraXaml` 一定已存在；
  `<style>` / `<link>` / `<iframe>` / `<object>` 等标签直接丢弃（皮肤走属性，不走来路不明的 CSS）。
- 编译上限：深度 64、节点 4000、产物 4 MiB；`<!DOCTYPE>` / `<!ENTITY>` 一律拒绝（无实体扩展）。

#### ⑥ 主题令牌

宿主把当前生效的 `--hira-*` 计算值作为 `:root{…}` 注入 srcdoc，**深浅色自动跟随**。写界面时：

- 前景用**面板档**：`--hira-panel-fg` / `--hira-panel-fg-soft` / `--hira-panel-fg-muted`
  （没设时回落到 `--hira-text-primary/secondary/tertiary`）；
- 背景别自己铺：iframe 容器透明，面板底色由外壳透出；确需分区才用 `--hira-bg-subtle` / `--hira-surface-soft`；
- 强调与语义：`--hira-accent` / `--hira-on-accent` / `--hira-danger` / `--hira-warn` / `--hira-success`；
- 线用 `--hira-border-subtle`，交互态用 `--hira-hover-bg`，输入底用 `--hira-field-bg`。

不在表里的名字不会报错，只会**取不到值**（`var()` 走兜底）。完整名单以 `hira.theme.tokens()` 为准。

#### ⑦ 校验与常见白屏原因

```bash
pnpm plugin:validate panel-ui-lab       # 作者手上这一遍
pnpm plugin:coverage                    # 仓库级门禁
```

校验器会拦：`ui` 入口不合法（绝对路径 / 穿越 / 扩展名不对 / `kind` 冲突）、入口文件不存在、
既无 `main` 又无 `ui` 面。运行时常见白屏原因：

1. 文件名大小写与实际不一致（打包/跨平台后才暴露）；
2. 入口超过 2 MiB；
3. XAML 用了属性元素但父容器不支持（内容被丢弃，看起来像"少了一块"）；
4. 面板插件没启用（`defaultDisabled` 的插件要先在插件中心打开）；
5. **整份界面一点样式都没有、绑定/点击全部失灵** → 打开元素面板看是不是 `hira-xaml-unknown`：
   标签不在元素表里（拼错 / 用了自定义控件名）就会被降级成 div —— 内容还在，皮肤与事件没有；
6. 控制台报 `Fetch API cannot load hira-plugin://… URL scheme "hira-plugin" is not supported`
   —— **不是**"渲染进程 fetch 不支持自定义 scheme"，而是 `hira-plugin` 没被登记成特权协议。
   全库只有 `main/scheme-privileges.js#registerAppSchemes()` 一次
   `registerSchemesAsPrivileged` 调用（那个 API 是**覆盖语义**，分散调用会互相顶掉）。


- `contributes.panels[]` 里 `id` / `title` / `icon` / `ui` 四项就够用；`order` / `segment` 可选。
- `ui` 是**唯一**的面板实现字段（字符串或 `{ entry, kind }`）。`entry` / `html` / `view` /
  `renderEntry` 是模型自创过的名字，宿主不认（创作侧会自动纠正并给 warning）。
- `permissionLevel` 只写 `none` / `ui`（第一方才可能 `network` / `full`）；
  **`network` 只放开 `img/media/connect`，永远不放开脚本外链**。
- `requestedPermissions` 写「想用什么」，不写「已授权什么」—— 授权由用户在插件中心确认。
  没声明 `storage:read` 却调 `hira.storage.get()` 会直接 reject（错误信息里带缺失的 scope）。

**② `panel.html`**（与 manifest 同级，放插件根目录）

```html
<!doctype html>
<html lang="zh-CN">
<head>
  <meta charset="utf-8">
  <title>固定书签</title>
  <style>
    :root { color-scheme: light dark; }
    body {
      margin: 0; padding: 12px;
      /* 面板文档能拿到主题令牌 → 永远用 var(--hira-font-ui)，不要自己写字体串。
         兜底值必须与 shared-types/font-stack.mjs#UI_FONT_STACK 逐字同值。 */
      font: 13px/1.5 var(--hira-font-ui, "Segoe UI Variable Text", "Segoe UI Variable", "Segoe UI", "Microsoft YaHei UI", "Microsoft YaHei", "PingFang SC", "Noto Sans SC", system-ui, -apple-system, sans-serif);

    }

    .row:hover { background: var(--hira-hover-bg); }
    /* 只给第一方插件看的元素 —— 纯 CSS 分支，不写一行 JS */
    .first-party-only { display: none; }
    html[data-hira-first-party="true"] .first-party-only { display: block; }
  </style>

  <h1 id="title">加载中…</h1>
  <div id="list"></div>

  <!-- 不能写 type="module"：opaque origin 下会被 CORS 拦；也不能引 CDN -->
  <script src="./panel.js"></script>
</body>

```

**你什么 hira:// 都不用声明**。`<head>` 里只需要 `<meta charset>` 与 `<title>`：

| 你可能想写的 | 实际做法 |
| --- | --- |
| `<script src="hira-plugin://…/panel.js">` | 写 `./panel.js`。宿主注入的 `<base href="hira-plugin://<插件id>/">` 会把它解析过去 |
| `<base href="…">` | **不要写**。宿主已注入，且 `base-uri` 只允许自身 —— 自己写的会被 CSP 拦掉 |
| `<meta http-equiv="Content-Security-Policy">` | **不要写**。宿主按 `permissionLevel` 派生并放在文档最前面，写了只会更严或无效 |
| `<script type="module">` | **不可用**。opaque origin 下模块按 CORS 取，而 `hira-plugin://` 不发 ACAO。用经典脚本 + async IIFE |
| CDN 的 `<script>` / `<link>` | **不可用**。`script-src` 只有 `hira-plugin:` 与 `'unsafe-inline'` |
| `localStorage` / `cookie` / `IndexedDB` | **不存在**。持久化一律 `hira.storage.*`（按 profile + 插件隔离） |

**③ `panel.js`**（`window.hira` 一定早于本文件就位；经典脚本没有顶层 `await`，所以用 IIFE）

```js
(async function () {
  // 身份：我是谁、哪个面板、什么权限档
  const info = await hira.app.info()
  document.title = '固定书签 · ' + info.panelId

  // 能力自查：不用背文档，宿主现问现答
  const caps = await hira.capabilities()
  console.log('可用能力', caps.map((c) => c.method))

  // 持久化：沙箱里没有 Web Storage，一律走宿主
  const pinned = (await hira.storage.get('pinned')) || []
  await hira.storage.set('pinned', pinned)

  // 主题：可读令牌，也可纯 CSS 用 var(--hira-*)
  const tokens = await hira.theme.tokens()
  document.body.style.background = tokens['--hira-panel-bg'] || 'transparent'

  // 事件：返回退订函数，卸载时必须调
  const off = hira.on('bookmarks:changed', () => refresh())
  window.addEventListener('pagehide', () => off())

  await refresh()

  async function refresh() {
    const items = await hira.bookmarks.list()
    const list = document.getElementById('list')
    list.textContent = ''
    for (const item of items) {
      if (!item || !item.url) continue // 文件夹 / 分隔项跳过
      const row = document.createElement('div')
      row.className = 'row'
      row.textContent = item.title || item.url
      row.onclick = () => hira.tabs.open(item.url)
      list.appendChild(row)
    }
  }
})()
```

**怎么拿 `hira.*` 能力**（完整 40 条见 ④）

- **方法即路径**：`hira.tabs.list()` / `hira.storage.get('k')` / `hira.ui.confirm({ … })`。
  子侧是一个泛化 Proxy —— 不 import、不知道 IPC 通道名，只认「方法路径」；父侧逐条判定
  权限级别 + scope + 参数体积 + 限流。
- **一律返回 Promise**，宿主 `ok:false` 时**直接 reject**（`error.message` 就是原因），
  `try/catch` 或 `await` 即可，不必解析信封。
- **不确定有什么就用 `hira.capabilities()`**：返回 `[{ method, minLevel, scope, summary }]`。
- **订阅用 `hira.on(channel, fn)`**：返回退订函数，白名单 5 条通道（见 ④），
  不订阅就收不到；`pagehide` 必须退订，否则桥会一直往已销毁的 iframe 发消息。
- **`window.hira` 被 `defineProperty` 钉死**（不可写、不可配置），插件脚本覆盖不掉。

**宿主在 `<head>` 里注入了什么**（7 段，按顺序；插件不写、也写不了）

| # | 注入内容 | 作用 |
| --- | --- | --- |
| 1 | `<meta charset="utf-8">` | srcdoc 没有响应头，中文靠它 |
| 2 | `<meta http-equiv="Content-Security-Policy">` | 按 `permissionLevel` 派生：`default-src 'none'`，`script-src` 只有 `hira-plugin:` + inline |
| 3 | `<base href="hira-plugin://<插件id>/">` | 让 `./panel.js`、`./icon.svg` 直接指向插件目录 |
| 4 | 主题变量 `<style>:root{--hira-*:…}</style>` | 直接 `var(--hira-panel-fg)`，深浅色自动跟随 |
| 5 | 身份脚本 | `window.__hiraPanelUiPluginId` + 下面 6 个 `<html data-hira-*>` |
| 6 | 桥脚本 | 定义 `window.hira`，一定在插件自己的脚本之前执行 |
| 7 | 最小基础样式 | `margin:0` / 系统字体 / 透明背景 / `box-sizing` |

**`<html>` 上的 `data-hira-*` 约定**（可信内联脚本写入，插件源码无法伪造）

| 属性 | 值 | 例子 |
| --- | --- | --- |
| `data-hira-plugin-id` | 插件 id | `pinned-bookmarks` |
| `data-hira-panel-id` | 面板 id（= `contributes.panels[].id`） | `pinned` |
| `data-hira-panel-kind` | 文档种类：`html` / `xaml` | `html` |
| `data-hira-permission-level` | `none` / `ui` / `network` / `full` | `ui` |
| `data-hira-first-party` | `"true"` / `"false"`（第一方免逐个 scope 授权） | `false` |
| `data-hira-bridge-version` | 桥协议版本（当前 `1`） | `1` |

纯 CSS 分支就用它（比 `hira.app.info()` 更早、不用等 Promise）：

```css
html[data-hira-first-party="true"] .first-party-only { display: block; }
html[data-hira-panel-kind="xaml"] .html-hint { display: none; }
```

### 4.2 提供一个新扩展点（宿主侧）

1. 在 `official-extension-points.js` 的官方表里加一行 `{ id, mode, description, owner }`。
2. 在**宿主**里接线（点名调用）：
   ```js
   const out = await ctx.extensionPoints.call('your.ep.id', payload);
   // 渲染路径用 callSync；REDUCE 记得给 initialValue 或在 spec 里声明
   ```
3. 宿主拿不到调度器时：进程级单例在 `main.js` 里创建（`extensionPoints`），
   按需注入宿主（参考 `createThemeManager({ extensionPoints })`）。

### 4.3 接一个新的渲染侧插槽（产出面在渲染层）

1. 加官方插槽声明（`official-extension-points.js`，MODE 用 `MULTI` 或 `SINGLE`）。
2. 把 slotId 加进 `RENDERER_HOSTED_SLOTS`（`apps/app-main/src/main/slot-render.js`）。
3. 在渲染层宿主里：
   ```js
   const items = await slotsClient.render('your.slot.id', {/* payload */});
   for (const { key, descriptor } of items) {
     // descriptor 只有纯数据；要画的图标用 iconByName(descriptor.icon, doc)
     element.onclick = () =>
       slotsClient.dispatch('your.slot.id', key, {/* payload */});
   }
   ```
4. 在宿主里订阅 `IPC_EVENTS.pluginsChanged` 重挂一次（插件启停会改变项集合）。

**插件的实现写法**（与菜单插槽一致）：

```js
extends: [{ to: 'your.slot.id', impl: (p) => ([
  { id: 'a', label: '第一个按钮', icon: 'Camera', onSelect: () => { /* 在主进程执行 */ } },
  { id: 'b', label: '第二个按钮', icon: 'CopyPlus', onSelect: () => {} }
]) }]
```

⚠ 实现必须**同步返回**且**顺序稳定**（见 §3.6 的约束表）。

### 4.3.1 接一个**同进程**渲染侧插槽（产出面与实现都在渲染层）

适合"产出物是 DOM / 需要事件闭包"的槽（见 §3.8）。宿主侧四步：

1. 加官方插槽声明（`official-extension-points.js`）。
2. 在**宿主所在的渲染入口**里声明 + 激活：
   ```js
   import {
     defineRendererSlots,
     activateRendererSlots,
     callRendererSlot,
   } from '../shared/plugin-slots.js';

   defineRendererSlots(['your.slot.id']); // 必须在激活之前
   // …
   activateRendererSlots(); // 文件末尾；插件启停后重跑一次
   pluginsClient.onChanged(() => {
     activateRendererSlots();
   });
   ```
3. 渲染时直接调用：
   ```js
   const node = callRendererSlot('your.slot.id', {/* payload */}, null); // SINGLE，返回 HTMLElement | null
   // MULTI：callRendererSlotMulti(id, payload)   REDUCE：reduceRendererSlot(id, payload)
   container.replaceChildren(...(node ? [node] : [defaultNode]));
   ```
4. **交互机制（点击 / 悬停 / 键盘）由宿主统一接管**，插件只决定"长什么样"。

插件的实现写在 `.renderer.js` 里（**不是** `.cjs`）：

```js
export const rendererPlugin = {
  slots: {
    'your.slot.id': (payload, ctx) => {
      const el = document.createElement('div');
      el.textContent = payload.title;
      return el;
    },
  },
};
```

### 4.4 给扩展点挂实现（插件侧）

在插件模块（`.cjs`）里加一个可选 hook：

```js
module.exports = {
  install() {},
  async extensionPoints(ctx) {
    return {
      // 我提供的插槽（纯声明；有 impl 的插槽一般是宿主提供，不在这里声明）
      provides: [

        // 菜单类插槽：返回描述符**数组**（推荐），onSelect 在主进程内被调用
        {
```

菜单类插槽的实现细节（描述符字段、为什么会展平一层、坏实现怎么处理）见 §3.5。

禁用插件时 `disable()` 会自动 `slots.removeImplementations(pluginId)`，插槽立刻回落 ——
不需要插件自己清理。

### 4.5 加一个声明式贡献（新 kind）

`ContributionRegistry` 支持任意 kind。加一个新 kind 只需一步：

```js
contributions.define('context-menu-items', { mode: 'multi' });
```

然后插件在 manifest 里写 `contributes: { "context-menu-items": [...] }` 即可 ——
**注册中心不认识业务 kind**，具体字段由消费方解释。
`mode: 'single'` 表示该 kind 只保留最后一个实现（如"唯一的渲染器"）。

**现有的 kind 与消费方**：

| kind            | 消费方                                     | 说明                                                                                           |
| --------------- | ------------------------------------------ | ---------------------------------------------------------------------------------------------- |
| `panels`        | `panel-catalog.js`                         | 侧栏面板（id / title / icon / order / segment / bangs）；可带 `ui`（`.html` / `.xaml` 入口，见 §4.1.1） |
| `pages`         | `main/plugin-surfaces.js#syncPages`        | 内部页（`id / title / dir / entry`）→ 注册成 `hira://p-<plugin>-<page>/`，每页独立 origin      |
| `bangs`         | `main/plugin-surfaces.js#listBangs`        | 地址栏搜索指令（`id / trigger / title / url`，url 里的 `{query}` 会被替换）                     |
| `menus`         | `main/plugin-surfaces.js#menuItems`        | 菜单项（`id / label / where / when / action`），主菜单与各类右键菜单共用一套描述符              |
| `userscripts`   | `main/plugin-surfaces.js#resolveUserScriptsForUrl` | 用户脚本（`id / name / file / order`）：`.user.js` 按 `@match` 在各网页执行（§4.7 ④）  |
| `rendererSlots` | `renderer/shared/plugin-slots.js`          | 声明"这个插件的渲染模块要在哪些窗口被 import"（见 §3.6 / §3.8）                                 |
| `importFormats` | `ipc/bookmarks.js#bookmark:import-formats` | 自定义书签导入格式（`{ id, label }`）。**声明侧**在这里，实现在扩展点 `bookmark.import-format` |

> ⚠ 一个功能若要"UI 先能看到、再能执行"，**声明侧**（`contributes.*`）与
> **执行侧**（扩展点实现）要成对给出。只给一半的表现是"下拉里出现了这个格式，
> 选了却报未知格式"（或反过来，"能执行但用户不知道有这个格式"）。

### 4.6 面板能拿到什么（端口 ctx）

面板包**不得** import `apps/app-main/src/renderer/shared/*-client.js`
（那是 APPS 层，会构成 UI → APPS 反向依赖，违反 CONTRACT-11）。
宿主注入的 `ctx` 就是唯一能力边界：

```
ctx.doc                  Document
ctx.bridge               IPC 底座（provider.invoke / on.subscribe）
ctx.layout               layoutClient
ctx.clients              { tabs, panels, bookmarks, extensions, space, profiles, settings, plugins }
ctx.menu                 原生右键菜单
ctx.events               事件名表（IPC_EVENTS）
ctx.on(route, handler)   订阅
ctx.confirm(opts)        统一外观确认框
ctx.previewOverlay       面板外侧 hover 预览浮层
ctx.createTabRowMenu()   两个标签面板共享的右键菜单工厂
ctx.icons                应用层图标（space / ui）
```

**以后要放开新能力，就往 `renderer/panels/main.js` 的 `ctx` 里加一项** ——
一处定义，所有面板同时获得。

### 4.7 四类声明式扩展面（pages / bangs / menus / userscripts）

这四类是**给外部插件作者用的开放面**，共同点：**纯数据、不需要 `render`、不过 IPC**。
第三方运行时安装的插件（`userData/plugins/<id>/`）写进 manifest 就生效，
消费方统一在 `main/plugin-surfaces.js`，生命周期由 `refreshPluginSurfaces()` 一处收口。

四个 kind 全部 `mode: 'multi', namespaced: true` —— 社区插件各写 `id: 'github'`
不会互相覆盖，桶内键是 `${pluginId}\u0000${id}`，对外仍返回原始 `id`。

#### ① 内部页 `contributes.pages`

```jsonc
{
  "contributes": {
    "pages": [
      { "id": "home", "title": "我的首页", "dir": "pages/home", "entry": "index.html", "order": 100 }
    ]
  }
}
```

- 落盘：`<插件根>/pages/home/index.html`（`dir` 缺省 = `pages/<id>`，`entry` 缺省 = `index.html`）。
- 地址：`hira://p-<插件id>-<页面id>/`，**每页一个独立 host/origin** —— 插件之间的
  `localStorage` / `cookie` 天然隔离，也不与内置页（`hira://settings/` 等）撞名。
- 资产：同目录下的相对引用（`./app.js`、`./style.css`）由插件目录解析，
  路径中的 `..` 一律拒绝（安全边界在 `normalizeRelPath` + 根目录 `startsWith` 校验）。
- 启停：停用插件 → `syncPages()` 注销该 host，`hira://` 立刻不可访问；
  重新启用再注册。**不需要也不允许插件自己调协议层。**
- 页面本身不会自动出现在任何界面，要给它入口就配一条 `menus`（见下）。

#### ② 搜索指令 `contributes.bangs`

```jsonc
{
  "contributes": {
    "bangs": [
      { "id": "gh", "trigger": "gh", "title": "GitHub 搜索", "url": "https://github.com/search?q={query}" }
    ]
  }
}
```

- 用户在地址栏输入 `!gh 关键词` 即命中；模板支持 `{query}` / `%s`，也兼容
  `?q=` 就地替换与裸域名追加（规则在 `packages/shared-types/src/search-url.mjs`，**唯一真源**）。
- `trigger` 大小写不敏感、忽略空白；`showSuggestions: false` 可关掉建议列表命中。
- 内部 `id` 会被加上 `plugin:<插件id>:` 前缀，渲染层据此**跳过使用次数统计**，
  不会污染用户自己的自定义引擎数据。
- 需要**动态计算**（远端索引 / 本地大表）时不要用声明式，改用插槽
  `search.bang-provider`（MULTI，返回 `{ trigger, title, url }` 或数组），
  它只在 `search:config` 这条异步通道里被等待。

#### ③ 菜单项 `contributes.menus`

主菜单、列表右键、网页右键**共用同一套描述符**，只靠 `where` 区分落点：

```jsonc
{
  "contributes": {
    "menus": [
      {
        "id": "open-home",
        "label": "打开我的首页",
        "where": ["app.tools", "webview.context", "tabbar.context"],
        "action": { "type": "page", "page": "home" },
        "order": 100
      },
      { "id": "sep", "type": "separator", "where": ["app.tools"], "order": 90 },
      {
        "id": "search-sel",
        "label": "搜索「%s」",
        "where": ["webview.context"],
        "when": { "selection": true },
        "action": { "type": "bang", "trigger": "gh" }
      }
    ]
  }
}
```

**`where` 词汇表**（缺省 `['app.root']`，接受数组 / 逗号 / 空格分隔）：

| 分组     | 取值                                                                                                                                                          |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 主菜单   | `app.file` `app.edit` `app.view` `app.tabs` `app.history` `app.bookmarks` `app.tools` `app.help`（追加到对应顶级菜单底部）；`app.root`（作为**新的顶级菜单**） |
| 右键菜单 | `webview.context` `tabbar.context` `bookmark.context` `history.context` `download.context` `note.context` `easel.context` `archive.context` `open-tab.context` `media.context` `session.context` |

**`action.type`**（六种，全部在主进程执行，异常统一收口）：

| type      | 字段                                            | 行为                                                       |
| --------- | ----------------------------------------------- | ---------------------------------------------------------- |
| `url`     | `url`                                           | 当前窗口打开该地址                                         |
| `page`    | `page`（本插件页面 id，或 `其他插件id:页面id`） | 解析成 `hira://p-…` 后打开；页面不存在则告警并放弃          |
| `panel`   | `panel`                                         | 打开侧栏面板；存在性由宿主管，不存在则无动作               |
| `command` | `command`                                       | 执行 `app-menu` 动作表里的命令（与原生菜单同一份）          |
| `bang`    | `trigger`（或直接给 `url` 模板）+ 可选 `query`  | 用 `buildSearchUrl` 生成搜索地址；`query` 缺省取选区文本    |
| `slot`    | `id` + 可选 `payload`                           | `emit` 官方插槽（EVENT 语义，不等返回值）                  |

其余字段：`label`（`%s` = 选区文本，过长自动截断）、`enabled`、`accelerator`（**只显示不注册**，
快捷键统一由 `keybindings` 拦截）、`type: 'checkbox' | 'radio' | 'separator'`、`checked`、
`submenu`（递归，子项同形状）、`order`（升序，同值按声明顺序稳定排列）。
`when` 支持 `selection / link / image / editable / mediaType`，只对右键菜单有意义。

> **动态菜单项**用插槽 `app-menu.item` / `context-menu.item`（MULTI，主进程执行，
> 可返回闭包 `onSelect`）。声明式优先 —— 数据能表达的就别写代码。

**脚手架三条命令**（`pnpm plugin:new`，见 §13.1）：

```bash
pnpm plugin:new my-plugin --page "home:我的首页"   # 生成 pages/home/index.html + 注册
pnpm plugin:new my-plugin --bang "my:我的搜索"     # 生成一条 !my 指令
pnpm plugin:new my-plugin --menu                   # 往「工具」+ 网页/标签右键各加一项
```

`--menu` 会按「page → bang → panel → 兜底 URL」自动挑选动作目标，生成后**直接能跑**。

#### ④ 用户脚本 `contributes.userscripts`

**Tampermonkey 风格的 `.user.js` 在本项目里就是插件的一种**（`type: "userscript-plugin"`）。
于是它没有自己的生命周期：启停 = 插件开关、卸载 = 插件卸载、失败原因 = 插件状态。

```jsonc
{
  "id": "userscript-hello-hira",
  "name": "Hello Hira",
  "type": "userscript-plugin",
  "trustLevel": "community",
  "contributes": {
    "userscripts": [
      { "id": "Hello Hira", "name": "Hello Hira", "file": "script.user.js", "order": 0 }
    ]
  }
}
```

- 使用者不必手写这份 manifest：插件中心「安装用户脚本」把 `.user.js` 读进来，
  解析 `==UserScript==` 头后自动生成 manifest 并落盘（`userscript-installer.js`），
  之后一切操作都在插件中心里完成。也可以调 IPC `plugins:install-userscript`
  直接传脚本文本（粘贴安装）或路径（不传则主进程弹选择框）。
- `file` 是**相对插件根**的脚本路径，必须真实存在（安装器的 `inspectDir` 会校验），
  且路径经过 `path.resolve` + 前缀比较 —— 写到插件目录之外一律拒绝。
- 元数据头按 Tampermonkey 语义解析（**唯一真源**：`packages/shared-types/src/userscript.mjs`）：
  `@match` / `@include` / `@exclude`（`exclude` 优先，`match` 与 `include` 任一命中），
  `@run-at`、`@grant`、`@name` / `@version` / `@description` / `@namespace`。
- **执行时机**：页面加载完成（`did-finish-load`）后与站点注入共用一次 `executeJavaScript`；
  每个脚本各自 IIFE + `try/catch`，一个脚本抛错不影响同页其它脚本。
- **GM API 垫片**：`GM_addStyle` / `GM_log` / `GM_getValue` / `GM_setValue` /
  `GM_deleteValue` / `GM_listValues` / `GM_setClipboard` / `GM_openInTab` / `GM_info` /
  `unsafeWindow`。存储落在 `localStorage`，键前缀 `hira:gm:<插件id>:<脚本id>:` ——
  按站点隔离、刷新不丢，且不需要额外引入 preload/IPC 桥。
  `GM_xmlhttpRequest` **不提供**（需要跨域代理，属于另一条通道）。
- **禁用即失效**：`contributes` 只在 `enable` 时登记，且 `getPluginRoot()` 只对已启用插件
  返回目录 —— 两层门控，不需要在注入点再判一次"这个脚本开没开"。
- 脚本文件按 `mtime + size + 声明` 缓存，改文件后下一次导航即生效，不必重启。

## 5. 面板生命周期与释放

面板是**惰性**创建、**可销毁**的。三条规则：

1. **绝不预热**：启动期不创建任何面板视图（`side-panel-skeleton` 明确不 warmup）。
   首次真正显示时才 `LayoutCoordinator.showPanel()` → `WebContentsManager.loadPanel()`。
2. **只在必要时销毁**：`hidePanel()` 只 `setVisible(false)`（开关面板零重建、零抖动）；
   `WebContentsManager.destroyPanel()` 只在**插件被禁用/卸载**时调用，真正释放渲染进程。
3. **目录变化必须对账**：插件启停 → `main.js#reconcilePanelsAcrossWindows()`
   （用"目录指纹"短路，无关插件启停不会打扰布局层）
   → 各窗口 `LayoutCoordinator.reconcilePanels(validIds)`
   → 关掉已失效的活动面板 + 销毁不在目录里的面板视图。

> 漏掉第 3 条会出现「按钮没了、面板还开着、渲染进程还占着内存」的错位 ——
> 这是"开关看起来没生效"的根因。

## 8. 插件状态的持久化与 profile 隔离（决策记录 + 进度）

> 这一节是**路线记录**，不是待办清单。写下来的目的是：这块的决策一旦漂移会很难查
> （"重启后我的禁用丢了""为什么 A 用户关的插件 B 用户也没有了"），所以把结论与理由固定住。

### 8.1 六态语义（**已落地**）

插件状态不是布尔值，是**六态**。混淆任何两个都会产生"用户从没关过它，怎么关着"这类故障：

| 状态              | 含义                                                   | 是否落盘                              | 谁写入                                                                                                            | 怎么解除                                                             |
| ----------------- | ------------------------------------------------------ | ------------------------------------- | ----------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| `enabled`         | 正常启用                                               | —                                     | `enable()` 成功                                                                                                   | —                                                                    |
| `userDisabled`    | **用户主动关的**                                       | ✅ 落盘（`plugins.disabled`）         | 插件中心的开关（唯一入口）                                                                                        | 只能由用户再点一次                                                   |
| `failed`          | **启用时**抛错（附 `error` 原文）                      | ❌ **不落盘**                         | `enableAll` 的异常路径                                                                                            | 下次启动自动重试（自愈，用户无需动手）                               |
| `autoDisabled`    | **运行期连环出错**被系统停用（附 `error` 作原因）      | ✅ 落盘（`plugins.autoDisabled`）     | 两个入口：`lifecycle.onCrash`（`reportPluginError` 触顶）与 `lifecycle.healthCheck`（主动巡检连续未通过，见 §12） | **用户点开关即可**（一键恢复）                                       |
| `blocked`         | **硬前置未启用** —— 它一行代码都没跑（根因在上游）     | ❌ 不落盘                             | `enable()` 的前置闸门                                                                                             | 用户点开关（会按拓扑序把前置一起拉起）；前置若被自动停用则需先处理它 |
| `awaitingConsent` | **第三方插件在等用户授权**（它申请了权限，还没被同意） | ❌ 不落盘（**授权结果**落盘，见 §11） | `enable()` 的授权闸门                                                                                             | 用户在插件中心点「同意并启用」，或「暂不」（按用户停用处理）         |

**六个状态的根因位置各不相同，所以界面必须给六种不同的下一步** —— 这是本节的核心：

| 状态              | 根因                     | 颜色 | 下一步                                                        |
| ----------------- | ------------------------ | ---- | ------------------------------------------------------------- |
| `failed`          | 它自己抛错了             | 红   | 「下次启动会自动重试」（**用户什么都不用做**）                |
| `autoDisabled`    | 它跑过、崩了、被系统停用 | 琥珀 | 「点右侧开关可重新启用」（**需要用户动手**）                  |
| `blocked`         | 它没跑过，卡在上游       | 蓝   | 「点开关会一并启用前置」（修法明确）                          |
| `awaitingConsent` | 它没跑过，**卡在用户**   | 紫   | 列出它申请的权限 +「同意并启用 / 暂不」（**只有用户能决定**） |

区分三条边界（每一条都对应一类真实故障）：

1. **`failed` vs `userDisabled`：落不落盘。** `failed` 一旦落盘，一次偶发失败（端口占用、
   文件锁、网络）就被记成"已禁用"，之后每次启动都坏，而用户从没关过它。不落盘 = 下次
   启动自动重试 = **失败自愈**。UI 上两者也必须可分辨（用红色警示 + 原始错误 +
   "下次启动会自动重试"），不能合并成一句"出错了"。
2. **`autoDisabled` vs `userDisabled`：谁写的。** 两个都落盘，但写入方不同 ——
   前者是**系统判定**，后者是**用户意图**。所以 `enable()` 成功后**清 `autoDisabled`、
   不清 `userDisabled`**：前者是"系统停的，用户能拿回来"，后者"只能用户自己解"。
   若 `autoDisabled` 被误写成 `userDisabled`，用户将**永远无法**从崩溃停用里出来。
3. **`autoDisabled` vs `failed`：启不起来 vs 启起来了但一直崩。** 两条不同的故障时段，
   因此也是两条不同的 UI 文案 —— 前者"点右侧开关可重新启用"（需要用户动手），
   后者"下次启动会自动重试"（用户什么都不用做）。UI 用琥珀色（警示）vs 红色（错误）分开。

**顺带修掉的一个旧 bug**：`enableAll` 原来是裸 `await this.enable(m.id)` 循环 ——
任何一个插件抛错，循环当场结束，**排在它后面的插件一个都不会启用**。而顺序是按依赖
拓扑排的，于是"坏一个、后面全空"，错误只指向那一个插件，极难定位。现在改为逐个
try/catch + 记 `failed`。

#### 8.1.1 `lifecycle.onCrash` 的判定细节（**已落地**）

**输入从哪来 —— 两个汇聚点，一条出口。** 插件自己的代码有两个执行面，两处都报：

| 执行面                    | 谁捕获                               | 上报点                                                         |
| ------------------------- | ------------------------------------ | -------------------------------------------------------------- |
| 扩展点插槽实现            | `extension-points.js` 的调度器 catch | `main.js` → `reportPluginError`                                |
| provider（`around` 包装） | `provider-registry.js` 的 `onError`  | `main.js` → `reportPluginError`（按 capability 反查 pluginId） |

`main.js` 的 `reportPluginError` 是**唯一出口**，它做两件事：过滤域服务错误 → 迟绑定到
`pluginRegistry.reportPluginError`（注册中心是**后台启动**的，建 sink 时它还不存在，
与 panelCatalog / contributions 同一套路：先建壳、后灌实例）。

**窗口内计数，不是累计计数。** `onCrash: restart:3 then disable` 的意图是**防止连环坏**
（一个 Mod 在循环里疯狂抛错），不是"一天里偶发三次就停用"。累计计数会让长期运行的会话被
偶发错误误杀。因此 `_errorStamps` 存时间戳数组，每次先按窗口（默认 60s）过滤再计数，
触顶阈值默认 3。窗口过期后计数自然归零。

**域服务的错不算在插件头上。** 这是本机制最容易做错的一点：`service-plugin.js` 是
"插件代码包着域服务调用"的唯一处，DB 锁 / 网络抖动都从这个调用里抛出来。不打标记的话，
**一次瞬时故障连续三次就会把用户的书签引擎永久停掉**。做法是 `around` 里给错误打
`hiraDomainServiceError` 标记，`reportPluginError` 见到就跳过计数。

> ⚠ 同步与异步**两条路都要标记**：域服务绝大多数是 async，只 `try/catch` 同步路径等于
> 几乎没起作用（Promise 的拒绝不走 `catch`）。实现里同步 `catch` 与 `.catch()` 各调一次
> `mark()`，这条已由冒烟覆盖（两者都验证过）。

**触顶后的三段分工：判定 / 卸载在 infra，落盘 + 广播在 APPS。**

| 段          | 谁做                                      | 做了什么                                                   | 为什么是它                                              |
| ----------- | ----------------------------------------- | ---------------------------------------------------------- | ------------------------------------------------------- |
| 判定        | `autoDisable`（infra）                    | 记 `_autoDisabled`、清错误邮票、记原因原文、打日志         | 判定就是注册中心的状态机                                |
| **卸载**    | `autoDisable` 排队调 `disable()`（infra） | 摘 provider / 插槽实现 / 声明式贡献 / 样式                 | 四张表与 `_context` 都在 infra 手里，本就不需要外部帮忙 |
| 落盘 + 广播 | 注入的 `onAutoDisable`（APPS）            | `setAutoDisabled(id, true)` + 布局对账 + `plugins:changed` | storage 与 IPC 出口在 APPS                              |

> ⚠ **`autoDisable` 刻意不把 `_states.enabled` 置 false，这个细节是整块的正确性关键。**
> 若先置 false，紧接着排队的 `disable()` 会在 `if (!st.enabled) return` 处**短路** ——
> 插件带着 provider 与插槽实现**继续跑**，而界面显示"已停用"。
> 那正是 §9 的"假生效"病，只是换了个入口。**状态必须由真正执行卸载的那一步来落。**
> （这条已由冒烟钉死：自动停用后 `getByCapability(...)` 必须为 0、贡献列表必须为空。）

**卸载为什么排队到微任务**：`reportPluginError` 是在插件自己的调用栈里被调用的，
同步 `disable()` 会把插件代码从它自己的栈下方抽走。
**为什么先回调、后卸载**：落盘与广播要尽快到达 UI；而 IPC 本身是异步的，
微任务里的 `disable()` 必定先跑完 —— UI 拿到清单时 `enabled` 已是 `false`。

**为什么只停用、不自动重启用。** 自动重新启用会让"崩 → 启 → 崩"变成静默的死循环；
落盘 + 用户可见的琥珀色提示，把决定权交回用户，是唯一不会掩盖故障的做法。

### 8.2 存储落点与作用域（**已落地**）

- **键**：settings KV 的 `plugins.disabled`（字符串数组，只存 id）。
  该键**不在** `settingsRegistry` 的 schema 里 —— 设置页只渲染 schema 声明的项，
  所以它不会作为一个"设置项"冒到用户面前；插件中心才是它的界面。
- **为什么复用 settings 而不是新开文件**：项目里已有先例（外部协议授权记录同样复用
  settingsService 的 KV + 独立前缀）。复用直接拿到防抖写盘、原子写、多进程去回声。

**作用域钉死在 `default`（= 全局）**，这一点必须显式，因为 main 侧的 settingsService 是
**按 profile 覆盖**的（`createProfileSettingsOverlay` → `userData/profiles/<id>/settings.json`）。
不钉的话会出现一种极隐蔽的**半隔离**：

```
启动时 enableAll 在无 IPC 上下文里跑      → 读 default 的覆盖
从非 default 窗口的插件中心点「禁用」      → 写那个 profile 的覆盖
                                    ↑ 读的和写的不是同一份，只在多 profile 下暴露
```

所以 `plugin-state-store.js` 把读写都用 `runAsProfile('default', …)` 包住，
**插件开关是全局状态**。这是**最终形态**而非权宜之计 —— 理由见 §8.3（已决定不做 profile 隔离）。

### 8.3 profile 隔离（**已决定：不做**）

**结论：插件开关是全局的，不做 profile 隔离。** 这不是"麻烦所以跳过"，
而是**隔离的单位选错了**——按插件一刀切必然误伤不该切的部分。

隔离的最小单位其实是**能力面**，而插件是"能力的打包单位"，同一个插件里常常既有该隔离的
部分、又有根本不该隔离的部分。按插件切就会把它们一起切掉：

```
keybindings-service   展示/绑定可以按 profile 不同
                      但注册到操作系统的全局快捷键是**进程一份** → 按插件切会连它一起切
side-panel-skeleton   面板内容该按 profile 分
                      但它是 10 个面板插件的前置 → 关掉 = 那个 profile 的面板全废
settings-service      语义是"整个设置系统在不在"
profile-service       自指：它就是**定义 profile 的那个东西**，不能由 profile 决定它开不开
```

**三类结构上无法隔离的判定标准**（留着这个标准就够了 —— 将来若真有 Mod 需要按 user 隔离，
照它判断，而不是照"插件"这个粒度判断）：

| 类别           | 特征                                                     | 现有例子                                                  |
| -------------- | -------------------------------------------------------- | --------------------------------------------------------- |
| 进程级单例资源 | 关掉 = 对所有人关掉，不存在"对某个 profile 关掉"这个状态 | 全局快捷键、托盘、`external-games-service`                |
| 设施 / 前置    | 关掉会连锁废掉一片                                       | `settings-service`、`side-panel-skeleton`、`tabs-service` |
| 自指           | 定义 profile 的东西不能由 profile 来决定                 | `profile-service` / `space-service`                       |

**由此产生的一个直接收益**：既然不做隔离，§8.2 的「作用域钉在 `default`」就不是权宜之计，
而是**最终形态**。`plugin-state-store.js` 因此不需要任何后续改动，
manifest v2 里也**不需要** `scope` 字段。

注意 `lifecycle.onCrash`（崩溃自动禁用）与 8.1 的 `failed` 是**两件事**：
`failed` 是"启用失败、下次重试"；`onCrash` 是"运行期崩溃、连续 N 次后禁用"。
后者落盘写成 `userDisabled` 之外的第 4 态 `autoDisabled` 并允许用户一键恢复，
否则用户永远无法从"崩溃被自动禁用"里出来。

> **✅ 已落地（见 §8.1 的四态表 + §8.1.1 的判定细节）。** 该键为 `plugins.autoDisabled`，
> 与 `plugins.disabled` 分开存 —— 两套语义的生命周期不同（用户禁用只能由用户解除；
> 自动停用允许"用户点一下恢复"），分开存也让老用户的 `plugins.disabled` **不需要迁移**。

## 9. ~~已知语义缺口~~：功能插件（xx引擎）的开关**已真生效**

> **状态：已修复（§9.3 的 `blockedCapabilities` 已落地 = §10.5 步骤 ①）。**
> 本节保留完整诊断过程，因为这是本项目最隐蔽的一类病：
> 开关**看起来工作**（插件中心显示已禁用、状态也持久化了），但功能一点没变。
> 以后再有"某开关没效果"的报告，照本节的三环节逐条对。

### 9.1 链路的三个环节（已核实）

```
① 域 IPC 一律写成 invoke(capability, () => service.xxx())
   —— 第二个参数是**域服务直连**（见 ipc/bookmarks.js 等全部 19 个 registrar）

② provider-bridge.js 的语义：
       const hasProvider = providerRegistry.getByCapability(capability).length > 0
       if (!hasProvider) return fallback()          // ← 直连域服务

③ 禁用引擎 → 它的 provider 被反注册（PluginRegistryV2.disable 按 pluginId 反注册）
   → hasProvider === false → 走 fallback → 功能照旧
```

`createServicePlugin` 的 `disable() {}` 是空的，provider 的摘除只发生在注册中心那一侧 ——
摘完之后正好落进 fallback 分支，于是**开关的净效果为零**。

### 9.2 开关生效面（① 落地前后对照）

| 类型                       | ① 之前 | ① 之后 | 原因                                                                                       |
| -------------------------- | ------ | ------ | ------------------------------------------------------------------------------------------ |
| 面板插件（11 个）          | ✅     | ✅     | 面板目录真增删，rail/navbar 按钮 + 面板视图一并销毁（§5）                                  |
| `bookmark-backup-provider` | ✅     | ✅     | 有**真实副作用**：`disable()` flush + stop 定时器，自动备份真停                            |
| 其余 14 个引擎             | ❌     | ✅     | 卸载由注册中心做（摘 provider / 插槽实现 / 贡献），**功能面由 `blockedCapabilities` 关闭** |

> **注意"`disable()` 为空"不等于"没卸载"。** 对 `createServicePlugin` 造出来的引擎，
> `disable() {}` 是**正确**的：要拆的东西（provider、插槽实现、声明式贡献、注入的样式）
> 全在注册中心手里，由 `PluginRegistryV2.disable()` 统一摘。
> 「引擎适配」在 ④ 里真正要审的是**另一件事**：有没有该插件自己持有、注册中心看不见的
> 资源 —— 定时器、原生快捷键注册、进程级单例、外置资源目录。
> 已知需要真 `disable()` 的：`bookmark-backup-provider`（定时器，已做）、
> `keybindings-service`（全局快捷键）、`external-games-service`（进程级资源，见 §8.3）。

### 9.3 这是设计张力，不是接线漏了

fallback 本身是**必需的**（"无插件也能跑"、插件出错要能降级）。但它同时让"禁用"失去语义
—— **因为兜底永远在**。要让它生效，必须把两件事分开：

```
插件不存在 / 加载失败   → 走 fallback（降级，功能保留）   ← 现状，正确
插件被用户显式禁用      → 不走 fallback（功能真的消失）   ← 缺失的语义
```

**做法（✅ 已落地，即 §10.5 的步骤 ①）**：注册中心维护一张「**被显式禁用的插件所贡献的能力**」
的表，invoker 命中该表即抛"功能不可用"而非 fallback。

三个关键设计点（都踩过坑才定下来的）：

1. **计算式，不是增删式。** 表由 `_manifests` + 两个禁用集合**现算**（带惰性缓存）。
   增删式要维护一份与真实状态同步的镜像，每次禁用/启用/自动停用/失败都要记得改 ——
   漏一处就留下幽灵条目，表现是"启用了但功能还是不可用"，极难定位。
2. **能力清单取自 `manifest.capabilities`，不是模块的 `registerProviders()`。**
   启动时就被禁用的插件**根本没被 enable**，没有 provider 可枚举；而"它贡献了哪些能力"
   此刻就必须知道。manifest 是静态声明 —— 唯一可用且正确的来源。
3. **`autoDisabled` 与 `userDisabled` 同等对待**：系统因连环坏停用的插件同样不该继续提供服务。
4. **不可禁用的插件（`core` / `nonDisableable`）永不进任何禁用集合** —— 用户禁用与
   **系统自动停用**都必须被拒（`setUserDisabled` / `setAutoDisabled` / `autoDisable` 三处同一条守卫，
   外加 `reportPluginError` 不计数、`enableAll` 自愈历史残留）。

   ⚠ 这一条是**踩坑补的**：最初只挡住了用户禁用，`autoDisable` 没挡 ——
   于是 `tabs-service`（core）连错 3 次被连环坏判定停用，`tabs.navigate` 等能力落入
   `isCapabilityBlocked` 分支被**直接抛错**（不是 fallback），表现为
   `nav:go → 能力不可用：tabs.navigate（提供它的插件已被禁用）`，
   整个浏览器导航瘫痪，**且点插件中心的开关也救不回来**（那条 IPC 本身就在它提供的能力里）。
   后果不对等：普通插件坏掉只损失一个功能，核心插件坏掉损失整台车 —— 所以它对"自愈"的要求更高，
   而不是"再坏也留着"的偏袒。

**判据挂在 `ProviderRegistry` 上，靠注入的解析器回连注册中心。**
20 个 registrar 拿到的都是 `ProviderRegistry`（`createProviderInvoker(providerRegistry)`），
所以 `isCapabilityBlocked` 必须在那里可问；而账本在 `PluginRegistryV2`。
用 `setBlockedCapabilityResolver(fn)` 注入闭包即可 —— 既不用改 20 个调用点，
也不把"插件"这个概念漏进通用的 ProviderRegistry（它仍可独立使用/测试）。

**判定只在 `!hasProvider` 分支做**（`provider-bridge.js`），这一条是正确性关键：
若另一个仍启用的插件也提供同一 capability，功能照常可服务 ——
**"某个被禁用的插件也声明过它"不足以判定不可用。**

错误的可判定性：抛出的 Error 带 `hiraCapabilityBlocked = true`。
上层（IPC / 渲染层 notice）需要把它与"真的坏了"分开 —— 它是**用户自己选择造成的正常结果**，
不该弹成故障、也不该污染健康度判断。

**必须配套的前置（否则用户会觉得"点了开关浏览器就废了"）**：UI 目前没有"功能不可用"的表达。
真禁掉 bookmark 引擎后，书签栏 / 星标 / 书签面板会全部报错或空列表 ——
所以这一刀要**连 UI 的优雅降级一起做**（入口隐藏，而不是留着报错），即 §10.5 的步骤 ④。

**判定标准**：一个插件的开关"该不该真生效"，看它是否**独占**某个功能面 ——
独占（面板、自动备份）就该真生效；被兜底覆盖（引擎）则不做"假生效"，
要么不做、要么按上面那一条做彻底。

## 10. 前置关系的体现 / 管理 / UI 与引擎的联动禁用（**✅ 已落地**）

> **定位**：§9 解决的是"开关为什么不起作用"（实现层）；本节是它上面的**语义层** ——
> 一旦开关真的起作用了，立刻会冒出三个必须一起回答的问题：
> **谁依赖谁看得出来吗？禁用一个会连带什么？依赖没了 UI 怎么办？**
> 三块必须一起做：只做其中一块会比现在更糟（例如开关真生效了但没有 UI 让步，
> 用户体验就是"点一下浏览器废一半"）。

### 10.1 现状基线（已经有的，别重复造）

| 能力         | 现状                                                                                    |
| ------------ | --------------------------------------------------------------------------------------- |
| 硬依赖声明   | manifest `dependsOn`（PART7 §7.4 的五类关系里**只实现了这一种**）                       |
| 启动校验     | `validateDeps` 校验硬依赖存在性                                                         |
| 启用顺序     | `topoSort` 拓扑排序                                                                     |
| 禁用保护     | `ipc/plugins.js` 检测"已启用插件里有没有依赖它的" → **拒绝禁用**并回传依赖方名字        |
| 插件中心呈现 | ✅ **已升级（步骤 ②）**：双向关系专列 + 中文名 + 硬/软分列；"被依赖"里已启用者标红      |
| 软依赖       | 步骤 ② 之前**完全没有** —— 已补上 `optionalDependsOn`（含校验/环检测/呈现三处区别对待） |

### 10.2 一块：体现（把依赖关系画出来）（**✅ 已落地 = 步骤 ②**）

- **目标**：插件中心能看到**双向**关系 —— 我依赖谁、谁依赖我；禁用前先让人看见连带范围。
- **要点**：显示**中文名**而不是 id（现在那串 id 对用户等于没信息）；`owner`/`type`
  分组已经做了（§4.1），依赖关系应挂在同一处呈现。
- **顺带补齐 manifest**：`optionalDependsOn`（软依赖）现在完全没有 ——
  它是"存在就用、不存在也照装"的降级语义（PART7 §7.4），
  **软依赖与硬依赖在 UI 上必须分开呈现**（一个是"缺了会废"，一个是"缺了降级"）。

**落地内容与关键决策：**

| 面           | 做了什么                                                                                                                              |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------- |
| manifest     | `normalizeManifest` 新增 `optionalDependsOn`（字符串数组）                                                                            |
| 校验         | `validateDeps` **只对硬依赖抛错**；软依赖缺失静默跳过（"软"的定义）                                                                   |
| 环检测       | **软依赖不参与环检测** —— A 软依赖 B、B 软依赖 A 是合法的"谁先都行"表达                                                               |
| 拓扑         | 排序仍只看硬依赖（软依赖是**声明**，不是约束；见下方"为什么"）                                                                        |
| `describe()` | 新增正向 `optionalDependsOn` + **反向** `requiredBy` / `optionalRequiredBy`                                                           |
| 契约         | `pluginInfoSchema` 同步四个新字段（zod 会**静默剥掉**未声明字段 → UI 永远收不到）                                                     |
| UI           | 关系专列（不再是 meta 行里那串裸 id）：`依赖` / `可选` / `被依赖` / `可选被依赖`，中文名，硬/软用配色区分，"被依赖"里**已启用**的标红 |

**反向关系在注册中心算，不在 UI 算**（`describe()` 里一次建索引）。理由：反向关系只是
`dependsOn` 的转置；让展示层拿 25 份 manifest 自己建图，等于把关系语义复制一份到 UI ——
将来加软依赖/冲突关系时必然漏改一处。

**`requiredBy` 列出全部依赖方（含已禁用的），不只列启用的。** 两个理由：
① §10.2 要的是"禁用前先让人看见连带范围"；② 已禁用的依赖方同样会被波及（用户重新启用它时
前置必须还在）。"启用与否"由 UI 用 `enabled` 字段自行呈现 —— 于是"标红已启用的那几个"
这个动作发生在**展示层**，而它正是"为什么这个开关关不掉"的答案（IPC 的依赖保护拒绝）。

**为什么软依赖不进拓扑排序**：把缺失的软依赖塞进 `topoSort` 的 `visit()` 会抛
`Missing plugin` —— 那等于把软依赖偷偷升级成硬约束，作者写下的降级意图当场失效。
若只把"存在的软依赖"塞进去，又会与"软依赖成环合法"自相矛盾（`visit()` 会因为
软边判出环）。所以软依赖的定位明确为**纯声明**：它给 UI 看、给插件自己在运行期判断
（"那个引擎在不在"），不参与加载顺序。

> ⚠ `ipc/plugins.js` 的依赖保护（禁用前检查已启用依赖方）**只看硬依赖**。
> 拿软依赖挡禁用与"软依赖不进拓扑"是同一个错误的两面。

### 10.3 二块：管理（连锁语义）（**✅ 已落地 = 步骤 ③**）

**原来的"拒绝禁用"是防呆，不是管理。** 三个方案里**选定 (b)**：

| 方案                   | 行为                                         | 代价                               | 结论        |
| ---------------------- | -------------------------------------------- | ---------------------------------- | ----------- |
| (a) 级联禁用           | 禁用 A → 自动按**逆拓扑序**禁用所有依赖 A 的 | 用户"关一个它关了一片"，且没被告知 | ✗           |
| **(b) 确认后一起禁用** | UI 明确列出"将同时禁用 X、Y"，用户确认才执行 | 需要把连带集合算出来并回传 UI      | **✅ 采用** |
| (c) 维持拒绝           | 现状                                         | 用户被挡住却不知道为什么"关不掉"   | ✗           |

**(b) 是两段式协议，不是"弹个框"那么简单。** 第一段：不带 `cascade` 的调用**不执行任何禁用**，
只回 `{ requiresCascade: true, dependents: [{id, name}] }`；第二段：UI 弹确认，
用户同意后带 `cascade: true` 重发，主进程按**逆拓扑序**（下游在前）逐个禁用。
为什么不做"静默级联"：用户按下的是一次点击，不该顺手关掉他看不见的一串东西 ——
那些下游的面板会一起消失，而"我的面板怎么没了"极难倒推回"因为刚才关了一个引擎"。

**四条必须处理的，逐条落地如下**（编号与原文一致）：

**1. 启用必须按拓扑序恢复。** 唯一路径 = `PluginRegistryV2.enableWithPrerequisites()`：
先按 `prerequisiteIds()`（递归 + 拓扑序）逐个拉起前置，再启用目标。
顺序反了的话前置还没起来依赖方就失败，会被误记成 `failed`，然后触发失败自愈重试，
变成每次启动都报一次假失败。

> **里面有一个必须做对的区分**：同样"关着"的前置，含义相反 ——
>
> | 前置状态                     | 处理                                         | 为什么                                                                     |
> | ---------------------------- | -------------------------------------------- | -------------------------------------------------------------------------- |
> | `userDisabled`（用户关的）   | **一起恢复**，并记入 `restored` 回传 UI 告知 | 用户要开下游，而下游**必须**有它 —— 恢复是这次意图的必然含义，不是自作主张 |
> | `autoDisabled`（连环坏停用） | **绝不复活**                                 | 那是系统为压住崩溃循环做的保护；顺手复活 = 把刚扑灭的火重新点着            |
>
> 差别在"**谁的决定**"：前者是用户的决定，被用户的另一个决定覆盖，合理；
> 后者是系统的安全判定，只能由用户专门针对那个插件去解除。
> 恢复必须**回传并告知**（"已一并启用前置：X"）—— 静默恢复会让人下次看到
> "我明明关过的东西怎么开着"，那是信任问题，不是信息问题。

**2. 下游需要第 5 态 `blocked`（✅ 已实现）。** 前置被禁用导致下游起不来时，
它既不是 `enabled` 也不是 `failed`。→ 与 §8.1 的四态合并成**五态**：
`enabled` / `userDisabled` / `failed` / `autoDisabled` / `blocked`。

三个"没在跑"的根因位置完全不同，UI 用**三种颜色 + 三句不同的下一步**区分：

| 状态           | 根因                             | 颜色 | 文案给的下一步                                       |
| -------------- | -------------------------------- | ---- | ---------------------------------------------------- |
| `failed`       | 它自己抛错了                     | 红   | 「下次启动会自动重试」（**用户什么都不用做**）       |
| `autoDisabled` | 它跑过、崩了、被系统停用         | 琥珀 | 「点右侧开关可重新启用」（**需要用户动手**）         |
| `blocked`      | 它**一行代码都没跑**，根因在上游 | 蓝   | 「点开关会一并启用前置」（**问题可修，且修法明确**） |

实现要点：`blocked` 是 **`enable()` 里的前置闸门**（硬依赖里有任一未启用 → `markBlocked` 后
**安静返回**，不 `throw`）。不 `throw` 是关键 —— 抛错会被归到 `failed`（"这个插件自己坏了"），
而事实是它没跑过。闸门位置在 `preEnable` **之前**：都不打算启用它，就不该执行它任何一段代码。
与 `failed` 一样**不落盘**（下次启动前置若已就绪就该正常启用）。

**3. CORE 静态判定 + 被依赖动态判定，两者都要拦（✅ 已实现）。**
两道闸门的**提示语必须不同** —— 一个是"这东西不能关"（静态、永远为真），
一个是"现在关会带走别人"（动态、可以绕过）。合并成一句会让用户无法判断该怎么办。

两个容易做错的边界：

- **CORE 是静态的，但 CORE 插件常常是"被依赖方"**（面板依赖骨架）。只查它自己拦不住 ——
  从依赖方向一样能把它关掉。所以必须多一道：**连带集合里含 CORE 也硬拒**。
- **这道检查必须排在 `requiresCascade` 之前。** 否则带 `cascade: true` 的调用会绕过它
  （用户"确认"了一个本来就不允许的操作）。**权限判定必须早于确认流程**，
  否则那个确认框就变成了绕过闸门的入口。

落地时给两个结构性不可隔离的引擎打上 `trustLevel: "core"`（判定依据见 §8.3 的三类标准）：
`tabs-service`（拥有全部 `tabs.*`：列表/新建/切换/关闭/排序/导航/固定/静音/休眠 ——
**没有它浏览器就没有标签**）、`settings-service`（设置页与全部 IPC 上的 KV 读写）。
两者都**没有任何 manifest 声明 `dependsOn` 它们**，所以动态依赖保护挡不住 —— 只能靠 CORE 静态判定。

**4. 取消禁用后的恢复顺序，与第 1 条同源。** 走的就是 `enableWithPrerequisites` 这一条路径，
**没有第二份实现**（IPC 里不另写循环）。两条路径各写一份的话迟早分叉，
而分叉的表现就是"从 A 入口开正常、从 B 入口开就报假失败"。

### 10.4 三块：UI 与引擎的联动禁用（**✅ 已落地 = 步骤 ④**）

- **原来的现状**：无。禁掉 bookmark 引擎后，书签栏 / 星标 / 书签面板照旧渲染 → 报错或空列表。
- **目标**：引擎被禁用 → 依赖它的 UI 入口**自动隐藏**（而不是留着报错）。
- **机制要点**（原计划三条，逐条落实）：
  - 一张「**功能面 → 所需引擎插件**」的映射；
  - **收口成一个"功能可用性"查询端口 + 一处订阅**；
  - UI 侧只做"渲染 / 不渲染"，不做"降级到某个 fallback"—— 那是 §9 的 `blockedCapabilities` 的职责。

#### 落地的四件东西

| #   | 文件                                                       | 是什么                                                          |
| --- | ---------------------------------------------------------- | --------------------------------------------------------------- |
| 1   | `apps/app-main/src/main/feature-map.js`                    | **唯一**的「功能面 → 引擎插件」表（15 个功能面）+ 判定函数      |
| 2   | `infra-ipc/contracts/plugins.js` + `ipc-channels.mjs`      | 契约 `featureAvailabilitySchema` + 通道 `features:availability` |
| 3   | `apps/app-main/src/renderer/shared/features-client.js`     | 渲染侧**单例 store**：一份状态 + 一条桥订阅 + 一次去重请求      |
| 4   | `app-shell` / 两个 controller / `icons.js` / 面板 manifest | 各入口按它收敛                                                  |

#### 判定规则：fail-open 的**精确**形式（这一条决定成败）

一个功能面**不可用** ⟺ 它的引擎插件**存在**且处于「**被显式关掉**」的三种状态之一：
`userDisabled` / `autoDisabled` / `blocked`。

**刻意不包含**的三种"没在跑"，它们都不该让 UI 消失：

| 情形                                       | 为什么算可用                                                         |
| ------------------------------------------ | -------------------------------------------------------------------- |
| **插件不存在**（目录里没有它）             | 那时功能由域服务直连兜底，**功能其实还在** —— 与 §9.3 的判据完全同源 |
| **`failed`**（启用时抛错）                 | 下次启动自愈；把它算作不可用会让用户凭空少一个入口                   |
| **尚未启用**（`enableAll` 正在按拓扑序跑） | 那只是启动头几百毫秒；算作不可用会让整个界面先隐藏再冒出（闪一下）   |

这条规则带来一个额外好处：**不需要"插件系统就绪"标志位**。判定只看"是否被显式关掉"，
而禁用状态在 `enableAll` **之前**就已恢复完毕 → 从第一帧起答案就是稳定的。

> 反面教材（差点踩）：最初想用 `enabled !== true` 判定，结果启动期整屏 UI 会消失再回来，
> 且 `failed` 的插件会让入口凭空少一个。**隐藏 UI 是破坏性动作，必须建立在确定的信息上，
> 不确定时选可逆的那一侧。**

#### 入口分两类，走**两条不同**的机制（不要混）

| 类                    | 例子                                                     | 怎么消失                                                                                   | 为什么走这条                                                     |
| --------------------- | -------------------------------------------------------- | ------------------------------------------------------------------------------------------ | ---------------------------------------------------------------- |
| **插件提供的入口**    | 11 个面板（收藏/历史/下载/扩展/权限/固定/空间…）         | 在 manifest 里把引擎写进 `dependsOn` → 引擎被禁 → 下游 `blocked` → 贡献被摘 → 目录里没有它 | 依赖图**本身就是**联动机制，零新增 UI 代码（步骤 ②③ 的直接收益） |
| **硬编码核心 chrome** | 星标 / 权限 Bell / 拦截盾牌 / 书签栏 / 下载条 / ⋮ 菜单项 | 走 `features:availability` 端口                                                            | 它们不是插件，没有 manifest 可以声明依赖                         |

**核心 chrome 的收敛点**（每个入口一行，全在这一份清单里）：

| 入口                           | 收敛方式                                                                                        |
| ------------------------------ | ----------------------------------------------------------------------------------------------- |
| 星标 / 权限 Bell / 拦截盾牌    | `CHROME_BUTTONS` 各项加 `feature` 字段 + `filterCatalogByAvailability()` 过滤**目录**           |
| ⋮ 菜单的 11 项                 | `MENU_FEATURE` 映射 + `withFeatureGate()` 过滤                                                  |
| 书签栏（含星标状态）           | `bookmark-controller#syncEngineAvailability()`（引擎没了清空并收起）                            |
| 下载条                         | `download-controller#syncEngineAvailability()`（**停表** + 清空）                               |
| 书签页的 Backup / Backups 按钮 | 页面内查一次 `features:availability`（它属 `bookmark-backup-provider`，与书签引擎**各判各的**） |

**为什么必须过滤目录、而不是只把 DOM 藏起来**：目录同时驱动**按钮编辑浮层里的格子**。
只藏 DOM 的话用户能把"引擎已不在"的按钮重新拖出来，然后点它报错 ——
这就是 §10.4 原本预告的"面板陷阱"，在按钮上同理。过滤目录 = 按钮与它的格子同时消失，口径一致。

#### 第三类入口：**主进程触发点**（藏 UI 不够，必须收住源头）

有一类"入口"根本不在界面上 —— 是**主进程主动弹/主动推**的东西。对它们，隐藏 UI 是无效的
（UI 本来就由主进程决定弹不弹），必须在**触发点**收住：

| 触发点                                                               | 引擎                 | 不收住的后果                                                                                  | 处理                                                                                                         |
| -------------------------------------------------------------------- | -------------------- | --------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| `setPermissionRequestHandler` 的 "ask" 分支（`main.js`）             | `permission-service` | 网页**卡在"等待授权"**：请求已登记，而回答它的 `permission:respond` 已被 blocked → 没人能回答 | 引擎关时**直接拒绝**（`callback(false)`）                                                                    |
| 关引擎那一刻**已在等回答**的请求                                     | `permission-service` | 同上（关引擎之前登记的）                                                                      | `closeOutPendingPermissionRequests()`：逐个 `respondToRequest(id, false, /**persist**/)`                     |
| `password:autofill-menu` / `password:captured`（`ipc/passwords.js`） | `password-service`   | 弹出一个**点了必然失败**的浮层（它的数据要经已 blocked 的 `password.*` 取）                   | 入口处直接 `{ ok: false }`，且放在**任何 invoke 之前**（免得刷一屏"能力不可用"的错误日志，被读者当成真故障） |

**门禁位置的精确性 —— 这一条比"加个判断"更难做对。** 权限那条闸门**刻意放得很靠后**
（在 `resolveRequest` 判定出 `allow`/`block` 之后、`createRequest` 之前），而不是 handler 开头：

- `openExternal` / `fullscreen`（`ALWAYS_ALLOW`）/ 非主框架 / `DEFAULT_ALLOW` /
  **库里已存的 allow·block** —— 这些分支**都不需要界面**，引擎关了它们依然正确；
- 只有 `'ask'` / 无记录这一段，前提才是"有个界面能问用户"。

闸门提前到开头会平白砍掉前面那些仍然正确的行为（fullscreen 被一起拒、已存的"允许"规则失效）。
**"引擎关了"该收敛的是"需要它的那一段"，不是整个 handler。**

**`persist=false` 也是刻意加的**：那次拒绝是**系统替用户做的**，不能写进权限库 ——
否则会给该站点永久留下一条 "block" 规则，用户重新打开引擎后会看到
"这个网站怎么自己变拒绝了"，且再也说不清是谁改的。只拒绝**这一次**在等回答的请求，
不改变任何已存的用户决定。

> 主进程侧用的是**同一份 `feature-map`**（`isFeatureOn(id)`），与渲染侧的
> `features:availability` 端口同源。共用是必须的：两边各判各的会出现
> "界面把入口藏了、后端却照旧接受请求"（或反过来）的分叉。

**下载条那条"顺带修掉的真问题"**：它每 1500ms 打一次 `download:list`。引擎被禁后那次调用
必然失败 —— 白白唤醒主进程 + 刷一屏错误。所以引擎没了必须**停表**，不能只隐藏。
这与该文件头那条"窗口不可见时绝不唤醒主进程"是同一条原则。

#### 有意**不**登记的功能面（按事实登记，不按愿望登记）

- ~~`space.*`（空间）~~：**已闭环**。收尾遗留时补上了 `space-service` 引擎插件，
  现在 `spaces` 按事实登记，空间切换器胶囊 / 空间菜单浮层 / 空间面板都跟着它联动。
  （补归属之前不能登记 —— 那时引擎启停根本不影响空间，登记了只会把正常入口藏起来。）
- **`settings`（设置）与 `tabs`（标签）**：对应引擎已是 core（不可禁用），
  登记了永远不会命中，反而让人误以为可关。
- **⋮ 菜单里的 cookies / clear-data / import-data / task-manager / certificates / update /
  crash-report / about / view-source / page-info**：逐个核对过 registrar 与通道 ——
  它们由内核直接实现，**不经过任何 14 引擎的 capability**，引擎开关不影响它们。

#### 依赖次序（原计划）与实测结果

本块的输入确实是 §9.3 的 `blockedCapabilities` 与 ②③ 的关系数据 ——
**没有 ②③，这里的"隐藏依据"就是假的**（面板不会 blocked、关系表算不出连带）。
实测顺序成立：① → ② → ③ → ④ 每一步的产出都是下一步的输入，没有回填。

### 10.5 执行顺序（**已定，不许跳步**）

> 顺序严格照本节的既有小节次序：**§9（地基）→ 10.2 体现 → 10.3 管理 → 10.4 联动**。
> 用户明确要求：**一次把所有引擎全部适配**，不做"先拿一个试点" —— 只覆盖一部分引擎会留下
> "有的开关真生效、有的假生效"的**半生效态**，比现状更难解释（现状是统一假生效，用户至少
> 能学到一条规律）。所以是「先把机制做全，再一次性铺到全部引擎」，不是「滚动试点」。

| 序    | 对应小节 | 做什么                                                                                                                                                                                                       | 状态                        |
| ----- | -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------- |
| **①** | §9.3     | `blockedCapabilities`：注册中心依据「被**显式禁用**（用户关 or 连环坏停用）的插件的 `manifest.capabilities`」现算一张表；`provider-bridge` 在 `!hasProvider` 分支命中该表即**抛"能力不可用"而非走 fallback** | ✅ **已落地**（冒烟 15 项） |
| **②** | §10.2    | **体现**：双向依赖可视化（我依赖谁 / 谁依赖我）、显示中文名、`optionalDependsOn`（软依赖）与硬依赖分开呈现                                                                                                   | ✅ **已落地**（冒烟 16 项） |
| **③** | §10.3    | **管理**：选定连锁语义 **(b) 确认后一起禁用**（两段式）；拓扑序恢复；下游第 **5** 态 `blocked`；**CORE 静态判定 + 被依赖动态判定两者都要拦**；取消禁用后的恢复顺序                                           | ✅ **已落地**（冒烟 33 项） |
| **④** | §10.4    | **联动**：「功能面 → 引擎插件」映射 + **一个**可用性查询端口 + **一处**订阅；面板走依赖图、核心 chrome 走端口；依赖各引擎的 UI 入口逐个优雅隐藏                                                              | ✅ **已落地**（冒烟 22 项） |

**每一步的净效果**（这就是"不许跳步"的意义 —— 每一步都把上一步的产出当输入）：

```
① 让"禁用"有净效果        →  关掉 bookmark 引擎，bookmark.* 调用真的失败
② 让人看得见连带范围      →  插件中心出现"依赖 / 被依赖"，且软硬分列
③ 让禁用可控             →  关前置会先确认"将一并禁用 X、Y"，下游落 blocked 而非 failed
④ 让界面跟着收敛          →  书签栏/星标/⋮菜单项/面板入口一起消失，不留报错
```

少任何一步都会留下一个"看起来能用、实际是坏的"状态：只有 ① 会到处报错；
只有 ①② 会"看得见连带却关不掉"；只有 ①②③ 会"关得掉但界面留着报错的入口"。

**依赖是硬的**：③ 的"被依赖动态判定"需要 ② 的关系数据；④ 的 UI 隐藏需要 ③ 的
`blocked` 态与 ① 的真禁用（否则隐藏的依据是假的）；④ 内部的"14 引擎适配"又必须在
① 之后（否则被 fallback 兜着，白改）。

> **①与④之间有个必须忍的中间态**（现已走完）：只做了 ① 而没做 ③④ 时，用户能关掉
> `tabs-service` 这种结构性核心，浏览器当场不可用；也能关掉 `bookmark-service` 而
> 书签栏 / 星标 / ⋮ 菜单里「书签」全都还在，点进去才报错。§9.3 已经预告过这一点
> （"必须配套的前置"）。这不是可以偷懒跳过 ③④ 的理由 —— 而是**必须连续把 ①②③④
> 走完**的理由。四条现已全部落地（见下方 ✅ 标记）。

| 9   | `session-service`          | `session.*`         | 空                                        | 会话恢复 / 退出时保存                                              |
| 10  | `settings-service`         | `settings.*`        | 空                                        | **设置页 + 全部 KV 存储**（见下方 ⚠）                              |
| 11  | `keybindings-service`      | `keybindings.*`     | 空                                        | 快捷键绑定 / 全局快捷键注册                                        |
| 12  | `extensions-service`       | `extensions.*`      | 空                                        | 扩展管理 / 扩展加载                                                |
| 13  | `external-games-service`   | `external-games.*`  | 空                                        | 外置游戏（进程级单例资源，见 §8.3）                                |
| 14  | `tabs-service`             | `tabs.*`            | 空                                        | **标签管理**（被面板插件与绝大多数 UI 依赖，见下方 ⚠）             |
| 15  | `space-service`            | `space.*`           | 空（工厂默认）                            | 空间切换器胶囊 / 空间菜单浮层 / 空间面板 / 空间管理页              |

> **第 15 行是收尾遗留时补上的**：`space.*` 此前**没有任何插件声明**，于是它既进不了
> `blockedCapabilities`（开关对它无效），也无法在 §10.4 的可用性表里按事实登记。
> 补 `space-service` 时才暴露出这一类改动最典型的坑 —— 见下条 ⚠。

> ⚠ **两个"动一下就伤到自己"的**，归**步骤 ③（§10.3 管理）**处理，不当普通引擎：
>
> - **`settings-service`**：`plugin-state-store.js` 本身就用 settingsService 的 KV 存
>   `plugins.disabled` / `plugins.autoDisabled`。禁用它 → **设置页与所有 IPC 上的 KV 读写
>   全断**（插件开关状态本身仍能落盘 —— 那一路走的是 settingsService 的**直接引用**，
>   不经 invoker，这个区别很关键，别误判成"存储层自己没了"）。
>   它属 §8.3 的**设施/前置**类，正解是 §10.3 point 3 的 **CORE 静态判定**。
> - **`tabs-service`**：拥有全部 `tabs.*`（列表/新建/切换/关闭/排序/导航/固定/静音/休眠），
>   是**浏览器最小可运行集合**。它同样没有任何 manifest 声明 `dependsOn` 它，
>   所以 §10.3 的动态依赖保护**挡不住它**，也必须靠 **CORE 静态判定**。
>   两者一起，正是 §10.3 说的"CORE 是静态声明、被依赖是动态信息，**两者都要拦**"。

> ⚠⚠ **把某个域"插件化"时最容易踩的坑：只搬实现、不搬副作用。**
>
> `provider-bridge` 的调用式是 `invoke(capability, fallback)`，第二个参数是
> 「**没有 provider 时**才跑」的分支。而历来的写法把 **API 编排也写在这个 fallback 里** ——
> 在没有对应引擎插件的年代它总能跑到（永远走兜底），所以完全看不出问题。
>
> 一旦补上引擎插件，fallback 就不再执行，于是**这些副作用静默消失**：
>
> | 位置           | 写在 fallback 里的编排                                     | 插件上线后的症状                   |
> | -------------- | ---------------------------------------------------------- | ---------------------------------- |
> | `ipc/space.js` | `notifyChanged`（建/删/改/排序空间后广播 `space:changed`） | 改完空间界面不刷新，**无任何报错** |
> | `ipc/space.js` | `destroySpaceTabs`（删空间时销毁它的标签）                 | 删掉的空间标签变成僵尸，占着内存   |
> | `ipc/space.js` | `space.listAll` 的 internal-profile **过滤**               | internal 空间漏进用户可见列表      |
> | `ipc/space.js` | `switchSpace` + `emitToWindow`（切空间的编排与窗口级推送） | **切空间不生效**，且界面不知道     |
>
> **正确做法：编排一律提到 handler 里、在 provider 调用之后执行**（这样两条路径都会跑到），
> 只有"实现需要的数据"才经 `invoke` 的第 4 个参数（context）传进去
> （例如 `getUsingSpace`：它是**窗口级**运行态，插件自己查不到"是谁在问"）。
> 判据很简单：**"无论谁实现都必须发生的事" = 编排，留 handler；
> "实现要靠它才能算出结果的东西" = 数据，走 context。**

> ⚠ **配套门禁：`manifest.capabilities` 必须覆盖模块实际注册的能力。**
>
> `blockedCapabilities` 完全建立在 manifest 的静态声明上（原因见上文），
> 所以"模块注册了但 manifest 漏声明"的 capability **不会**被禁用拦下 ——
> 表现就是又一个"开关失效"。这类漂移人眼盯不住（改 `.cjs` 忘改 `.json` 太容易），
> 因此 `scripts/check-plugin-coverage.cjs`（`pnpm plugin:coverage`）加了一条硬性检查：
> 用桩 ctx 调 `registerProviders()`，要求 **实际注册 ⊆ manifest 声明**。
>
> 它上线当天就抓到两个真实漏声明（共 6 个能力）：
> `extensions-service` 的 `inspectViewSources / inspectView / updateAll / newTabOverrideUrl`、
> `tabs-service` 的 `recently-closed / recently-closed:clear` —— 都是"引擎关了却照旧可用"。
> 方向是单向的：**实际 ⊆ 声明** 必须成立；声明多出来无害。

**步骤 ④ 内部还有一个必须守住的约束**（见上方面板陷阱）：面板插件的入口集合与
「按钮编辑浮层里的格子」必须**同源**，否则格子会永远拖不回来（§5 / §2 单一事实源）。
所以 ④ 的 UI 隐藏不是"给每个 UI 加个 if"，而是"把 UI 入口的可见性统一改接到可用性端口上"。

### 10.6 「不可禁用」：关掉它就没有回头路（**已落地**）

§10.3 的 CORE 静态闸门解决的是"关掉浏览器就残了"。但还有第二类插件，关掉它的后果
不是"功能坏了"，而是**按一下就永久锁死**：

| 插件                                    | 关掉之后的后果                                                 |
| --------------------------------------- | -------------------------------------------------------------- |
| `panel-plugins`（**插件中心面板自己**） | 用户把"管理插件的唯一入口"关掉了 —— 之后再也找不到地方把它打开 |
| `side-panel-skeleton`（所有面板的骨架） | 每个面板插件落 `blocked` → 插件中心面板也消失 → 同样是锁死     |

所以新增 `manifest.nonDisableable: true`（语义是"某个功能的唯一出口"，比 `core` 更窄），
并与 `core` 一起收口到**一个判定**：

```js
// PluginRegistryV2#isNonDisableable —— 唯一判定入口
return m.trustLevel === 'core' || m.nonDisableable === true;
```

**三层防线，缺一不可**：

| 层         | 位置                                                                 | 拦的是                                                                                                       |
| ---------- | -------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| ① 判定收口 | `isNonDisableable` + `describe().nonDisableable`                     | 不让各处各写一遍 `core \|\| nonDisableable`（将来加第三类必然漏改一处）                                      |
| ② 写入闸门 | `setUserDisabled(id, true)` 返回 `false`                             | **所有**写入路径：启动恢复、连带禁用、`enableWithPrerequisites`、IPC。只拦 IPC 等于没拦                      |
| ③ 启动自愈 | `enableAll` 循环前把不可禁用的从 `_userDisabled` 剔掉，`healed` 回传 | **已经写进去的历史状态** —— 老版本的 `plugins.disabled` 里躺着 `panel-plugins`，不剔就是"修了但他还是打不开" |

配套：`ipc/plugins.js` 的两道禁用闸门都改用**快照**里的 `nonDisableable`
（⚠ 不能用 `normalizeManifest` 的产物：那里的 `nonDisableable` 只是**原始声明**，
对 `core` 插件是 `false` —— 照着判会让 core 绕过闸门 1，真的被卸载）；
`plugin-bootstrap.js` 把被拒的 id 落盘清掉（一次性收尾）；
UI 的开关用它上锁并说明原因（"关掉它之后再没有界面入口能把它打开"）。

> **连带方向同样要挡**：只挡"禁用它自己"是没用的 —— 禁掉它的硬前置，它一样会落
> `blocked` 而从界面上消失。所以「连带集合里含不可禁用 → 硬拒」这条也必须保留，
> 且必须排在 `requiresCascade` 之前（权限判定早于确认流程）。

## 11. 插件权限与授权（PART7 §7.5）（**已落地**）

`plugin-sandbox.js` 早就实现了，却**从未被导出过** —— 一直是死代码。
现在它接进了两条链路：**加载期沙箱** + **授权闸门**。

### 11.1 manifest 侧的两个字段

| 字段                                       | 含义                                                    | 谁影响它                         |
| ------------------------------------------ | ------------------------------------------------------- | -------------------------------- |
| `requestedPermissions: string[]`           | 这个插件**想用哪些能力**（scope 名，如 `history:read`） | 插件作者                         |
| `permissionLevel: 'none'\|'ui'\|'network'` | 沙箱的**模块白名单级别**                                | 插件作者**建议**，但被信任级覆盖 |

**信任级决定待遇，绝不由插件自己声明**（`normalizeManifest` 里实现）：

```
trustLevel: 'internal' / 'core'   →  permissionLevel = 'full'、不加沙箱、不需要授权
其它（第三方）                     →  permissionLevel 取声明值（缺省 'ui'，非法值也回落 'ui'）、
                                     **加沙箱**、声明了权限就必须等用户授权
```

这一条是整个体系的支点：若插件写 `"permissionLevel": "full"` 就能拿到完整能力，
那这套权限体系等于**没有**。所以第三方声明的 `full` 会被**强制回落**到 `ui`。

**未知 scope 名在加载期就抛错**（`Manifest x: unknown permission scope(s): …`）。
静默忽略的后果是"插件以为自己要到了 `tabs:write`、实际什么都没要到"，
然后运行期报一堆看不懂的错 —— 而根因在 manifest。

### 11.2 沙箱（加载期）

非第一方的插件模块**不走原生 `require`**，而是把源码包一层、注入受限的 `require`：

```js
const factory = new Function(
  'require',
  'module',
  'exports',
  '__filename',
  '__dirname',
  source,
);
factory(createSandboxedRequire(level, scopes), mod, mod.exports, entry, dir);
```

**边界要写清楚，免得被误解成"安全沙箱"**：它挡的是**误用与顺手牵羊**
（社区 Mod 直接 `require('fs')` 读写用户磁盘 / `child_process` 起进程），
不是对恶意代码的对抗 —— 所以它**不是**唯一的一层。真正的隔离在 §11.5：
非第一方插件跑在**独立进程**里，这一层沙箱在进程内继续收窄"能 require 什么模块"，
两者是"进程边界 + 进程内白名单"的关系，不是替代关系。

### 11.3 授权闸门与第 6 态 `awaitingConsent`

`enable()` 的**第一道**闸门（先于前置闸门）：非第一方 + 声明了权限 + 尚未授权 → 停在
`awaitingConsent`，它**一行代码都不会被执行**。

**为什么排在前置闸门之前**：一个还在等用户点头的插件，连它的**前置都不该被拉起来** ——
否则用户"拒绝授权"之后，会留下一串"被他拒绝的插件的依赖被启用过"的状态。

**声明 ≠ 授权**，所以有独立的一张授权表：

| 动作                 | 结果                                                                                                                            |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| 用户点「同意并启用」 | `plugins:grant-permissions` → 主进程与 manifest **取交集** → 落盘 `plugins.grantedPermissions` → 顺手 `enableWithPrerequisites` |
| 用户点「暂不」       | 按**用户主动停用**处理（`setUserDisabled`）——它留在关闭态、不再挂提示；想用再点开关会**再问一次**                               |
| 撤销授权             | 传空数组 → 立刻 `disable`（否则它会带着刚被收回的权限继续跑）                                                                   |

两条安全边界：

- **`scopes` 只能是插件自己声明过的那些**（主进程取交集，越界项记告警并忽略）。
  渲染层无权给插件塞它没申请的权限 —— 否则一个被篡改的渲染层就能提权。
- **`setUserDisabled(id, true)` 会清掉 `awaitingConsent`**：用户用「暂不」表达过态度了，
  再一直挂着"请授权"的弹窗就是把责任推回去。

### 11.4 界面：四种"没在跑"用四种颜色

插件中心按状态给出**不同的下一步**（见 §8.1 的表）：`failed` 红（等自愈）/
`autoDisabled` 琥珀（点开关恢复）/ `blocked` 蓝（点开关会拉起前置）/
`awaitingConsent` **紫**（列出申请的权限 + 同意/暂不）。

**授权弹窗必须逐条列出它想干什么**，且用**中文名**（"读取浏览历史"）而不是
`history:read`。用户唯一能做的判断就是"我愿不愿意让它读我的浏览历史"——
只给一个"同意"按钮而不说同意什么，那是把责任推给用户却不给信息。
翻译表（`SCOPE_LABELS`）放在 `plugin-sandbox.js`（scope 的权威定义处），
经 `describe().requestedPermissionLabels` 下发，**不在渲染层抄一份** ——
否则加 scope 时必然漏改一处。

**「拒绝」也必须给得出**：不然用户只有"同意"一条路，那不叫授权，叫通知。

### 11.5 进程级隔离（`utilityProcess` 宿主，**已落地**）

§11.2 那层沙箱挡的是"顺手 require"，挡不住恶意逃逸（拿到 `Function` 就能绕过一切）。
唯一真正的边界是**进程**：非第一方插件不再长在主进程里，而是被 `utilityProcess.fork`
到一个自包含的宿主进程里跑。**第一方插件不受影响**（它们是浏览器本身，必须和主进程共享
同一份活对象），所以下面所有描述都只针对**非第一方**。

#### 三个文件，一条边界

| 文件                         | 角色                                                                                                                       |
| ---------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| `main/plugin-host.js`        | **宿主进程**（worker）。只 `require` `fs`/`path`，自带一个迷你 CJS 加载器，`new Function` 编译插件源码。它是隔离的物理边界 |
| `main/plugin-host-client.js` | 主进程侧的宿主客户端。`fork` / 握手 / 超时 / 崩溃上报 / 在**真 ctx** 上执行能力调用 / 权限闸门                             |
| `main/plugin-isolation.js`   | 隔离**端口**的实现（组合根）。决定"哪些插件进进程、哪些走默认策略"，并算模块白名单                                         |

**infra 对"进程"零感知**：`PluginRegistryV2` 只知道自己拿到一个 `options.loader` 端口，
端口签名是 `loader(manifest, { context, loadDefault })` —— 端口可以只接管一部分插件，
其余 `loadDefault()` 委托回默认策略（第一方 require / 第三方进程内沙箱）。
`plugin-isolation.js` 正是这么做的：`m.isFirstParty` → 直接委托。

#### 协议（主进程 ⇄ 宿主，两向四类消息）

| 方向      | 消息          | 载荷                                                                                          |
| --------- | ------------- | --------------------------------------------------------------------------------------------- |
| 主 → 宿主 | `init`        | `{ reqId, id, entry, source, permissionLevel, grantedScopes, allowedModules, deniedModules }` |
| 主 → 宿主 | `invoke`      | `{ reqId, path, args }` —— 调 `exports` 上的某个函数                                          |
| 主 → 宿主 | `call-result` | `{ reqId, ok, value \| error }` —— 回宿主发起的 `call`                                        |
| 主 → 宿主 | `dispose`     | 无载荷，宿主 `process.exit(0)`                                                                |
| 宿主 → 主 | `ready`       | `{ reqId, ok, exports \| error }` —— 编译完成的握手回执                                       |
| 宿主 → 主 | `reply`       | `{ reqId, ok, value \| error }` —— `invoke` 的应答                                            |
| 宿主 → 主 | `call`        | `{ reqId, path, args }` —— 宿主请求主进程执行一个能力                                         |
| 宿主 → 主 | `log`         | `{ level, message }` —— 未捕获异常 / 未处理拒绝走这里                                         |

三条**请求-应答**通道（`invoke`/`reply`、`call`/`call-result`、`init`/`ready`）各自带
`reqId`，两边都维护 `pending` 表 + 超时（客户端缺省 15s、宿主侧调用 20s）。

#### 函数与活对象怎么过进程：三种句柄

`postMessage` 的结构化克隆**丢函数**，而插件 API（`ctx.tabManager.create()`、回调注册…）
几乎处处是函数。解法是"把不可克隆的东西换成句柄标记，到了对面再还原成代理"：

| 标记           | 含义                                                           | 还原成                                 |
| -------------- | -------------------------------------------------------------- | -------------------------------------- |
| `__hiraRemote` | 一个函数（带 `REMOTE_PATH` 的可调用句柄）                      | 本地函数，调用即向对面 `invoke`/`call` |
| `__hiraCtx`    | **ctx 顶层值**的身份标记（如整个 `tabManager`、`webContents`） | 对面 ctx 上的同一个值，**不进引用表**  |
| `__hiraRef`    | 其余活对象（非 ctx 顶层）                                      | 按 token 从引用表取回原对象            |

`__hiraCtx` 这层是刻意加的：hook 参数是 `{ ...context, pluginId, manifest }`，
`context` 的每个顶层值都不可克隆，若都进引用表会**疯狂膨胀**；用身份反查把它们换回
"对面本来就是同一个 ctx"的标记，只有真正零散的非 ctx 活对象才登记 `__hiraRef`
（两侧引用表都设上限，超了 FIFO 淘汰）。

#### 权限闸门（ctx 侧）

宿主里的插件拿到的是一个 **Proxy**：属性读就往下走一层（返回更深的能力代理），
调用就发 `call` 回主进程执行。**能不能走到某个路径由主进程说了算** ——
`_assertCtxAllowed(segs[0])` 对着两张表放行：

- `BASE_CTX_PATHS`：`providerRegistry` / `contributions` / `extensionPoints` / `panelCatalog`
  —— 这些是**扩展面本身**（注册 provider、声明贡献、调度插槽、读面板目录），
  任何已启用插件都放行：插件用它来扩展浏览器，不是读用户数据。
- `SCOPE_CTX_PATHS`：scope → 它解锁的 ctx 顶层路径（如 `tabs:read` → `tabManager`、
  `permissions` → `getDomainServices`）。**scope 的语义只有一份**（在 `plugin-sandbox.js`
  的 `SCOPE_PERMISSIONS`），这里只多一句"落到哪个 ctx 手柄"——APPS 侧才知道 ctx 长什么样。

未授权的 scope **连路径都走不到**：不是"调了被拒"，是 `tabManager` 这个手柄压根没下发。

#### 崩溃语义（PART7 §7.13 的硬指标）

宿主 `exit`（崩溃 / 被超时 kill / `dispose`）时客户端做三件事：**拒绝全部 pending**、
`_failInit`（若还没握手完）、非主动 `dispose` 时回调 `onCrash(id, err)`。
`onCrash` 接到 `PluginRegistryV2.reportPluginError` → 落到 `failed` / 连环坏 → `autoDisabled`。
**主进程与其余插件毫发无损** —— 这正是"社区 Mod throw 100 次，其他插件完全不受影响"。

#### 加载链路的配套改造（异步化）

fork + 握手是**异步**的，于是 `PluginRegistryV2._loadModule` 从 sync 变 async，并带出三处：

| 改造                                     | 为什么                                                                                 |
| ---------------------------------------- | -------------------------------------------------------------------------------------- |
| `_pendingLoads`                          | 并发加载**合并**为同一个 Promise（否则 `installAll` + `enable` 会 fork 两个宿主）      |
| `_loadErrors`                            | 会话内**失败缓存**：坏插件不在 `installAll`、`enable` 各试一次（且 `reload` 会清掉它） |
| `installAll` 改 async + 单插件 try/catch | 一个坏插件不拖垮其余插件的安装（对齐 `enableAll` 的失败隔离）                          |
| `disable` / `uninstall` tolerant load    | 加载失败的插件再次进入清理路径时不再抛错（`mod` 可能为 `null`，钩子加 `mod &&` 守卫）  |

#### 打包与退出

- `package.json` 的 `build.asarUnpack` 把 `out/main/plugin-host.js` 解出来 ——
  `utilityProcess.fork` 要指向**真实磁盘文件**，asar 内路径不可靠。
- `onBeforeQuit` 第 8 步 `pluginIsolation.dispose()`：无参 dispose 关掉**全部**宿主，
  同时置 `disposed` 标志，之后任何新的加载请求直接抛错（避免退出中途又 fork 出孤儿进程）。

## 12. 主动健康检查 + 热重载（PART7 §7.5）（**已落地**）

### 12.1 为什么还需要健康检查（`onCrash` 不够）

| 机制                    | 触发方式                     | 抓的是                                                                           |
| ----------------------- | ---------------------------- | -------------------------------------------------------------------------------- |
| `lifecycle.onCrash`     | **被动**：出错才计数         | "调用了坏代码"                                                                   |
| `lifecycle.healthCheck` | **主动**：定时问"你还活着吗" | "没抛错但已经不能干活了"（它依赖的外部服务退了、连接断了、进入了半死不活的状态） |

后者**永远不会触发前者** —— 没有异常可抛。两者互补，不是替代。

**判定与后果复用同一条路**：连续失败触顶 → `autoDisable()`（第 4 态
`autoDisabled`）→ 于是"一键恢复""落盘""广播""面板对账"全都有了，**不需要第二套**。

### 12.2 manifest 与 hook

```json
{
  "id": "external-games-service",
  "healthCheck": { "interval": 30000, "timeout": 5000, "failures": 3 }
}
```

也接受 PART7 的分组写法 `lifecycle: { healthCheck: {...} }`（与 `entry.{main,render}`
同一套"兼容读"策略）。**未声明 = 不做检查**（默认行为与加入本特性之前逐字一致）。

模块侧：

```js
module.exports = {
  healthCheck(ctx) {
    if (!upstreamAlive()) return { ok: false, reason: '外部服务已退出' };
    // 返回 undefined / true 都算健康
  },
};
```

| 返回                    | 判定                                                      |
| ----------------------- | --------------------------------------------------------- |
| `undefined` / `true`    | 健康                                                      |
| `false`                 | 不健康（通用文案）                                        |
| `{ ok: false, reason }` | 不健康，`reason` 会**原样进入自动停用原因**（用户看得到） |
| 抛错 / 超时             | 不健康                                                    |

### 12.3 三条容易做错的边界

| 边界                   | 处理                           | 为什么                                                                  |
| ---------------------- | ------------------------------ | ----------------------------------------------------------------------- |
| 上一拍还没跑完         | **跳过这一拍，不排队**         | 健康检查慢 = 它本身有问题，堆一队只会压更多调用上去                     |
| 计时器                 | 一律 `unref()`                 | 健康检查**绝不能拦住进程退出**；退出时另有 `stopAllHealthChecks()` 兜底 |
| 声明了却没写 hook      | **不起表，也不告警**           | "只声明不实现"是合法降级，不是错误                                      |
| 期间被停用/禁用/热重载 | 结果**作废**（比对表实例身份） | 否则会把旧实例的失败记到新实例头上                                      |

计时器由 **infra** 拥有，不是 APPS：配置（manifest）、hook、计数三样输入全在
infra 手里，APPS 要做得先把三样都问一遍再自己计数 —— 那才是真的耦合。
APPS 侧只多了一行 `stopAllHealthChecks()`（退出时）。

### 12.4 热重载（`plugins:reload`）

改一行插件代码就要重启整个浏览器，是这个系统最大的开发体验缺口。
`PluginRegistryV2#reload(id)` 补上它，插件中心每行有「重新加载」按钮。

顺序**先停干净再换代码**，不是反过来：

```
disable()          摘 provider / 插槽实现 / 声明式贡献 / 样式 / 健康检查表
   ↓
modules.delete(id) + 清 require.cache（仅第一方入口）
   ↓
重读 manifest（作者可能同期改了它；解析失败 → 退回内存里的旧版本并告警）
   ↓
重新编译模块 → 原本在跑就 enable() 重挂
```

⚠ **失败语义是刻意的**：新代码加载不了就**抛给调用方**（UI 显示"模块无法加载：xxx"），
插件停在停用态。悄悄退回旧版本更糟 —— 作者会以为"我的改动生效了"，
然后在完全错误的方向上调试。

**已知边界**：只清**入口文件**的 `require.cache`。第一方插件入口自己 require 的兄弟文件
仍是旧代码（本仓库的插件都是单文件 `.cjs`，不存在这种形态）；第三方插件走沙箱路径
（每次重读源码），不受此限。

## 13. 插件作者手册（SDK：脚手架 + 校验器）

> 面向**写插件的人**（含未来的第三方）。维护者视角的原理与决策记录在前 12 节。

### 13.1 五条命令

```bash
pnpm plugin:new my-plugin --cap my.thing --render --panel "my-panel:我的面板:Star"
pnpm plugin:new my-plugin --page "home:我的首页"   # 内部页：pages/home/index.html → hira://p-my-plugin-home/
pnpm plugin:new my-plugin --bang "my:我的搜索"     # 搜索指令：!my 关键词
pnpm plugin:new my-plugin --menu                   # 主菜单「工具」+ 网页/标签右键各加一项
pnpm plugin:validate my-plugin        # 也可以传目录或 manifest 路径；零错误才能往下走
pnpm plugin:publish my-plugin         # 打包 zip + 算 sha256 + （可选）签名 + 生成索引条目
pnpm plugin:coverage                  # 仓库级门禁（CI / 提交前）
pnpm plugin:publish my-plugin --help  # 全部选项
```

`plugin:new` 生成的是**能跑的真插件**，不是占位桩：声明的能力一定在
`registerProviders()` 里逐条注册（否则 `plugin:coverage` 立刻报「声明了却没注册」）。
生成后 `plugin:validate` 应当**零错误**通过。

`plugin:validate` 的**错误 / 警告分界**（刻意如此）：

| 类别     | 内容                                                                                                                                             | 影响退出码 |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------ | ---------- |
| **错误** | manifest 解析不了 / 未知权限 scope / 入口不存在 / `render` 后缀不对 / 模块加载失败 / 缺 `install·enable·disable` / **能力声明漂移** / 硬依赖缺失 | ✅         |
| **警告** | 文件名与 id 不一致 / 第三方插件声明面板却没有 `render` / 声明了 `healthCheck` 却没写 hook / 软依赖缺失 / capabilities 重复                       | ❌         |

一条字段写错**不会**只报它 —— 校验器会降级成"宽松版 manifest"把余下问题一次报全，
免得作者来回改十遍。

#### 13.1.1 打包与发布（`plugin:publish`）

```bash
# 最小：产出 dist/acme-demo-1.0.0.zip，并打印索引条目让你自己贴
pnpm plugin:publish ./my-plugin

# 完整：就地合并索引 + 签名
pnpm plugin:publish ./my-plugin \
  --out ./dist \
  --index ./dist/index.json \
  --base-url https://cdn.example.com/pkgs \
  --key ~/.keys/acme-publisher.pem --key-id acme-publisher
```

| 选项                         | 作用                                                                                              |
| ---------------------------- | ------------------------------------------------------------------------------------------------- |
| `--out <目录>`               | 产物目录（默认 `<插件目录>/../dist`）                                                             |
| `--base-url <地址>`          | 索引里的 `url` 写成绝对地址；不给则写相对路径 `./xxx.zip`（索引与包放在一起时更好，换域名不用改） |
| `--index <文件>`             | 已有索引：**按 id 就地覆盖**那一条（不会动其它插件的条目；索引坏掉时拒绝改动而不是重建）          |
| `--key <私钥> --key-id <id>` | 给 manifest 签名。`keyId` 默认取私钥文件名；用户需把对应**公钥**放进 `plugin-trust/<keyId>.pem`   |
| `--no-write-manifest`        | 不把签名写回 `hira-plugin.json`（默认**会写回**，因为签名是 manifest 的一部分、该进版本控制）     |
| `--dry-run`                  | 只打印计划与 sha256，不写任何文件                                                                 |

**两条必须知道的行为**：

1. **打包用的忽略表与遍历就是安装器那套**（`node_modules` / `.git` / 符号链接一律不进包，
   体积上限同一份）。所以"本地能跑、装上去少文件"这类问题不会因为打包脚本而出现。
2. **包里的 manifest 由最终对象直接渲染**，不是回读磁盘那一份 —— 否则
   `--no-write-manifest` 会把刚算好的签名丢掉（打成"不带签名"的包，而你以为是签过的）。

发布完把 `dist/` 整个传到任意静态托管，在插件中心的「插件源」里填索引地址即可。

### 13.2 manifest 字段速查

| 字段                   | 必填 | 说明                                                                                                                                                                                                         |
| ---------------------- | ---- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `id`                   | ✅   | 与文件名保持一致（校验器会警告）                                                                                                                                                                             |
| `name` / `description` |      | 支持 `{"zh-CN": "…"}` 多语言形态，注册中心会归一化成单串                                                                                                                                                     |
| `version`              |      | 缺省 `0.0.0`                                                                                                                                                                                                 |
| `type`                 |      | `feature-plugin`（默认）/ `ui-panel-plugin` / `service-plugin` / `community-mod`                                                                                                                             |
| `trustLevel`           |      | `internal`（默认）/ `core` / `community`。**`internal` 与 `core` = 第一方**：不沙箱、不需要授权、`permissionLevel` 强制 `full`                                                                               |
| `main`                 | ✅   | 主进程入口（相对 manifest）。也接受 v2 分组写法 `entry: { main, render }`                                                                                                                                    |
| `render`               |      | **渲染侧入口**。内置实现以 `.renderer.js` 产出独立 ESM；第三方可写 `.js/.mjs/.cjs`，统一由 `hira-plugin://` 运行时加载                                      |
| `capabilities`         |      | 这个插件**提供**的能力面。⚠ 必须与模块实际注册逐字一致（见 §9.3）                                                                                                                                            |
| `dependsOn`            |      | 硬依赖：缺了启动期直接抛错                                                                                                                                                                                   |
| `optionalDependsOn`    |      | 软依赖：存在就用、不存在也照装                                                                                                                                                                               |
| `conflictsWith`        |      | 声明冲突（互斥）                                                                                                                                                                                             |
| `requestedPermissions` |      | 想申请的 scope（见 `plugin-sandbox.js#SCOPE_PERMISSIONS`）。**写错的名字在加载期就抛错**                                                                                                                     |
| `permissionLevel`      |      | `none` / `ui` / `network` / `full`。第三方**写 `full` 会被强制回落 `ui`** —— 信任级决定待遇，不由插件自声明                                                                                                  |
| `healthCheck`          |      | `{ interval, timeout, failures, enabled }`；见 §12                                                                                                                                                           |
| `nonDisableable`       |      | **不可禁用**（比 `core` 更窄的那一类，见 §10.6）：它是某个功能的**唯一出口** —— 关掉之后没有任何界面入口能再把它打开。目前用于 `panel-plugins`（插件中心面板自己）与 `side-panel-skeleton`（所有面板的骨架） |
| `signature`            |      | `{ algo, keyId, value }` —— 可选签名，**仅在安装时校验**（见 §15.6）。验不过**不阻止安装**，只在插件中心提示；`unknown-key` 与 `invalid` 是两件事                                                            |
| `contributes`          |      | 声明式贡献：`panels` / `pages` / `bangs` / `menus` / `rendererSlots` / `importFormats` / …（见 §4.5、**§4.7**）。`rendererSlots` 决定非面板窗口要不要 import 你的渲染模块，漏写 = 那里的槽不生效 |

### 13.3 生命周期 hook（按调用顺序）

```
install 期（只在首次安装跑一次）  preInstall → install → postInstall
enable  期（每次启用都跑）        preEnable  → enable  → postEnable
disable 期（停用时跑）            preDisable → disable
uninstall                         uninstall
```

外加（不按阶段，按需调用）：

| hook                     | 用途                                                                |
| ------------------------ | ------------------------------------------------------------------- |
| `registerServices(ctx)`  | 导出服务对象（`{ name, service }`）                                 |
| `registerProviders(ctx)` | 注册能力 provider（**capabilities 的落地处**）                      |
| `extensionPoints(ctx)`   | `{ provides: [插槽定义], extends: [{ to, impl }] }` —— 挂扩展点实现 |
| `injectStyles(ctx)`      | 往渲染层注入 CSS                                                    |
| `healthCheck(ctx)`       | 主动健康检查（§12）                                                 |

⚠ **`disable` 里的清理是硬要求**：`enable` 挂的定时器 / 订阅 / 全局副作用必须在这里收干净，
否则"禁用"只是看起来生效（这正是本仓库 §9 那个最难查的病的形态）。

### 13.4 三种扩展方式，该用哪个

| 想做的是                                              | 用哪个                                                  | 关键约束                                |
| ----------------------------------------------------- | ------------------------------------------------------- | --------------------------------------- |
| 提供**能力**（让宿主能 `invoke('x.y')`）              | `capabilities` + `registerProviders`                    | 清单必须与注册一致                      |
| 往**数据流**里插一脚（搜索建议、历史过滤、导航改写…） | 扩展点插槽（`extensionPoints` hook，§3.10 契约速查）    | 先声明后实现；未声明的槽会抛错          |
| 往**界面**里加东西                                    | `contributes`（纯数据）或 `render` + 渲染侧插槽（§3.8） | 产出物是 DOM → 必须走渲染侧；过不了 IPC |
| 加**内部页**（`hira://` 独立页面）                    | `contributes.pages`（§4.7 ①）                           | 纯静态资产，相对引用；`..` 会被拒绝     |
| 加**搜索指令**（`!xx 关键词`）                        | `contributes.bangs`（§4.7 ②）                           | 模板认 `{query}` / `%s`；动态的走插槽   |
| 加**主菜单 / 右键菜单项**                             | `contributes.menus`（§4.7 ③）                           | 靠 `where` 定落点；动态项走插槽         |

**三份清单别混**：`capabilities`（我能干什么）≠ `contributes`（我往界面填了什么数据）
≠ 插槽实现（我在别人的流程里插了一脚）。一个功能常常要两两配合，
例如书签导入格式：`contributes.importFormats`（声明侧，给 UI 列下拉）

- `bookmark.import-format` 插槽（执行侧，真正解析）。

## 14. UI 视觉回归基线（`pnpm test:ui-tabbar`）

### 14.1 为什么要它

`tabbar.*` 那三个插槽（`item-renderer` / `drop-target` / `tab-stack-renderer`）
在 `ui/ui-tabbar` 里接线之前，先钉住了"接线前的样子"。标签条是整个界面**最热**的
渲染路径，没有这层安全网，"改完有没有画坏"只能靠肉眼 —— 而现在三个槽都已接上，
每一处改动都在 diff 之下（见 §3.9 的"追加不替换"契约）。

**这条基线还有一个副产品**：它把"渲染环境漂移"和"代码改动"彻底分开了。
接线过程中曾出现过稳定的 36 像素差异，逐文件回滚后差异**依然存在** ——
于是可以确凿地判定那是首帧渲染的暖机差异，与代码无关。
没有基线就只能靠猜。

### 14.2 怎么跑

```bash
pnpm test:ui-tabbar                 # 与基线比像素；不一致 → 退出码 1 + 写出 diff 图
pnpm test:ui-tabbar -- --update     # 用本次结果覆盖基线（**确认没画坏**之后才这么用）
pnpm test:ui-tabbar -- --case=003   # 只跑某一条
```

| 位置                              | 内容                                                                      |
| --------------------------------- | ------------------------------------------------------------------------- |
| `tests/ui/tabbar/cases.cjs`       | case 表（**纯数据**）：每个 case = 主题 + 尺寸 + 一份 `renderTabs()` 投影 |
| `tests/ui/tabbar/run.cjs`         | 运行器：esbuild 现场打包 → 真实 Chromium 截图 → 与基线比像素              |
| `tests/ui/tabbar/page.mjs`        | 页面侧 harness（只渲染，不做断言）                                        |
| `docs-ng/ui-baseline/tabbar/`     | 基线 PNG + 元数据（尺寸 / 缩放 / 标签数 / 芯片数）                        |
| `tests/ui/output/tabbar/<runId>/` | 每次运行的 actual / diff / report                                         |

### 14.3 四条设计约束（都踩过）

| 约束                                          | 为什么                                                                                                                                                                                                                                                                                                |
| --------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 必须**真 Chromium**（不用 jsdom）             | 基线的全部价值是像素。jsdom 不做布局、不做层叠、算不了 `getBoundingClientRect` —— 拿它跑出来的是"桩的基线"                                                                                                                                                                                            |
| 背景与文字色必须用**主题变量**                | 标签栏自己是透明的（铺在窗口画布上）。硬编码 `#ffffff` 会让深色 case 拍出来还是浅底；而 tokens 只定义了 `--text-color` **变量**、没人消费成 `color`，缺了 app-shell 那层 `html, body { color: var(--text-color) }`，文字会落回浏览器默认黑 —— 那不是组件缺陷，是 harness 少一层的假象                 |
| 截图统一 `resize` 到 case 声明的 CSS 像素尺寸 | 不同 DPI 下 `capturePage` 的物理像素不同，不归一会让基线在不同机器上根本不可比                                                                                                                                                                                                                        |
| 基线**必须可复现**（连跑两次 diff = 0）       | 会漂的基线等于没有基线。7 条在连续两次之间都是 0 差异（首次生成时曾出现稳定 36~74 像素的暖机漂移 —— 用 `--update` 重采一次后归零，说明它来自首帧而不是组件）。⚠ **深色那张是唯一偶发漂的**（实测出现过一次 19 像素，推断是深底上的抗锯齿）：阈值取 `matchRate ≥ 0.99`，别把阈值调到"一个像素都不能差" |

> ⚠ **首次生成基线时要人工看图**。基线一旦错误地生成，之后它会一直"通过" —— 那还不如没有。
> 运行器会明确提示这一点。

### 14.4 现在覆盖什么

`001` 基础三标签 / `002` 单标签全部状态（激活·固定·静音·播放·加载·无痕）/
`003` 展开的标签组（含下划线与成员标记）/ `004` 折叠的标签组 /
`005` 溢出收缩 / `006` 深色主题下的混合形态 /
`007` **装饰层**（`decorations: true` 的 case 会注入一对测试装饰器，走的是与真实插件
完全相同的那条路：宿主端口 → `appendDecoration`）。
`007` 同时带一个 `decorationCount` 度量 —— 只比像素的话，"装饰没挂上"和
"挂上了但被裁掉"长得一模一样。

## 15. 运行时插件：社区市场的加载 · 安装 · 插件源（**主链路已落地**）

### 15.1 统一运行时加载

第一方插件由构建脚本预编译成独立 ESM，第三方插件由安装器落盘；两者都通过
`hira-plugin://` 特权协议加载。加载器不再依赖 Vite 的 `import.meta.glob`，
因此壳层、面板进程和静态内部页共用同一份规则。

```
manifest.render ──→ import(`hira-plugin://<id>/<file>?v=<mtime>`)
                                          │
                                          ├─ 只服务**当前已启用**的插件（禁用即失效）
                                          ├─ URL 锁在该插件自己的目录内（目录穿越 403）
                                          └─ 扩展名白名单（笔记/密钥等非资源文件 403）
```

### 15.2 安装 = 往 `userData/plugins` 放一个**目录**

```bash
<userData>/plugins/<plugin-id>/
  hira-plugin.json      # 必须；trustLevel 得是非 internal/core（否则按第一方对待）
  main.cjs              # 主进程入口（第三方走沙箱）
  ui.renderer.js        # 可选的渲染侧入口
  ...                   # 其余是它自己的资源
```

两条刻意的设计：

| 决定                                                     | 理由                                                                                                                                           |
| -------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| 用户插件**单独一个目录**，不与内置混放                   | 应用目录打包后只读（asar / Program Files）；且卸载/更新应用**绝不能**抹掉用户装的东西                                                          |
| **目录形态**（一个插件一个子目录），不像内置那样扁平铺开 | 第三方插件的代码 + 图标 + 许可是一整套资产，要能整体安装/卸载，也要能在目录级锁住（协议层的前缀判断就建立在这一点上）                          |
| id 撞名时**内置优先**                                    | 让用户那份胜出 = 允许用一次安装替换掉 `tabs-service`，那是提权不是扩展。撞名的那份被忽略并告警（不报错：用户装了个重名插件不该让浏览器起不来） |

插件的"信任级"完全由 manifest 的 `trustLevel` 决定，不由它自声明能力：
非 `internal` / `core` 即第一方之外 → 走沙箱、`requestedPermissions` 必须逐条授权、
`permissionLevel: "full"` 会被强制回落 `ui`（见 §11）。

### 15.3 三道安全边界（都在 `main/plugin-protocol.js`）

| 边界             | 处理                                                   | 不做的后果                                                                |
| ---------------- | ------------------------------------------------------ | ------------------------------------------------------------------------- |
| **目录穿越**     | `path.resolve` 之后做前缀比较                          | 一个 `../../` 就能把磁盘上任意文件喂给页面                                |
| **扩展名白名单** | 只放行 js/css/json/图片/字体                           | 插件目录里可能还躺着作者的笔记、`.env`、密钥 —— 全部暴露给页面            |
| **仅已启用**     | `getPluginRoot` 只对 `enabled === true` 的插件返回路径 | "禁用"只摘掉了 provider，插件代码照样还在页面里跑（"假生效"的另一种形态） |

外加单文件 2MB 上限（不让一个畸形 URL 把渲染进程内存吃光）与 `Cache-Control: no-store`
（缓存失效交给 URL 上的 `?v=<文件 mtime>`，而不是让浏览器自己猜）。

**`?v=` 是这套设计的支点**：URL 变了 → 浏览器模块映射必然重新加载；没变 → 正常命中缓存。
所以"作者改了渲染代码"必定生效，而热重载（§12.4）也不必额外做缓存失效。

### 15.4 URL 形状只有一处权威

`hira-plugin://<id>/<file>?v=<mtime>` 由 **APPS 的协议层**拼（`buildPluginAssetUrl`），
随 `plugins:list` 以 `renderUrl` 下发，渲染层只管 `import(item.renderUrl)`。

不在渲染层拼的理由：那样 URL 形状就有了两份实现，改动时必然漂移 ——
而漂移的表现是"作者改了代码但页面还是旧的"或"插件 UI 整个加载不出来"，都极难查。

### 15.5 安装器（`install` / `uninstall`，**已落地**）

"安装"= 把一个插件的资产**安全地**放进 `userData/plugins/<id>/`。它拆成两个互不知道对方的模块：

| 模块                       | 管什么                                                             | 为什么这样切                                                                                                                                      |
| -------------------------- | ------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| `main/plugin-installer.js` | 体检 / 复制 / 覆盖 / 卸载 / 签名验签                               | **纯文件系统 + crypto**，不认识 Electron、不认识注册中心 → 可被单独跑（`pnpm verify:plugin-install`）。"装完起不来"这类问题不必等整机跑起来才暴露 |
| `main/plugin-archive.js`   | 读 zip（只解压，不压缩不加密）                                     | 主进程的依赖会进每一个安装包；为一个"读一次 zip 就完了"的动作引一个上万行的库不划算                                                               |
| `ipc/plugins.js`           | 两者的**粘合**：装完 `discover()` + `enable()`；卸载先停用再删文件 | 注册中心只认识目录、不认识"安装"这个词                                                                                                            |

**四条安全边界**（每条都对应一种真实事故）：

| 边界                                  | 处理                                                                                   | 不做会怎样                                                                 |
| ------------------------------------- | -------------------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| 解压/复制时的**目录穿越**（zip-slip） | `resolveInside`：**两侧都 `path.resolve` 之后比前缀**（不是过滤 `..`）                 | 条目名写 `../../` 就能写到 `userData` 之外，甚至覆盖应用自己的文件         |
| **符号链接**                          | 用 `lstat` 识别并跳过（不跟随）                                                        | 源目录里一条指向 `C:\Windows` 的链接，会让"复制一个目录"变成"复制整台机器" |
| **与内置插件撞名**                    | 安装前直接拒绝；内置名单从**磁盘**读（`readBuiltinPluginIds`），不维护一份会过期的名单 | 允许用一次安装替换掉 `tabs-service` —— 那是提权                            |
| **体积上限**                          | 2000 个文件 / 64MB                                                                     | 一个"插件包"如果有 20 万个文件，它不是插件包                               |

**落盘是"先暂存再换名"**：源复制到 `plugins/.install-*`，体检通过后才 `rename` 成 `plugins/<id>`，
旧的那份先改名为 `.old-*` 再删。中途失败（磁盘满 / 文件被占用）不会留下"半份"，而半份是最糟的状态
——**它看起来是装好的**。

⚠ 与之配套的一处基础设施改动：`PluginRegistryV2#scanPluginDir` 现在**跳过点开头的目录**。
不跳过的话，一次被中断的安装留下的 `.install-<id>/`（里面带着完整 manifest）会被当成插件扫到，
而它先被扫到就**顶掉**真正的那个 —— 那是"插件偶发加载成旧版本"这种查不出来的怪现象。

### 15.6 签名：能验，但"信任谁"由用户决定

manifest 可选 `signature: { algo, keyId, value }`：

```
algo    ed25519 | rsa-sha256
keyId   公钥标识，对应 <userData>/plugin-trust/<keyId>.pem
value   base64 签名，签的是**去掉 signature 字段后递归按键名排序的 JSON**
```

顺序必须规范化，否则"字段顺序不同"会让同一个 manifest 验不过 —— 这类问题在真实发布里
一定会出现（不同工具重新序列化一遍就变了）。

四种结果**分开呈现，绝不合并成"没签名"**：

| 状态          | 含义                                                 | 安装                                             |
| ------------- | ---------------------------------------------------- | ------------------------------------------------ |
| `none`        | 没有签名                                             | 允许                                             |
| `unknown-key` | 有签名，但本机没这把公钥                             | **允许**（社区生态不该被一把没配好的钥匙卡住）   |
| `valid`       | 验签通过                                             | 允许，UI 提示"签名已校验"                        |
| `invalid`     | 验不过（内容被改过 / 算法不支持 / keyId 含路径字符） | 允许，但 UI 明确提示"签名校验未通过，请谨慎使用" |

`unknown-key` 与 `invalid` 必须分开：前者是"我还没决定信不信这个人"，后者是
"这个人签的东西被改过"。合并成一句会让最该被看见的那种情况淹没在噪音里。

> 这是**验签**，不是完整的信任链：`plugin-trust` 里放哪几把公钥由用户决定 ——
> 但"放进哪几把"这件事**有界面**（插件中心的「受信任的签名公钥」区：导入 / 列出指纹 / 移除），
> 否则这个能力对普通用户等于不存在（那个目录藏在 `userData` 深处）。

#### 公钥的**三级信任分级**（已落地）

公钥按**存放位置**分三级，级别既是"谁放的"，也是**查找优先级**：

| 级别        | 目录                                | 从哪来                             | 可写                       | 可移除   | 验签结果带的 `level` |
| ----------- | ----------------------------------- | ---------------------------------- | -------------------------- | -------- | -------------------- |
| `official`  | `<appRoot>/resources/plugin-trust/` | 随应用一起分发                     | **不可**（运行时拒绝写入） | **不可** | `official`           |
| `community` | `<userData>/plugin-trust/`          | 界面导入的作者公布公钥（默认级别） | 可                         | 可       | `community`          |
| `local`     | `<userData>/plugin-trust/local/`    | 用户自己生成 / 开发自用            | 可                         | 可       | `local`              |

几条设计取舍：

| 决定                                                  | 为什么                                                                                                                     |
| ----------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| **用「目录」而不是一份 `trust.json` 清单**            | 目录即事实。清单与文件一旦不同步，"这把钥匙到底算不算数"就变成要看两份数据才能回答的问题 —— 而用户只会看到"签名忽然失效了" |
| `official` 级**既不可写也不可移除**                   | 这才是"官方签名"的含义。允许用户误删，等于官方签名可以被一次右键操作搞没                                                   |
| 同名公钥**按级别优先**取最高那级                      | 优先级就是分级存在的意义：作者自己放了一把同名钥匙，不该顶掉随应用分发的那把                                               |
| 同名公钥**已在更高级别 → 导入被拒**，且说明优先级顺序 | 否则用户会以为"导入成功了但没生效"。给的是可执行的动作（先移除那把，或改用同一级别）                                       |
| 导入 / 移除**必须带 `level`**                         | 不同级别允许同名，只给 `keyId` 无法确定动的是哪一个                                                                        |

`findTrustedKey(keyId)` 按 `official → community → local` 顺序查，并挡住 `keyId` 里的路径字符
（否则一个坏 manifest 就能读任意 `.pem`）。三级**都能验签** —— 分级只决定优先级与可写性，
不决定"能不能用"；否则分级就只是个摆设。

自动更新仍**不做**（见 §15.10）。

### 15.7 插件源（社区市场的**索引那一半**，**已落地**）

前两节解决了"装什么、怎么装"；这一段解决"**从哪知道有什么可装**"。
索引就是一个**静态 JSON**（任何静态托管都能放），所以这一层**不需要自建服务端**：
作者把索引与若干 zip 丢上去，用户填一个地址就能浏览 / 一键安装 / 一键更新。

```json
{
  "schema": 1,
  "name": "示例插件源",
  "plugins": [
    {
      "id": "acme-demo",
      "name": "Acme 演示插件",
      "version": "1.2.0",
      "description": "…",
      "author": "…",
      "homepage": "https://…",
      "url": "https://…/acme-demo-1.2.0.zip",
      "sha256": "…"
    }
  ]
}
```

#### 多源聚合（**已落地**）

源是**一个列表**（不是单个地址），最多 20 个。几条语义是刻意定死的：

| 语义                                                                            | 为什么                                                                                                                                                  |
| ------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **顺序即优先级**                                                                | 同一个 `id` 出现在多个源里时，**排在前面的源胜出**并计入 `duplicates`。让两个源的版本互相覆盖（谁后到谁赢）会产生"刷新两次结果不一样"这种最难复现的问题 |
| **一条源失败只影响它自己**                                                      | 并发拉取，逐条回报 `sources[] = [{ url, ok, name, reason, cached, skipped, count }]`。否则用户面对 3 个源只得到一句笼统的失败，完全不知道该改哪一个     |
| 只有**所有**源都失败时顶层 `ok` 才是 `false`，并把各源原因**拼起来**当 `reason` | "有一个能用的源" ≠ 失败。但真全挂时，必须有一句话能说清是哪些源、各自为什么                                                                             |
| 缓存**按 URL 分桶**（`Map<url, {at, data}>`）                                   | 增删某一个源只作废它自己那份；保留的源仍走缓存，不因为改了一行配置就全部重新出网                                                                        |
| 拉取用 `Promise.all`（不是 `allSettled` + 早退）                                | 每个源自己已经兜住异常并返回 `{ok:false}`，不需要第二层兜底；而"等齐再合并"是必须的 —— 否则条目顺序会随网络快慢变化                                     |
| 源**整表提交**（`marketSetSources`），不是 add/remove 两条 IPC                  | 顺序即优先级，所以顺序也必须能被设置 —— 那只有"整表提交"这一种语义是对的。拆成两条会让"两条相继失败"产生一个界面上看不到的中间态                        |

**源内搜索是纯前端的**（面板侧对 `entries` 做大小写不敏感的子串匹配，命中 `name` / `id` /
`description` / `author`）：搜索**不该出网**。把它做成一次远端查询，等于每敲一个字符就
发一次请求，而且结果依赖那一次请求的成败 —— 用户会看到"搜着搜着列表空了"。
本地过滤还有个副作用是好的：搜索**跨源**（不需要用户先想"这个插件在哪个源里"）。

#### 这个模块**不做**的三件事（比它做了什么更重要）

| 不做                       | 理由                                                                                                                                                    |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **不绕过安装器的任何一道** | 下载下来的包一律走 `installer.installArchive` —— 体检、撞名、zip-slip、扩展名白名单、签名一个都不少。"从市场装的"不是一种更可信的来源，只是更省事的来源 |
| **不自动信任索引**         | 索引是远端数据：`id` 要过安装器同一套字符集，`url` 要过协议白名单（`https:`，或 `http:` **仅回环**）。一个坏索引不该能让主进程去下载任意 URL            |
| **不自动更新**             | 它只回答"有哪些更新可用"，装不装是用户点的                                                                                                              |

#### 几条实现上的硬要求

| 要求                                               | 为什么                                                                                                                                                            |
| -------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 下载地址跟随重定向后**复核最终协议**               | 否则一个 https 索引可以把你导去 http（甚至 file）—— 白名单形同虚设。这条教训在 favicon 代理那里已经踩过一次                                                       |
| 索引 1MB / 包 64MB，**流式读 + 封顶**              | 远端响应不能无上限地进内存；超限立刻 `cancel()` 断开                                                                                                              |
| 超时 15s（`AbortController`，不是 `Promise.race`） | 只有前者能真正掐掉连接；一个卡住的源不该让插件中心永远转圈                                                                                                        |
| 坏条目**逐条跳过**并回传 `skipped`                 | 一条笔误不该让整个源"打不开"，作者在几百条里找那一处会疯                                                                                                          |
| 索引声明的 `sha256` **必查**（不符即丢弃并说明）   | 这是"从市场装"相对"自己下载"多出来的那道保证。没声明的仍可装，但 UI 会标"未提供校验和"                                                                            |
| 下载到 `os.tmpdir()` 的临时文件，**成败都清**      | 失败不污染插件目录；成功也不该把别人的代码留在临时目录里越积越多                                                                                                  |
| 60s 短期缓存 + `force` 绕过                        | 面板每次刷新都出网是浪费；但用户点"刷新"必须是真刷新                                                                                                              |
| 版本比较 = **字符串不等**（不是 semver）           | 两个版本号来自本地 manifest 与远端索引，格式由作者决定。拿 semver 规则去比非 semver 字符串会得出"永远有更新/永远没更新"这类静默错误；字符串不等至少是**可解释**的 |

**更新为什么走 `reload()` 而不是 `enable()`**：`enable()` 对已启用的插件是**空操作**
（状态已是 enabled）→ 新代码永远不会被加载，表现是"更新成功了，但插件还是旧行为"。
`reload()` 才是"停干净 → 丢模块缓存 → 重读 manifest → 重新编译 → 重挂"。
所以安装后的统一收尾会**先取证**（`wasKnown` / `wasEnabled` / `wasUserDisabled`）再决定动作；
用户**主动关掉**的插件，更新之后也不会被顺手打开。

### 15.8 界面（插件中心）

| 入口                        | 行为                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| --------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 从文件夹安装 / 从压缩包安装 | 主进程**弹系统选择框**（渲染层不碰任何本地路径 API）；取消**不算失败**（不弹红字）                                                                                                                                                                                                                                                                                                                                                                         |
| 打开插件目录                | 安装失败的兜底路径 —— 用户始终能自己看一眼、手工放一份                                                                                                                                                                                                                                                                                                                                                                                                     |
| 行尾「卸载」                | **只对 `runtime === true` 的插件出现**（资产来自用户目录）。内置 / 不可禁用的插件连按钮都不给（主进程也会拒，但界面不该提供做不到的动作）。二次确认，且框里写插件名而不是 id                                                                                                                                                                                                                                                                               |
| 受信任的公钥区              | 列出三级 `plugin-trust` 里的公钥（**显示指纹而不是整段 PEM** —— 指纹是用户能拿去和作者公布值核对的那串），每条带**级别徽标**（官方 / 本地与默认级别视觉上分开）；导入时**选级别**（下拉只有 `community` / `local` —— 官方级不是能在这里写的东西），`official` 级**不出现移除按钮**（主进程也会拒，界面不该提供做不到的动作）。解析失败的 `.pem` 也会列出来并标红：它是"签名为什么不生效"的唯一解释                                                         |
| 插件源区                    | **源列表**（每条：地址 + 它自己的拉取状态 + 移除按钮；坏源只标红它自己）+ 一个添加框（回车即添加）+ 一个**搜索框**（纯前端过滤，跨源）。下面是合并后的插件列表：每个条目显示名称/版本/作者/简介与**来源源名**，主操作按钮是 `安装` / `更新` / `重装`。三种状态分开呈现：**未配置**（不是错误）/ **拉取失败**（红字说原因）/ **有结果**。被跳过的坏条目数与**同 id 撞车的条目数**（`duplicates`）都会显示 —— 作者少打一个字符，症状是"我明明发布了却没显示" |

> ⚠ 顺手修掉一个真 bug：插件中心原来在 `createPluginsPanel` 里直接调了一个**并不存在的自由变量**
> `pluginsClient`（模块作用域里没有它，只有 `mount` 里才有一个同名局部变量）→ 点"打开插件目录"
> 必抛 `ReferenceError`。哑组件的价值正在于此：外部能力只能从 `onIntent` 这一个口进来，
> 就不会再出现"随手引一个外部对象"的漏子。

`verify:plugin-publish` 的价值不在"再测一遍各层"，而在**测它们连起来对不对**：
三段各自绿、合起来坏，是发布链路上最典型的失败形态 —— 而且它只有在**作者机器上**才
暴露得出来（用户那边只会看到"装不上"）。它跑的就是真实链路：`plugin:publish` 打包 →
本地 http 托管 → `plugin-market` 拉索引安装 → 安装器验签；作者签名与用户验签
用的是**同一份** `canonicalBytes`。写这条验证时当场抓出一个真 bug：
`--no-write-manifest` 会把自己刚算好的签名丢掉（打成"不带签名"的包）。

`verify:plugin-install` 自带一个**最小 zip writer**，因为最需要测的那条边界是 zip-slip ——
而系统自带的压缩工具**造不出**那种包。"造不出攻击样本"意味着那条防线永远没被验过。

它覆盖：体检七种不通过的情形 / 目录穿越守卫的前缀判据 / 覆盖安装真的换新且不留残留 /
zip 的 store+deflate+目录项 / ZIP64 哨兵明确报错 / **zip-slip 后确认沙箱外真的没落文件**
（不能只看返回值）/ 签名四态 / `keyId` 路径字符 / 符号链接与 `node_modules` 被跳过 /
从插件目录内部安装被拒 / 卸载的三种失败 / 公钥的导入（非公钥被拒、同名不覆盖）、
列出（指纹与算法、坏文件标红）、移除（**移除后验签回落到 `unknown-key` 而不是 `invalid`**）、
以及**三级信任分级**（默认级别 / `local` 落子目录 / `official` 拒绝写入 / 官方优先于社区 /
同名已在更高级别时导入被拒并说明优先级 / 三级都能验签）。

> 同一个脚本还顺手修掉了一处**环境陷阱**：`ELECTRON_RUN_AS_NODE` 必须**删掉**而不是设成空串 ——
> Electron 判定的是"这个键在不在"，设成 `''` 仍会被读成 node 模式，于是它带着自己的 node 快照
> 初始化 V8 并断言崩溃（退出码 134，堆栈全在 V8 里，完全指不到真正原因）。

### 15.11 设置页（静态内部页；仅入口模块按需打包）

#### 现状：它就是一个普通内部页

|          |                                                                                         |
| -------- | --------------------------------------------------------------------------------------- |
| 源码     | `apps/app-main/src/pages/settings/`（`index.html` + `settings.js` + `settings.css`）    |
| 构建     | 登记进 `SOURCE_BUNDLED_PAGES`；只把 `settings.ts` 的模块图打成一个 ESM，HTML/CSS 仍原样分发 |
| 注册     | 协议层的**磁盘发现**自动注册，`main/hira-protocol.js` 里**没有任何** settings 特例      |
| 页面只认 | preload 桥 `window.hira`、`settings:*` IPC、共享插槽宿主、自己的 CSS                    |

页面本身**不认识任何具体设置项**：分区与字段来自主进程 `settings:schema`（功能模块通过
`registerSettingsSection` 注册），值走 `settings:list`，写入走 `settings:set`，
外部变更经 `settings:changed` 同步 —— 业务逻辑全在 domain / applier 层。
页面仍注册为 `hira://settings` 普通静态内部页；`bundleSourcePagesPlugin` 只解析 HTML 里的
一个入口并从源码打包。产物直接写回 `out/pages/settings/settings.js`，不改变协议路由，
不引入 Vite dev/prod 双形态映射，也不把页面变成 renderer 窗口。

#### 回退记录：为什么曾经迁进 Vite renderer，又为什么退回来

迁的动机只有一个：`settings.custom-widget` 是 46 个官方插槽里**唯一**要求宿主页面
**能跑插件渲染代码**的（控件要返回 DOM、挂事件、读 `window.hira`）。而那条加载链
（`plugin-slots.js` → `plugin-renderer.js`）要吃打包器的 `import.meta.glob`，
静态页喂不了 —— 于是把设置页整个变成 `electron.vite.config.js` 的一个 renderer 入口。

**退回来的原因：这条路要在协议层替一个页面开特例，而且特例还很难写对。** 三条坑全部
只在真机才暴露，留档如下（下次谁想再走一遍，先看完这三条）：

| 坑                                                | 现象                                                                           | 真相                                                                                                                                                                                                                                                                                                                                                                     |
| ------------------------------------------------- | ------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Vite 产物是**相对引用**，而 `..` 跨不过 host 边界 | `hira://settings/../assets/x.js` 被 URL 规范化成 `hira://settings/assets/x.js` | 必须"目录 + `/assets/` 前缀"两段映射，等于给通用协议层塞一个页面专属分支                                                                                                                                                                                                                                                                                                 |
| dev 下产物只在内存里 → 只能**反代**               | 反代要抹平三道口径差                                                           | ① 根绝对路径（`/@vite/client`、`/@fs/…`）能直接对上；② 相对引用（`./main.js`、`./settings.css`）要注入 `<base href="/settings/">`，否则落到 renderer 根的占位 `main.js`、或落到 SPA 兜底拿到一份 HTML；③ **请求头必须转发** —— Vite dev 按 `Accept` 决定 CSS 给的是原始 CSS 还是**编译成 JS 模块**的那份，漏了就是"页面出来但全无样式"，而 JS 照跑、完全看不出是代理的锅 |
| "404 就回退到另一个前缀"这种兜底**不可用**        | dev server 对未知路径 **SPA 兜底返回 200 HTML**                                | 兜底分支永远不触发，只会静默服错文件（`./settings.css` 拿到一份 HTML）                                                                                                                                                                                                                                                                                                   |

结论：为一个页面把通用协议层改成"能识别 Vite dev/prod 两种产物形态"，收益（1 个插槽）
远小于代价（协议层多一类特例 + dev 反代 + 三种失效模式）。**设置页退回静态页。**

#### 最终接线：统一加载器 + 薄宿主

`plugin-renderer` 已移除 `import.meta.glob`，所有渲染入口都由主进程下发的
`renderUrl` 经 `hira-plugin://` 动态加载；缓存键包含版本化 URL，热重载不会复用旧模块。
设置页只做三件事：

1. `defineRendererSlots(['settings.custom-widget'])`，再 `activateRendererSlots()`；
2. 按当前分区调用每个实现，把结果放进宿主统一生成的插件卡片；
3. 内容重建前派发 `hira:dispose`，并订阅 `plugins:changed` 触发重新激活。

`SOURCE_BUNDLED_PAGES` 只负责让静态页拿到 `plugin-slots` / `plugins-client` 的共享实现。
这条方式也可由其他内部页直接复用，不需要改 `hira://` 协议层。

#### `settings.custom-widget` 的契约（MULTI）

实现收到 `{ section }`（当前分区 id），返回：一个 `HTMLElement` / `{ title?, blurb?, element }` /
数组 / `null`（**这个分区我不参与**，最常用）。挂载粒度是**每插件一张卡** ——
否则两个插件的控件混在一个框里，用户分不清哪块是谁加的。

两条硬约束：

| 约束                                                                       | 为什么                                                                                                                                            |
| -------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| 切分区会整体重建 → 宿主每次重挂，并在摘掉旧节点前给元素派发 `hira:dispose` | 插件清定时器 / 断开订阅的唯一时机。不用 MutationObserver 让插件自己盯着：那要求每个插件都懂宿主的重建时序，而"什么时候该收尾"是宿主知道得更准的事 |
| 插件抛错不能拖垮设置页                                                     | 控件挂不上只是少一块卡片，设置项必须照常可用                                                                                                      |

#### 与 `settings.section-renderer` 的对照（别混）

|          | `settings.section-renderer`（主进程）                                   | `settings.custom-widget`（渲染侧）        |
| -------- | ----------------------------------------------------------------------- | ----------------------------------------- |
| 实现在哪 | 主进程                                                                  | 插件的 `.renderer.js`                     |
| 产出什么 | 一个**描述符**（字段声明），设置页按内建控件类型画                      | 插件自己返回 **DOM 并挂事件**             |
| 能画什么 | 内建类型（toggle / select / text / number / directory / action / list） | 任意                                      |
| 成本     | 零（不需要渲染入口）                                                    | 需要 `render` 入口                        |
| 何时用   | 只是"给某个分区加一个设置项"                                            | 需要自绘控件（调色板、预览、列表编辑器…） |

#### 验证：`pnpm verify:settings-page`

设置页踩坏的地方全都**只在真 Chromium 里才看得见**，所以这条冒烟刻意加载 `out/` 里的
**构建产物**（不是 `src/` 源码）—— 要验的就是"构建出来的东西能跑"。

覆盖：`hira://settings` 返回 200 / **HTML 里每一个 src·href 都能取到**（这条直接证明磁盘分发对了）/
真窗口里加载的确实是设置页 / DOM 渲染出导航·标题·卡片·控件且控件反映了值 /
CSS 真的生效（不是"有 DOM 无样式"）/ **零 console 错误**。

> 脚本里的「⑥ `settings.custom-widget` 端到端」当前仍待恢复。宿主已经接通，
> 恢复时只需造一个带 `rendererSlots: ['settings.custom-widget']` 的临时插件，
> 断言卡片挂载、分区切换后收到 `hira:dispose`、禁用插件后卡片消失且无残影。

> 写这条冒烟时在**渲染进程**里 `fetch('hira://…')` 探资源，全部报
> `URL scheme "hira" is not supported`，于是当时得出了「渲染进程 Fetch API 不支持自定义
> scheme」的结论，改用**主进程的 `net.fetch`**。
>
> **这个结论是错的，而且掩盖了一个真 bug**（2026-10 查清）：Electron 的
> `protocol.registerSchemesAsPrivileged()` 是**覆盖语义** —— 后一次调用会把前一次的整份
> 清单替换掉。当时 `main.js` 顶层有五个模块各调一次（`hira` → `hira-game` →
> `hira-plugin` → `hira-theme` → `hira-pwa`），最终**只有最后一个 `hira-pwa` 是特权的**，
> 其余四个全部退回「未登记」：渲染进程 `fetch()` / `import()` 一律报上面那句，而
> `protocol.handle()` 明明好的（导航、图片照常）—— 所以看起来像"fetch 不支持自定义 scheme"。
>
> 同一个 bug 的直接受害者是 HTML / XAML 面板：入口 `fetch()` 失败 → `panel-ui-frame`
> 走到失败态 → 面板白屏。
>
> 修法：**全库只有一次** `registerSchemesAsPrivileged`，清单收在
> `apps/app-main/src/main/scheme-privileges.js#SCHEMES`（`registerAppSchemes()`）。
> 新增协议 = 往那张表加一行，不要再单独调那个 API。
>
> **教训**：看到"某个 Electron 能力不支持"时，先怀疑**登记方式**（权限是全局、一次性、
> 覆盖语义的），再怀疑能力本身。验证脚本仍建议用 `net.fetch`（不依赖页面 origin），
> 但它**不再是唯一可行路径** —— 渲染进程的 `fetch()` 在 scheme 登记正确时是能用的。
