## 一、自动填充（补全）核心引擎

NG 在 [password-autofill.js](file:///e:/Desktop/OTHER/1A-STAR_Hira/1A-STAR_Hira_NG/infra/infra-window/preload/password-autofill.js) 中的实现比 Hira [passwordFill.js](file:///e:/Desktop/OTHER/1A-STAR_Hira/js/preload/passwordFill.js) 薄弱很多：

**字段识别精度**

- NG 关键词表极小：username 13 个、password 8 个，且只查 4 个属性（`name/id/placeholder/aria-label`）。
- Hira 关键词表 35+/14+ 个，查 6 个属性（含 `formcontrolname`、`autocomplete`），还支持中文关键词全量（用户名/帐号/手机号等）。
- NG 无 OTP 排除逻辑，`isUsernameLikeField` 会把邮箱/手机当用户名；Hira 有 `isLikelyOneTimeCodeField` 排除验证码/OTP/2FA。
- NG 只取"第一个命中字段"，无评分；Hira 用 `scorePasswordField`/`scoreUsernameField` + 同 form 加权，选字段更可靠。
- NG 不做刷新缓存/动态表单监听；Hira 有 `MutationObserver`（`startCredentialFieldObserver`）处理 SPA/动态渲染的登录表单。

**多凭据选择 UI**

- NG 用浏览器原生 `prompt()` 让用户手输索引——几乎不可用。
- Hira 用独立 BrowserWindow 原生密码填充菜单（`openAutofillNativeMenu` + `show-password-fill-menu`），锚定在输入框左下角，用户体验完整。

**填充与覆盖保护**

- NG 只派发 `input/change`，Hira 派发 `keydown/keypress/keyup/input/change` 并用 `InputEvent('insertReplacementText')`，兼容性更好。
- NG 填充后无高亮、无"覆盖保护"；Hira 有 `applyAutofillHighlight`（字段高亮）+ 拦截 `beforeinput/paste/compositionstart`，防止用户手动输入时与自动填充冲突清空。

**iframe / 路由 / 安全**

- NG 用 `window.location.hostname`，无法识别 iframe 域名与顶层不一致；Hira 用主进程传回的 `frameURL` hostname。
- NG 无 origin 校验、无路由变化（pushState/hashchange）清除 autofill UI；Hira 两者都有。
- NG 无快捷键触发（Hira 有 `keybindings.defineShortcut('fillPassword')`）；NG 无 `password-autofill-enabled` 握手，钥匙图标在后端不可用时也照常显示。

## 二、密码捕获与提示

NG [ui-password-manager](file:///e:/Desktop/OTHER/1A-STAR_Hira/1A-STAR_Hira_NG/ui/ui-password-manager/src/index.js) 的捕获条 vs Hira [passwordCapture.js](file:///e:/Desktop/OTHER/1A-STAR_Hira/js/passwordManager/passwordCapture.js)：

- **捕获时机单一**：NG 只在 `submit` + 按钮 click；Hira 覆盖 JS 表单（拦截 `HTMLFormElement.prototype.submit`）、Enter 键盘、`pagehide/beforeunload`。
- **登录按钮识别弱**：NG 只认 `BUTTON/INPUT` 且文本仅 login/sign/submit/登录；Hira 识别 `role=button` div，并支持 sign in/continue/next/登陆/提交/确定/下一步等多语言。
- **无 lastTyped 回退**：登录成功后密码框被清空时，Hira 用 `lastTypedCredentials`（120s 内）回退补全 username/password 再捕获；NG 会捕获失败。
- **存在性去重**：Hira 在 `saveCredential` 前后对比凭据已存在则不弹条；NG 只按 username 判断，且主进程侧未做完整去重。
- **交互形态**：NG 是网页内 fixed 卡片覆盖内容；Hira 用独立捕获栏 + `webviews.adjustMargin` 在网页底部预留边距，不遮内容。
- **本地化**：NG 文案硬编码中文；Hira 全部走 `l('xxx')` i18n。

## 错误页语义契约（地址栏 / 刷新 / 休眠）

错误页 `hira://error?...` 是**过渡视图**，不是用户要访问的页面。它出现时网络请求已经失败，用户心智里的“当前页面”仍是那个**失败的原网址**——输入框里是它、刷新想重试的是它、关掉再打开期望回到的也是它。这条契约把该心智固化到所有消费方，避免每个入口各写一份 `wc.reload()`。

### 契约四条

1. **地址栏显示原网址**：错误页期间 `t.url` 不被覆盖成 `hira://error?...`，地址栏（读 `tabSession.getActiveTab().url`）因此始终是失败地址。
2. **刷新 = 重试原网址**：任何“刷新”入口在错误页上都必须 `loadURL(失败地址)`，而不是 `reload()` 错误页；普通页才走原生 `reload()`。
3. **休眠不记录错误页**：休眠快照里的 `url` 写成失败地址，并从 `navHistory` 中剔除错误页条目，唤醒后不会“还原出一张错误页”。
4. **错误页不写导航历史投影**：`did-navigate` / `did-navigate-in-page` 双向守卫，错误页自身的 `replaceState` 也不会污染 `t.url`。

失败地址的权威来源是标签的 `t.error.url`（`handleLoadFailure` 写入、成功导航清空）；只有当宿主没有记录时才从错误页 URL 的 `url` query 解析兜底。

### 唯一实现：[page-reload.js](file:///e:/Desktop/OTHER/1A-STAR_Hira/1A-STAR_Hira_NG/infra/infra-window/src/page-reload.js)

| 导出 | 语义 |
| --- | --- |
| `retryUrlOf(wc, fallbackUrl)` | 当前在错误页 → 返回要重试的地址；否则 `''` |
| `reloadOrRetry(wc, fallbackUrl, { ignoreCache })` | 错误页 → `loadURL(原网址)`；普通页 → `reload()` / `reloadIgnoringCache()`；返回 `'retry' \| 'reload' \| 'noop'` |

`ignoreCache` 只影响普通页；错误页没有缓存可绕过，重试分支两者一致。

### 消费方（全部同源）

- 标签刷新 / 强刷：[TabManager#reload / #forceReload](file:///e:/Desktop/OTHER/1A-STAR_Hira/1A-STAR_Hira_NG/infra/infra-window/src/TabManager.js#L2464-L2500) → `_reloadTab` → `retryUrlOf` + `navigate`（走完整导航链，含休眠唤醒）。

- 独立侧栏：顶条 `command('reload')` / `command('reload-hard')`、右键菜单、视图模式切换前的重载，全部走 `reloadOrRetry(wc, state.url)`；`state.url` 本身有 `isWebErrorUrl` 守卫，永远不会被错误页覆盖。

### 已知取舍与边界

- `loadURL('hira://error')` 会计入 `webContents.navigationHistory`（Electron 没有“替换历史项”API），因此后退栈里可能残留一条错误页。缓解手段是上面的快照清洗与事件守卫；不尝试伪造历史。
- 内部面板（`WebContentsManager#reloadPanel`）承载的是应用自己的页面，不存在“失败原网址”，保持原生 `reload()`。
- PWA 窗口早已有 `errorUrl` + `getRetryUrl` 的等价实现（`pwa/window.js`），本次不改，仅保持语义一致。
