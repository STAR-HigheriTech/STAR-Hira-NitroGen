# 浏览器「一键迁移」调研与落地方案

> 目标：搞清楚 Tabbit / Chrome / Edge 这类浏览器是怎么做到「点一下就把握在用的 Chrome、Edge 数据搬过来」的，
> 并对照 Hira 现状给出可落地的模块化方案。
>
> 可信度标注：✅ = 已读源码或官方文档；⚠️ = 业界通用实现 / 媒体实测，落地前需自测。

---

## 1. 结论先行

1. **Tabbit 确实存在**（美团光年之外，Chromium 内核，Windows 10+/macOS，2026-03 公测）。它的迁移入口在**首次启动引导**里，
   一次带走书签、密码、历史、扩展，主打「切换成本 ≈ 0」。（⚠️ 媒体实测口径一致，但没有官方技术文档）
2. **一键迁移不是「打开对方的数据目录读文件」这么简单**，它是一条五段管线：
   `发现（装了且用过） → 拷副本（源库被锁） → 解析（各格式） → 解密（DPAPI/OSCrypt/NSS） → 幂等写入（去重）`。
3. **Chromium 的 importer 模块在 Electron 里拿不到**。它在 `chrome/` 层、跑在沙箱 utility 进程里，还绑定 profile 与 mojo。
   Electron 应用必须自建这条管线 —— 好处是可以做得比它更贴合自己的数据模型。
4. Windows 上「发现浏览器」的主判据**不是注册表**：注册表只证明「装过」，`User Data\Local State` + 一个真正有数据的
   profile 才证明「用过」。用后者当主判据，能天然跳过「装了但没登录过」的机器。
5. **书签 / 历史 / 自动填充 基本 100% 可导**；**密码 / Cookie 要分级**：Edge 与其它 Chromium 系（同一 Windows 账户下）可解，
   **Chrome 127+ 的 App-Bound Encryption（`v20` 前缀）会让第三方进程解密失败**。必须把「不可解密」当成正常结局来设计，而不是异常。

## 2. Tabbit 的做法（二手）

| 项 | 内容 | 可信度 |
| --- | --- | --- |
| 入口 | 首次启动引导流程内，不在设置页 | ⚠️ 实测 |
| 一次带什么 | 书签、密码、浏览记录、扩展（Chrome 扩展直接可用） | ⚠️ 实测 |
| 自动检测 | 自动识别 Chrome / Edge / Safari | ⚠️ 单一来源 |
| 叙事 | 用「你原来的浏览器」而不是「源数据」，把迁移说成「继续用」，不是「导入」 | ⚠️ 产品观察 |

**能确定的只有两点**：入口放在首启引导里（用户在「要换浏览器」的动机最强时出现）、一次任务带走多类数据（不让人勾五次）。
其余交互细节没有官方文档，本方案不引用其具体文案。

## 3. Chromium 自己的 importer（所有 Chromium 系浏览器的共同底座）

### 3.1 三层架构 ✅

| 层 | 位置 | 关键类 | 职责 |
| --- | --- | --- | --- |
| 浏览器进程·编排 | `chrome/browser/importer/` | `ImporterList`、`ExternalProcessImporterHost`、`ProfileWriter` | 枚举源、拉起 utility 进程、进度 UI、写入**目标** profile |
| 跨进程协议 | `chrome/common/importer/` | `importer_bridge.h`、`profile_import.mojom` | 回传书签 / 历史 / 密码等条目 |
| 沙箱读取 | `chrome/utility/importer/` | `firefox_importer.cc`、`ie_importer_win.cc`、`edge_importer_win.cc`、`bookmarks_file_importer.cc` | 真正打开源文件解析 |

两个对我们有用的事实：

- `ImporterList::DetectSourceProfiles` 在**线程池**里检测，产出 `SourceProfile{ importer_name, importer_type, source_path, services_supported 位掩码 }`。
  「支持哪些数据类型」是**源自己声明的位掩码**，不是 UI 写死的 —— 这正是我们要抄的接口形状。
- Chromium 开源代码里**只检测 IE / 旧 Edge / Firefox / 书签 HTML**；「从 Chrome 导入」是 Chrome、Edge、Brave、Vivaldi
  各自用 branding 代码补的。也就是说：**没有任何现成实现可以直接拿来用**。

### 3.2 Electron 为什么用不了 ✅

`chrome/browser/importer` 依赖 `Profile`、`ProfileWriter`、`PrefService`、`ContentBrowserClient`、沙箱 utility 进程与 mojo。
Electron 暴露的是 `session`（Cookies / Cache / Storage）与 `WebContents`，**没有 profile 写入器，也没有 importer 模块**。
`session.cookies` 只能管自己的 session，读不了别的浏览器的库。

## 4. Windows：怎么判断「装了、并且用过」

**安装证据（辅）** ⚠️

- Chrome：`HKCU\Software\Google\Chrome\BLBeacon`（版本号）、`HKLM\...\App Paths\chrome.exe`
- Edge：`HKCU\Software\Microsoft\Edge\BLBeacon`、`App Paths\msedge.exe`

**用户数据证据（主）** ⚠️ —— 我们采用这个

```
Chrome   %LOCALAPPDATA%\Google\Chrome\User Data\Local State
Edge     %LOCALAPPDATA%\Microsoft\Edge\User Data\Local State
Brave    %LOCALAPPDATA%\BraveSoftware\Brave-Browser\User Data\Local State
Vivaldi  %LOCALAPPDATA%\Vivaldi\User Data\Local State
Opera    %APPDATA%\Opera Software\Opera Stable\Local State   ← Roaming，不是 Local
```

判据链：

1. `Local State` 存在 → 浏览器的用户数据根目录成立；
2. 解析 `profile.info_cache` 拿到每个 profile 的 `path` 与显示名，`profile.last_used` 给出「上次用的那个」；
3. profile 目录内同时存在 `Preferences` 且（`Bookmarks` 或 `History`）→ 这个 profile **真的有数据**；
4. `Local State` 里有 `os_crypt.encrypted_key` → 密码 / Cookie 有解密可能；没有就只能导书签 / 历史。

第 3 步是关键：只检查第 1 步会把「装完就再没打开过」的浏览器也列出来，用户点进去看到 0 条会很困惑。

## 5. 每一类数据来自哪个文件

### Chromium 系 ✅+⚠️

| 数据 | 文件（profile 内） | 关键结构 |
| --- | --- | --- |
| 书签 | `Bookmarks`（JSON） | `roots.bookmark_bar / other / synced` → `children[]`，`type=folder\|url`、`name`、`url`、`date_added`、`guid` |
| 历史 | `History`（SQLite） | `urls(id,url,title,visit_count,typed_count,last_visit_time,hidden)`、`visits(url,visit_time,transition)` |
| 密码 | `Login Data`（SQLite） | `logins(origin_url,signon_realm,username_value,password_value,…)`，`password_value` 为密文 |
| Cookie | `Network/Cookies`（旧版在根目录 `Cookies`） | `cookies(host_key,name,value,encrypted_value,…)`、`meta(version)` |
| 自动填充 | `Web Data` | `autofill`、`autofill_profiles(_names/_emails/_phones)`、`credit_cards` |
| 搜索引擎 | `Web Data` + `Preferences` | `keywords` 表；偏好里的默认引擎 |
| 主页 / 启动页 | `Preferences`（JSON） | `homepage`、`session.startup_urls`、`session.restore_on_startup` |
| Favicon | `Favicons` | `favicons`、`favicon_bitmaps`、`icon_mapping(page_url→icon_id)` |
| 扩展 | `Extensions/<id>/<ver>/` + `Preferences` 的 `extensions.settings` | 目录 + 元数据 |

注意 `last_visit_time` / `expires_utc` 是 **WebKit 时间戳**（1601-01-01 起的微秒数），换算成 Unix 毫秒要
`(t / 1000) - 11644473600000`。

### Firefox 对照 ✅

| 数据 | 文件 | 结构 |
| --- | --- | --- |
| 书签 + 历史 | `places.sqlite` | `moz_places` + `moz_historyvisits`（过滤 `visit_type<=3`，去掉 iframe / 重定向）、`moz_bookmarks` |
| 密码 | `logins.json` + `key4.db` | NSS 加密，需要 NSS 解密链路 |
| 自动填充 | `formhistory.sqlite` | `moz_formhistory` |
| Favicon | `favicons.sqlite`（FF55+） | `moz_icons` |
| 主页 | `prefs.js` | 解析 homepage 偏好 |

一个顺序细节值得抄：**先导历史、再导书签**。书签会顺带导 favicon，而 favicon 只有在 URL 已存在时才落库。

## 6. 为什么必须先复制文件 ✅

`FirefoxImporter::StartImport` 第一步就是 `CreateUniqueTempDir()`，之后每个库都走
`GetCopiedSourcePath("places.sqlite")` → `base::CopyFile` → 用**副本**打开，头文件注释写明
「Using the copy is safe, ensures we don't modify Firefox's profile」。

原因：运行中的浏览器对 SQLite 持锁，直接打开会 `SQLITE_BUSY`；而**复制文件**在 Windows 上是被允许的（共享读），
复制完成就得到一个一致快照。

工程上还要多做两件事：

1. 复制 `-wal` / `-shm`，或者复制后对副本 `PRAGMA wal_checkpoint(TRUNCATE)`，否则会丢最近一次写入；
2. **只用只读连接打开副本**，并在完成后删除临时目录。

## 7. 加密：DPAPI / OSCrypt / v10 / v20

**根因** ✅：Windows `CryptProtectData`（DPAPI）的密文「通常只有**相同登录凭据**的用户、且**在同一台计算机**上才能解密」。
所以同一个 Windows 账户下，Edge 的密钥我们解得开 —— 它保护的是「这台机器上的这个用户」，不是「Edge 这个程序」。

**Chromium 的实现** ⚠️（实现级细节，需自测）

```
Local State → os_crypt.encrypted_key
  = Base64( "DPAPI" + CryptProtectData(32 字节 AES 主密钥) )

解密：DPAPI 解开 → 得到 AES-256-GCM 主密钥
密文格式：v10 / v11  前缀(3B) + nonce(12B) + 密文 + tag(16B)
```

**Chrome 127+ 的 App-Bound Encryption** ⚠️：改用 `os_crypt.app_bound_encrypted_key`，密钥与 Chrome 可执行文件 / 安装路径绑定，
解密要走 Chrome 自己的 elevation service 校验，密文前缀变成 `v20`。**第三方进程离线解密会失败。**

失败清单（必须写进 UI 文案，而不是报错弹窗）：

- 不同 Windows 账户 / 换了机器（DPAPI 机器绑定）；
- 便携版没有 `encrypted_key`；
- Chrome `v20`（App-Bound）；
- 企业策略下的增强安全模式；
- 源库 `-wal` 未落盘的半写状态。

**产品结论**：书签 / 历史 / 自动填充照常可导；密码 / Cookie 按浏览器分级，不可解时给
「这些网站需要重新登录一次」的降级说明，并保证**其它数据类型已经成功入库**。

## 8. Edge 的「首启自动带入」与手动导入的区别 ✅

Edge 有策略 `AutoImportAtFirstRun`：开启后首次运行**静默导入**，并**跳过 FRE 里的导入区块**；
可指定 `FromDefaultBrowser` / `FromGoogleChrome` / `FromMozillaFirefox` / `DisabledAutoImport`。
从 Chrome 带入的清单官方列出：收藏、密码、地址、支付信息、历史、设置、**固定的与打开的标签页、扩展、Cookie** ——
比 Chromium 开源 importer 宽得多。

与手动 `edge://settings/importData` 的差别：

| | 首启自动带入 | 手动导入页 |
| --- | --- | --- |
| 触发 | 一次性、无交互、按策略 | 用户主动、可反复 |
| 粒度 | 全量（含打开的标签页 / 设置） | 勾选类型 |
| 失败 | 静默跳过 | 逐项报结果 |

> ⚠️ 「Edge 每次启动持续导入」没有找到官方文档，不作为事实引用。

## 9. 值得抄的 UX（产品观察）

- **Arc**：把导入做成 onboarding 的必经一环，默认选中「你正在用的 Chrome」。
- **Brave**：`brave://settings/importData` 保留原生导入页兜底，首启另给「一键导入」卡片 —— 手动页兜底、首启页拉新。
- **Vivaldi**：导入后列出「哪些项失败 / 需要重新登录」，把不可导项显式化。
- **Opera**：首启检测 Chrome 并**预勾选**，完成给「已迁移 N 项」汇总。

可复用的五条：**自动检测 + 分类型预估数量 + 默认全选 + 明确标注不可导项 + 结果汇总**。
另外：导入过程要可取消（用户在等不确定的 30 秒会关窗），重复导入必须幂等（按 `guid`/`url`、`url+visit_time` 去重）。

## 10. 落到 Hira 的方案

### 10.1 现状

| 已有 | 位置 |
| --- | --- |
| 书签导入（Netscape HTML / 插件格式） | `bookmark:import`，[bookmarks-client.js](../apps/app-main/src/pages/_shared/bookmarks-client.js) |
| 密码导入（CSV） | `password:import-csv` |
| 插件贡献导入格式的扩展点 | `contributes.importFormats`（扩展点 `bookmark.import-format`） |
| 引导里的导入一屏 | `pages/onboarding/stages/migrate`（两条流程共用，位置由 ORDER 决定） |
| 独立导入页 | `pages/import-data`（作为标签页打开） |

也就是说：**入口和写入端都已经有了，缺的是「自动发现 + 直接读源库」这一段**。

### 10.2 建议的模块边界（插件化，五个可替换件）

```
main/import/
  detect/       每个源一个 adapter：chrome.js / edge.js / firefox.js / bookmark-html.js
                └─ 统一导出 { id, label, detect() → SourceProfile[], services: 位掩码 }
  copy/         源库 → 临时目录（处理 -wal/-shm、只读、清理）
  parse/        每个数据类一个 parser：bookmarks.js / history.js / passwords.js / cookies.js
  crypt/        KeyProvider 接口：dpapi.js（Win）/ 未来的 keychain.js（macOS）
                └─ 解不开返回 { ok:false, reason:'app-bound' }，不抛异常
  write/        幂等写入：复用现有 bookmark / history / password 服务，不新开写路径
```

三条硬约束：

1. **adapter 只声明能力**（位掩码 + 预估数量），UI 不按浏览器名字写 if/else；
2. **加密层永远返回结构化结果**，`v20` 是正常返回值的一种；
3. **写入端复用现有服务**，导入只是「另一种数据来源」，不复制业务逻辑。

### 10.3 与现有界面的接线

- `pages/onboarding/stages/migrate` 增加「一键从 Chrome / Edge 导入」卡片，与现有「选文件」并列 —— 后者作为兜底保留；
- `pages/import-data` 增加同一个卡片，两者共用同一份 adapter（同一个 `detect()` 结果）；
- 结果汇总沿用现有徽标 / 状态行语义（已导入 N 条 / 需重新登录 / 已跳过）。

### 10.4 分期

1. **P1**：Chrome / Edge 的 `Bookmarks` JSON + `History` SQLite（不需要解密，收益最大、失败面最小）；
2. **P2**：密码 / Cookie（DPAPI + `v10/v11`，`v20` 显式降级）；
3. **P3**：自动填充 / 搜索引擎 / 主页；Firefox 的 `places.sqlite`；
4. **P4**：扩展目录迁移（只做「装回去」的引导，不复制 `Local Extension Settings` 里的数据）。

## 11. 风险清单

| 风险 | 处理 |
| --- | --- |
| Chrome `v20` 解密失败 | 视为正常结局，文案说明「需重新登录」，其它数据照常入库 |
| 源库被锁 / 半写 | 复制 + `wal_checkpoint`，只读打开副本 |
| 时间戳单位错（WebKit µs） | 统一在 parser 层换算，不让上层看到两种单位 |
| 重复导入 | 按 `guid` / `url` / `url+visit_time` 幂等 |
| 关窗中断 | 每一步落库即提交，可续跑；UI 只在最后汇总 |
| 未经授权读取他人数据 | 只读用户自己账户下的文件；不做提权、不调 Chrome 的 elevation service |
