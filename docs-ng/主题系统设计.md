# 主题系统设计（Theme System）

> 目标：**主题是一份数据，不是一段代码。** 换主题 = 换一份「令牌表 + 背景图」，
> 浏览器外壳、内部页、新标签页三处同时换肤，且主题能像插件一样安装、启停、卸载、
> 从市场获取、导出给别人。
>
> 学习对象：**Vivaldi**（主题库 / 编辑器 / 背景 / 调度 / 可分享 ZIP / 图标集）；
> 保真基准：**旧 Hira**（深色四档策略、浅色预设 + 自定义色、起始页壁纸多来源、
> 模糊与遮罩、按壁纸亮度自适配文字色、favicon 动态着色、空间级主题隔离）。

---

## 0. 一句话架构

**一份主题数据 → 一张令牌映射表 → 三套消费面；安装/分发复用插件中心。**

```
                     ┌──────────────── 插件体系（安装 · 启停 · 市场 · 签名 · 持久化）────────────────┐
                     │                                                                              │
  theme.json ──▶ domain-theme ──▶ infra-theme ──▶ ┬─ 外壳 WebContentsView（shell/rail/panel/浮层）
  + background      （模型/解析/     （CSS 引擎 +   ├─ 内部页 hira://（base.css 令牌被覆盖）
                    目录/包格式）     themeManager）└─ 新标签页（背景层 + --nt-* 令牌）
                     ▲                                         ▲
                     └── 主题插件（type: theme-plugin）：contributes.theme + theme.source Provider
```

三块归属定死（各只有一处实现）：

| 东西 | 归谁 | 为什么 |
| --- | --- | --- |
| **主题数据 → 令牌** | `domain-theme`（纯函数，无 Electron / 无 IPC） | 唯一真源。三套消费面必须拿到同一组值，否则「同一个主题在三处颜色不一样」 |
| **令牌 → CSS** | `infra-theme`（已有） | 它已经在做「读 token 文件 + 叠扩展点 → 一段 CSS」，主题只是多叠一层 |
| **主题的安装/分发** | 插件体系（已有） | 发现/安装/启停/卸载/更新/签名/市场/落盘整条链路已存在，主题最贵的部分不该重造 |

## 1. 现状：为什么必须统一（三套令牌 + 三处死代码）

现状盘点（均已核对源码）：

| 消费面 | 令牌来源 | 现状 |
| --- | --- | --- |
| 浏览器外壳（app-shell / rail / panels / 各浮层 / 子窗口，共 18 个渲染入口） | `packages/shared-ui-tokens/{tokens-base,tokens-light,tokens-dark}.css` 的 `--hira-*` + 旧变量 | 活的，但只有 `app.theme` 三态（light/dark/system） |
| 内部页（`hira://` 下的设置/历史/下载/新标签页…） | `apps/app-main/src/pages/_shared/base.css` 的 `--bg/--surface/--text/--accent…` | **另一套令牌**，靠「与设置页同值」的注释手工对齐，无代码层共享 |
| 新标签页 | `apps/app-main/src/pages/newtab/newtab.css` 的 `--ntp-*` | 纯色，**无任何壁纸逻辑** |

三处死代码（主题系统的债）：

1. `tokens-light.css` 定义了 `light-theme-softWhite / -mint / -warmGray / -sakura` 四套，
   但 `theme-controller.js:26` **恒定只加 `light-theme-softWhite`**，其余三套全仓无消费者 → 不可达。
2. `tokens-base.css:297-312` / `tokens-dark.css:125-136` 为 `#custom-newtab-shell`、`.nt-force-dark`
   定义了整套 `--nt-*`，但**没有任何源码创建这个元素或加这个类** → 悬空规则。
3. `ui/ui-new-tab` 整个包（`createNewTabPage` / `injectNewTabStyles`）只在
   `apps/app-main/package.json` 有依赖声明，**全仓无 import**。

结论：主题系统不是"加一个设置项"，而是**把三套令牌收敛成一处产出**，顺手清掉上述死代码。

## 2. 数据模型：主题包格式（`theme.json`）

主题包 = 一个 ZIP，里面是 **`theme.json` + 可选背景图/图标**（Vivaldi 同构：一个 ZIP，JSON + 图片）。

**实际导出包里放三样**：

| 文件 | 内容 | 谁用 |
| --- | --- | --- |
| `theme.json` | 我们的主题定义（下面那个 schema） | 我们自己导入 |
| `vivaldi.json` | **同一个主题**的 Vivaldi 字段名版本 | 丢给 Vivaldi 试 |
| `background.*` | 背景图（仅当主题用图片背景；文件名与 `background.path` 一致） | 两边都用 |

同一份数据导出成两个字段名版本，而不是维护两套导出格式 —— 少一份会漂移的东西。
导入时按 `hira-plugin.json` → `theme.json` → 任意顶层 JSON 的顺序识别（见
`theme-package.js#unpackTheme`）。

```jsonc
{
  "id": "com.hira.theme.aurora-dark",     // 全局唯一，反向域名
  "name": { "zh-CN": "极光暗", "en-US": "Aurora Dark" },
  "author": "…", "version": "1.0.0", "schemaVersion": 1,

  // ── 1. 配色：我们自己的语义槽位（Vivaldi 用 colorBg/colorFg/colorHighlightBg/colorAccentBg…）──
  "colors": {
    "mode": "dark",                        // dark | light —— 决定是否同时驱动 nativeTheme
    "bg": "#0b0f14",                       // 主背景（对应 Vivaldi colorBg）
    "fg": "#e6edf3",                       // 主前景（colorFg）
    "surface": "#111820",                  // 抬升表面（工具栏/面板/卡片）
    "accent": "#22d3ee",                   // 强调色（colorAccentBg）
    "highlight": "#0e7490",                // 选中/高亮底（colorHighlightBg）
    "border": "#1f2b36"
  },

  // ── 2. 外观开关：Vivaldi「设置」页的对应项 ──
  "style": {
    "transparency": 0.0,       // 0~1，工具栏透明让背景透出（Vivaldi: Transparency）
    "blur": 0,                 // 0~40 px，透明层模糊（Vivaldi: Blur）
    "contrast": 0.0,           // 0~1，UI 元素对比度增强（Vivaldi: Contrast）
    "cornerRadius": 6,         // 圆角（Vivaldi: Corner rounding）；0 = 直角
    "contentInset": 4,         // 网页 / 面板四周的呼吸空；0 = 贴边无边框
    "colorizeMode": "unified", // 只剩 unified（统一着色）。Vivaldi 的 tabbar/addressbar 两档本项目无实现，导入时归一到 unified
    "material": "none"         // none | acrylic | mica —— 窗口级系统模糊（Vivaldi 无对应物，见 §6.2.3）
  },

  // ── 3. 背景：图 / 视频 / 纯色 / 每日图 / 桌面壁纸（Vivaldi「背景」页 + 旧 Hira 的壁纸来源）──
  "background": {
    "kind": "image",           // image | video | color | css | daily | desktop | none
    "path": "background.jpg",  // 资产 key（kind=image 或 video）—— 见 §6.4
    "color": "#0b0f14",        // kind=color（或作为图片加载前的兜底色）
    "position": "cover",       // cover | contain | center | tile（video 时映射到 object-fit）
    "opacity": 1.0,            // 不透明度（对齐旧 Hira: 1 - overlay*0.82）
    "blur": 0,                 // 背景自身模糊（旧 Hira blurLevel: 0~20）
    "overlay": 0.0,            // 遮罩浓度 0~1（旧 Hira overlayOpacity / 100）
    "overlayColor": "#0b0f14", // 遮罩色（对齐 Vivaldi 的 color 遮罩）
    "applyTo": ["window", "newtab"]  // 应用到哪几个面（Vivaldi: 窗口 / 起始页）
  },

  // ── 4. 图标集（Vivaldi: 自定义图标；阶段 P4 才做）──
  "icons": { "back": "icons/back.svg" },
  "preview": "preview.png"
}
```

**为什么背景放主题里，而不是独立"壁纸设置"**：Vivaldi 的壁纸是主题的一部分 ——
一个暗色主题配一张亮背景，观感就废了。旧 Hira 把它拆成 `startPageSettings.wallpaper` + 全局浅色预设，
结果是"换了主题背景没换"。**背景跟随主题**，用户想换背景就改主题（或建一个新主题）。

**兼容 Vivaldi**：导入时把 `colorScheme.colorBg/colorFg/colorAccentBg/colorHighlightBg/...`
映射到上面的 `colors.*`，`backgroundImage/backgroundPosition/blur/alpha/colorBg` 映射到 `background.*`
（映射表单独一个 `theme-vivaldi.js`，纯函数、可测）。导出的包同时保留 `theme.json`，
使主题可以双向搬运。

> **诚实的边界**：`theme-vivaldi.js` 的字段名取自 Vivaldi 的导出格式，方向是
> "我们的字段 ↔ 它认得的字段"。**没有在真实 Vivaldi 安装上验证过**（本仓库里没有
> Vivaldi），所以承诺是"字段名与语义对得上、且我们自己的导入能原样读回"，
> 不承诺"Vivaldi 一定能原样打开"。Vivaldi 里没有对应物的槽位（每日图 / 桌面壁纸）
> 在导出时降级为纯色；`cornerRadius` 的单位口径未必一致，导入时固定用我们的默认值。

## 4. ★ 令牌统一：一张映射表，三套消费面

这是整个系统**最不可妥协**的一条：颜色只有一处产出。

`tokenMap.js` 输入解析后的主题，输出一张**扁平变量表**：

```js
// 一份输入 → 三套令牌名（后面的是别名，指回同一个值）
{
  '--hira-bg-surface':    colors.bg,
  '--hira-bg-elevated':   colors.surface,
  '--hira-text-primary':  colors.fg,
  '--hira-accent':        colors.accent,
  '--hira-accent-bg':     colors.highlight,
  '--hira-border-subtle': colors.border,
  '--hira-chrome-alpha':  style.transparency,   // 工具栏透明层用

  '--main-bg-color':      colors.bg,            // 旧变量（ui-chrome-layout 等仍在用）
  '--text-color':         colors.fg,
  '--accent-color':       colors.accent,

  // 内部页（_shared/base.css 那套）
  '--bg': colors.bg, '--surface': colors.surface, '--text': colors.fg,
  '--accent': colors.accent, '--border': colors.border,

  // 新标签页（newtab.css 那套）
  '--ntp-bg': colors.bg, '--ntp-text': colors.fg, '--ntp-accent': colors.accent
}
```

三条落地方式（各自一个入口，不再各写各的）：

1. **外壳**：`theme-controller.js` 把这张表写进 `documentElement.style`（`setProperty`）；
   同时保留 `data-theme` + `body.dark` 类（现有 CSS 的 `body.dark` 规则仍在，作为"变量未覆盖时"的兜底）。
   —— 从"给 body 加类、靠 CSS 文件映射"改成"直接落变量"，主题才有可能任意配色（现在四套预设就是靠类硬写的）。
2. **内部页**：新增 IPC `theme:tokens`，`_shared/runtime.js#initTheme()` 拉到后写根变量；
   `_shared/base.css` 的 `:root` 降级为**兜底默认值**。
3. **新标签页**：与内部页同一条（它本来就是内部页），额外加载背景层（§7）。

> **内部页只有这一个主题入口**：任何内部页（设置 / 下载 / 历史 / 书签…）都必须在启动时
> 调 `_shared/runtime.js#initTheme()`，并且**不得**自己判断 `prefers-color-scheme`、
> 也不得写死深浅 —— 主题是用户显式选的（深色主题完全可能跑在浅色系统上），自算必然与
> 外壳不一致。设置页曾整页自算三态（"外壳换了、设置页没换"），错误页曾整页写死浅色
> （"深色主题下错误页白得刺眼"）—— 两者现在都只走 initTheme + 令牌消费。

> **为什么不用 `insertCSS` 注入变量**：`insertCSS` 是异步且每次返回一个 key，
> 重主题时要 remove 旧 key，容易漏；写 `documentElement.style` 是同步、幂等、可被覆盖的。
> `insertCSS` 继续只承担"静态 token 文件"（`infra-theme` 现有路径），不承担动态主题。

## 5. 主题即插件：与插件体系 / 插件中心的结合

### 5.1 为什么是插件

插件体系已经把主题系统最贵的部分做完了：

| 主题需要的能力 | 插件体系里已有的 |
| --- | --- |
| 发现 / 安装 / 卸载 | `plugin-installer`（体检、暂存、同盘 rename、备份回滚、zip-slip 守卫） |
| 市场获取 / 版本 / 更新 | `plugin-market`（多源索引、sha256 校验、`updateAvailable`） |
| 启停 / 禁用降级 | `PluginRegistryV2`（userDisabled / autoDisabled / blocked / failed 状态机） |
| 签名 / 信任分级 | `plugin-installer`（official / community / local + 公钥信任库） |
| 落盘 | `plugin-state-store`（复用 settings KV） |
| 声明式贡献 | manifest `contributes`（`normalizeManifest` 已宽松透传） |
| 贡献一段 CSS | 官方插槽 `theme.token-provider`（REDUCE，已存在） |

**"一个主题被禁用 = 换肤立刻失效"** —— 能力闸门天然成立，符合 Harness「禁用即真没了」。

### 5.2 插件形态（**已实现**）

```jsonc
// apps/app-main/plugins/theme-pack-nord.hira-plugin.json —— 出厂自带示例，纯数据、零代码
{
  "id": "theme-pack-nord",
  "name": { "zh-CN": "主题包 · Nord" },
  "version": "1.0.0",
  "type": "theme-plugin",           // 插件中心据此分组为「主题」段
  "trustLevel": "internal",
  // ⚠ 刻意**没有 main** —— 纯数据插件应当零代码。注册中心对无 main 的插件返回空模块
  //    （见 plugin-registry-v2.js#loadDefault），声明式贡献照常生效。
  "contributes": {
    "themes": [ /* 主题对象数组：id/name/mode/colors/style/background … */ ]
  }
}
```

- **`type: 'theme-plugin'`**：插件中心据此分组（[format.js](file:///e:/Desktop/OTHER/1A-STAR_Hira/1A-STAR_Hira_NG/apps/app-main/src/pages/plugins/format.js) 的
  `TYPE_SECTIONS` 新增「主题」段，与「面板/引擎」分开列）。
- **`contributes.themes`：声明式、纯数据、零代码** —— 这是「主题即插件」的**主路径**。
  它走的是既有的 `ContributionRegistry`（`contributeFromManifest` 通用登记任意 `contributes.<kind>`），
  因此**禁用主题插件 = 注册中心 `clearPlugin` 摘掉贡献 = 主题立刻从目录消失**，
  不需要主题层额外写一条清理规则。主题对象形状见 §2（`theme.json`），与 `normalizeTheme` 同构。
- **`main` 可选**：需要运行时才算得出的主题（从当前网页取强调色、随时间渐变…）
  才写入口模块，在 `extensionPoints()` 钩子里 `extends: { 'theme.source': () => … }`。
  **绝大多数主题不需要走这条**。
- **维护者视角**：一条主题 = 一段 JSON；一个主题包 = 一个 manifest 里的 `themes` 数组。
  安装 / 启用 / 禁用 / 卸载 / 市场 / 权限，全部复用插件体系的既有链路。

> 实现落点：`theme-service.js#refreshSources()` 合并「声明式 `contributes.themes`」与
> 「计算式 `theme.source`」两个来源到同一个目录；`main.js` 在插件启动完成、
> 以及每次插件启停/装卸后调用 `refreshThemeSources()` 同步（见 §10 的 P2）。

### 5.3 新增官方插槽（2 个）

在 `infra/infra-plugin/src/official-extension-points.js` 追加：

```js
{ id: 'theme.source',   mode: 'MULTI',  description: '主题来源（贡献一个主题定义）', owner: 'infra-theme' },
{ id: 'theme.decorator', mode: 'REDUCE', description: '主题令牌后处理（可整体改写配色）', owner: 'infra-theme', initialValue: null }
```

- `theme.source`：每个主题插件贡献一条主题；`domain-theme#list()` 合并"内置目录 + 用户目录 + 插件来源"。
- `theme.decorator`：REDUCE（`(主题) => 主题`），社区 Mod 可以整体改主题（降饱和、夜间压暗、色盲适配）。
  **`theme.token-provider` 保持原样**（它改的是最终 CSS 文本，粒度更细，两者互补）。

### 5.4 功能面登记

**不做**。理由：主题不是"某条 UI 入口依赖的能力"—— 内置主题永远存在（`theme-builtins.js`），
主题入口不会因为插件全被禁用而消失；插件主题只是**追加**到目录里。若给主题登记
`feature-map` 条目，反而会让"插件主题全禁用"误伤设置页的主题下拉（把内置主题也藏了）。
功能面登记留给"整个功能面唯一出口在插件里"的情形（如扫码器）。

### 5.5 插件中心的呈现

- 插件中心是**内部页** `hira://plugins`（`apps/app-main/src/pages/plugins/`），**已新增**分组 **「主题」**
  （`format.js#TYPE_SECTIONS`），列出 `type: theme-plugin` 的插件，与"面板/引擎"分开列。
- 主题专属的浏览/编辑/调度放在**内部页** `hira://themes`（`apps/app-main/src/pages/themes/`，
  学 Vivaldi 的「设置 > 主题」，随插件中心同构改造），
  侧栏 `ui-panel-themes` 只做轻量入口（当前主题 + 色卡网格 + 「管理…」）。
  面板与主题页是**两个独立视图**，共用同一个编排内核（`shared-types/src/themes/core.js`）——
  于是"面板里点一下换主题"与"页面里点一下换主题"是同一段代码。
- 面板入口是**声明式**的：`apps/app-main/plugins/panel-themes.hira-plugin.json` 的
  `contributes.panels` 加一条，面板目录（`main/panel-catalog.js`）里就多一项，
  rail / navbar / 按钮编辑浮层全部自动一致 —— 主进程与渲染层都不需要为此写代码。
- 面板里的「管理主题…」走面板宿主注入的**通用端口** `ctx.openPage('themes')`
  （`renderer/shared/panel-context.js`，内部实现 = `tabsClient.newTab({ url: pageUrl(host) })`）
  —— 面板因此不需要认识 URL 拼法，与 manifest 的 `opensPage` 是同一条判据。
- 页面登记只有一处：`packages/shared-types/src/pages.mjs` 加一行（`host: 'themes'`，
  `glyph: 'Palette'`）—— 侧栏导航、标签条图标、设置页入口全部从那张表派生。
  设置页「主题」分区因此改走 `entry.href = pageUrl('themes')`（与快捷键分区同款），
  不再有 `window: 'theme-manager'` 这种窗口类型声明。

## 6. 背景图的存储与应用

- **存储**：随主题包放在插件目录里（`apps/app-main/plugins/theme-<id>/background.jpg`，
  用户安装的落在 `userData/plugins/theme-<id>/`）。导入的主题包会被**装成一个主题插件**，
  于是"资产住在插件目录"这件事天然成立 —— 不需要为主题另造一套存储。
  ⚠ 这一条只对**插件主题**成立；**用户自建主题**的图片走另一条链（见 §6.0）。
- **取用**：走既有 `hira-plugin://` 特权协议（`plugin-protocol.js`），
  URL = `hira-plugin://<pluginId>/background.jpg?v=<主题版本>`。**已接上**：
  `theme.mjs#normalizeTheme` 带出 `pluginId`（由贡献注册表打标），
  `theme-service#assetUrlFor` 用注入的 `pluginAssets.url()` 拼 URL
  （URL 形状的唯一真源仍是 `buildPluginAssetUrl`）。
- **单文件上限按扩展名分档**（`plugin-protocol.js#maxBytesFor`）：
  代码/文本 2MB 不变，**图片/字体 8MB**（对齐 Vivaldi 的 8MB 上限）。
  安全边界不放宽：白名单、目录穿越守卫、"仅启用的插件可读"三条全部保持。
  为什么不统一放宽：`.js` / `.json` 会被当代码读进渲染层，8MB 的额度是一条能被
  用来一次性灌满内存的通道；而背景图是用户自己拍的照片，2MB 会让"导入主题"直接失败。
- **应用面**（`background.applyTo`）：

| 面 | 怎么画 |
| --- | --- |
| **窗口**（浏览器外壳） | `ui-shell` 的根容器加 `::before` 背景层（`background-image` + `position/size/repeat`），三个 chrome 区域的底色带 `--hira-chrome-alpha` 透明度（Vivaldi 的 "Transparency"），配 `backdrop-filter: blur()`（"Blur"）；`layout.setTabTheme()` 只设**网页之外**的两样原生色：`surfaceBackgroundColor`（rail / 面板这些 chrome 表面，带壁纸时透明）与 `frameBackgroundColor`（窗口底 = 网页外圈那 4px 缝）。**网页视图自己的画布色固定白纸，不由主题给**（见 §6.1.1） |
| **新标签页** | **不画背景**：标签视图是透明画布（APPS 侧 `tabCanvasColor` 钩子给 `#00000000`），body 在有壁纸时 `transparent` —— 直接露出外壳那一份，取景 / 模糊天然一致；`--ntp-*` 令牌只用于顶部控件与玻璃卡片 |

背景参数语义**照搬旧 Hira**（已实战验证过的手感）：
`backdrop-filter: blur(Npx)`、遮罩 `rgba(overlayColor, α)`、图片不透明度 `1 - α*0.82`。

### 6.0 用户主题的图片：`hira-theme://` + 内容寻址资产库

上面那套"资产住在插件目录"只覆盖**插件主题**。**用户在编辑器里自建的主题**从来不是插件 ——
于是 `assetUrlFor` 对非插件来源直接返回空串，编辑器里那一栏"图片路径"是个**死值**：
填了永远不生效。本轮把这条链补齐：

| 环节 | 落点 |
| --- | --- |
| 选图 | 编辑器「图片」一栏是**选择图片…**按钮 → `theme:asset:pick` → 系统文件对话框 |
| 落盘 | `theme-assets.js` 拷进 `<userData>/theme-assets/<内容哈希8位>-<消毒原名>.<ext>`（扁平、内容寻址：同名不同图不会互相覆盖，同图重复选自动复用） |
| 取用 | `hira-theme://asset/<key>`（`theme-asset-protocol.js`）。`theme-service#assetUrlFor` **按来源选通道**：`pluginId` → `hira-plugin://`，否则 → `hira-theme://` |
| 导出 | `ipc/theme.js` 的 `readThemeAsset` 同样按来源选：用户主题的图也会被带进 zip |

- **为什么另开一个协议而不是给 `hira-plugin://` 加个保留 host**：两者**安全边界不同**。
  插件协议必须下发**可执行代码**（`.js`/`.mjs`），而主题图片通道**只发图片** ——
  混在一起等于让"背景图"这条链凭空获得"能下发代码"的能力。分开后两侧各自收紧的改动面
  都只在自己那个文件里（与 `plugin-protocol.js` 文件头"刻意分成两个协议"同一条理由）。
- **不做资产回收（有意为之）**：删主题后图可能留在库里。自动清理需要"还有没有主题引用它"
  这个判据，而**刚选好、还没保存的草稿**也在引用那张图 —— 扫一遍会把用户刚选的东西删掉。
  代价只是磁盘上多几个文件，"删错"的代价是用户的工作没了。

### 6.0.1 「每日一图」：Bing 每日壁纸

`kind: 'daily'` 原来只是枚举里存在、**没有任何实现**（`backgroundImage` 恒为空）。
本轮的实现链：

- `theme-daily.js` —— 唯一会联网的地方。`GET https://cn.bing.com/HPImageArchive.aspx?format=js&idx=0&n=1&mkt=zh-CN`
  （失败回落 `www.bing.com` 的 `mkt=en-US`），取 `images[0].url` 拼绝对地址。
  缓存**按本地日期**（跨天自动失效，不需要定时器），失败记 5 分钟冷却（否则离线时
  `backgroundFor` 的每次调用都会再起一次请求 = 请求风暴）；用 `net.fetch` 走系统代理。
- 与旧 Hira 的**一处有意偏离**：去掉最后的第三方图床回落（`api.dujin.org`）——
  用户要的是"Bing 壁纸"，那个地址给的东西不受 Bing 控制。拉不到就不落图。
- `theme.mjs#themeBackgroundCss` 新增 `dailyUrl` 第三参，并与 `image` **合成同一条
  "照片型"口径**（`photoUrl`）—— 于是 `position` 那套 size/position/repeat 天然共用，
  不会出现"每日一图改不了铺法"。
- 取图是**异步**的，而该函数必须同步：所以主进程只读缓存，拿不到就起一次后台拉取，
  拿到后由 `theme-service` 发 `background` 主题事件 → `theme-runtime` **重发一次广播**
  （少了这一条，切到"每日一图"后会一直停在空白底上 = "选了没反应"）。

### 6.0.2 编辑器里"不许写代码"

- **渐变**（`kind: 'css'`）= **两个取色器**，不再是让用户手写 `linear-gradient(...)`。
  模型里仍然只有 `background.css` 一个字符串（Vivaldi 兼容字段，**不动 schema**），
  编辑器做的是「解析 → 两个色 → 重新生成」的往返（`format.js#parseGradient/buildGradient`），
  方向等其余信息从原值里保留。解析不出的（多色 / 径向渐变）**不覆盖原值** ——
  拆得面目全非比"改不了"更糟。
- **图片** = 文件管理器选择（见 §6.0），不再是一个让用户手填、且对用户主题从不生效的路径框。

### 6.1 网页四周那圈 4px 间隙：必须**显式**填 chrome 底色

`#chrome-content` 是外壳的"内容洞"，网页的原生视图被主进程按 `_contentPadding`
四边内缩 4px 放进去 —— 那 4px 落在 `#chrome-content` 自己的盒子里，**它的背景就是这圈缝的颜色**。

**为什么不能靠"透明 + 底下那层"**（曾经的实现就是这么不对的）：

- 深色令牌里 `body.dark { --main-bg-color: transparent }` —— 那是旧设计：要让**原生窗口表面**
  从缝里透出来。于是缝的颜色实际由 `layout.setTabTheme()` 设的**原生表面色**决定，
  而 navbar / tabbar / 侧栏用的是 `--main-bg-color` —— **两条独立的取值链**，
  深色主题下必然出现"navbar 是一种色、缝是另一种色"。
- 主题带壁纸时又要让这层透明（见 `html[data-theme-background='1']` 那条规则）。

所以 `#chrome-content` 显式铺 `--main-bg-color` —— 与 navbar **同一个变量**，
"缝与 chrome 同色"从此是构造保证，而不是两处各取一次值碰巧相等。
壁纸存在时，那条更高特异性的 `data-theme-background` 规则会把本行覆盖回 `transparent`，
语义不变（缝里透出壁纸，与 chrome 一致）。

**面板共用同一圈呼吸空与同一个圆角**（用户原话："面板也做个和网页一样的上下左右边距…
也做个和网页一样的圆角，是可以一起调节的"）—— 落点在 `LayoutCoordinator#_placePanelSlot`：
面板是**独立视图**，所以这里不是 CSS 而是原生 bounds + 原生圆角（`view.setBorderRadius`，
与标签视图**同一个值**）：

| 边 | 让出多少 | 为什么 |
| --- | --- | --- |
| 上 / 下 | `_contentInsetTop` / `_contentInsetBottom` | 与网页同一圈呼吸空（面板是"浮在内容区里的一块"） |
| **外侧**（面板自己那一侧） | `_contentInsetLeft`（左面板）/ `_contentInsetRight`（右面板） | 与 rail / 窗口缘之间也要那一圈 |
| **朝网页那一侧** | **0** | 网页自己那 4px 就是两块之间的间隔；再让一次就成 8px，与其它三边不一致 |
| 圆角 | `_tabBorderRadius`（= 主题 `style.cornerRadius`） | 一处调节、网页与面板两处生效 |

> **边距与圆角都是"0 = 关闭"的真值，不是"未设置"**：
> `style.cornerRadius = 0` 会原样下发（`setBorderRadius(0)`），网页 / 面板 / 标签 / 浮层一起变直角；
> `style.contentInset = 0` 让网页与面板**贴边**，那圈呼吸空（以及它带来的"边框"观感）消失。
> 两处都**没有** `value > 0 ? value : 默认` 这种钳制 —— 曾经 theme-runtime 与
> `webSidebarHeader` 各写过一条，结果编辑器显示 0、界面还是 6，属于历史 bug，已清除。

> **圆角遮罩会随"表面重建"丢失**：`setBorderRadius` 造出的遮罩挂在视图的合成表面上，
> 页面跨进程导航 / 渲染进程崩溃重建表面后旧遮罩就没了（账本还记着老值 ⇒ 布局去重跳过重写），
> 表现为"圆角拉大以后网页四角偶尔冒白色方块"。`LayoutCoordinator#_watchRadiusSurface`
> 在 `did-navigate` / `did-navigate-in-page` / `did-finish-load` / `render-process-gone`
> 上补写一次（下一拍再补一次），见 `RADIUS_SURFACE_EVENTS`。

**圆角刻度只有一份公式**：`shared-ui-tokens#tokens-base.css` 把 `--hira-radius-2xs/xs/sm/md/lg/xl`
与标签档 `--hira-radius-tab`、控件档 `--hira-radius-control` 全部定义成
`var(--hira-theme-radius) ± N × var(--hira-radius-step)`（步长恒 1px，由
`shared-types#themeTokens` 下发，圆角为 0 时步长同时归零）。chrome 里的标签、navbar 的
hover 按钮、书签栏、各类浮层内的按钮/输入框都只引这些令牌，**不再各写 px** —— 主题圆角
一调，整界面跟着走；拉到 0 时整界面一起变直角。

**基准 = 网页视图 / 浮层那一个数**（`--webview-radius` 与浮层面板都直接取
`--hira-theme-radius`）。其它表层只做**整数档的加减**，不做比例：r=6 → 5/6/7/7/8/9，
标签 7，控件 6，地址栏 7。**曾经**是 1×/1.33×/1.67×/2.33× 的等比放大（r=6 → 4/6/8/10/14/12），
默认值下还能忍，一调到 12 就变成"网页 12、标签 18、卡片 28"—— 同一根旋钮量出两套口径，
用户报的就是这个"各处的圆角偏大"。比例换成"加固定步长"后，r=12 也只是 11/12/13/13/14/15。

**不许再有写死的容器圆角**：`--ng-omnibox-radius` 之前钉着 18px（30px 高的字段被裁成
胶囊），主题 6 时它圆 18 —— 这是最后一批"同一数值下明显偏大"的来源，现已改成
`var(--hira-radius-sm)`（r=6 → 7，与标签 / 按钮同级）。今后新增容器只许引令牌；
只有 `50%` / `999px` 这类**形状**（圆形热区、开关轨道、进度条）才允许写死。

### 6.1.1 网页视图的画布色：固定白纸，主题不得参与

`WebContentsView` 的 `backgroundColor` 不是"窗口底色"，而是**网页的画布底色**：
站点不写 `html`/`body` 背景时（工具页 / 老站点 / 纯文本页很常见），Chromium 就直接
把这个值当作页面背景显示。而标签的 `webPreferences` 又是 `transparent: true`
（`infra-window/webPreferences.js#buildTabWebPreferences`），这条链上**没有任何**
"浏览器默认白"兜底 —— 视图底色就是最终呈现在用户眼前的那一层。

曾经的错误做法：`theme-runtime#applyNativeSurface` 把 `palette.bg` 当作 `backgroundColor`
传给 `LayoutCoordinator#setTabTheme`，后者对所有标签视图 `setBackgroundColor(主题色)`。
结果就是**大量没写背景的白页整页被染上主题色**（用户报告："简单没定义背景的白色背景网页
背景也跟着变颜色"）。主题只该拥有"网页之外"的表面，不该替站点决定页面底色。

现在的契约（一处分层、互不越界）：

| 层 | 拥有的颜色 | 落点 |
| --- | --- | --- |
| 网页视图（标签 / 独立侧栏网页） | 画布色 **固定 `#ffffff`** | `WebContentsManager#TAB_CANVAS_COLOR`（`createTab` / `adoptTab` / `createWebSidebarView` 三条路径统一） |
| chrome 表面（rail / 面板 / rail 浮层） | `surfaceBackgroundColor` | `WebContentsManager#setSurfaceBackgroundColor`（带壁纸时为透明） |
| 窗口底（网页外圈 4px 缝的占位） | `frameBackgroundColor` | `LayoutCoordinator#_frameBackgroundColor` + `win.setBackgroundColor` |

> 站点自己的深浅由站点（或未来的强制深色 / 注入规则）负责 —— 那属于 `webview` 域，
> 不进主题系统（与 §12「不做网页内容强制深色」同一条边界）。
> 需要给空白页换深色，是**网页层**的能力，不是把整个画布刷成主题色。
> `LayoutCoordinator#setTabTheme` 的入参里**没有** `backgroundColor` 这一项 ——
> 这是有意的：少一个口子，未来就不会有人再"顺手"把主题色写进网页。

### 6.1.2 原生表面的发布时序：先落原生，再判去重

原生表面（`setTabTheme`）是**窗口级**的，而新窗口不继承旧窗口的设置 —— 于是两件事必须同时成立：

1. `theme-runtime#publish()` 把 `applyNativeSurface(theme)` 放在**指纹去重之前**。
   主题没变（指纹相同 → 不广播）时，新建窗口仍然需要这一次原生落色，
   否则它停在构造期的出厂浅色上（`#f9fafb`）—— 表现就是"新窗口的 rail / 面板白一块"。
2. 窗口挂载时（`onWindowMounted`）**定向补推**一次当前主题（`broadcastCurrent({ windowId })`）。
   建窗到渲染层订阅之间有一段空窗，首帧不能靠"下一次主题变化"来救。
   `broadcastCurrent` 内部同样会先 `applyNativeSurface` —— 补推的不只是令牌，还有原生底色。

合起来才是"新窗口打开即正确"；缺任一条都会在深色 / 带壁纸的主题下暴露出来。

> **窗口材质走同一条时序**：`applyNativeSurface` 除了底色，还会把 `windowMaterial` 交给
> `setTabTheme`（见 §6.2.3）。所以"主题没变但新建窗口"时材质同样会被补上；
> 而重放本身是幂等的（`backdrop` 的 WeakMap + `_paintedFrameColor`），不会反复惊动 DWM。

### 6.1.3 全屏贴边 / 沉浸保留呼吸空：同一条判据派生两种表面形态

**结论**：真实窗口全屏（F11 / HTML5 全屏）时，网页**铺满整窗** —— 四边 4px 内缩归零、
页面圆角归零、分屏格间缝归零；**沉浸模式**（chrome 收起）只是界面走开，网页依旧保留
主题的呼吸空与圆角。

为什么必须区分：两者共用同一条 **chrome 显隐流程**（`chromeHidden = fullscreen || immersiveMode`），
但那是"谁让位"，不是"表面长什么样"。全屏时如果沿用 4px 内缩 + 圆角，屏幕上就是
**一圈底色缝 + 四个圆角缺口**，内容没有独占整窗（用户报告："全屏的时候，网页不应该
保留边距与圆角边框"）。

判据**只此一处**（`LayoutCoordinator#_isEdgeToEdge`）：

| 派生量 | 取值 | 落在哪 |
| --- | --- | --- |
| `edgeToEdge` | `_tabIsFullscreen \|\| win.isFullScreen()` | `applyInitialLayout` 入口 |
| `padTop / padLeft / padRight / padBottom` | 全屏 **0**，否则 `_contentInset*` | 网页 bounds |
| chrome 收起态 `topbarHeight` | 全屏 **0**，否则 `_contentPadding`（那份呼吸空） | 网页 bounds |
| 页面圆角 | 全屏 **0**，否则 `_tabBorderRadius` | `_pageRadius()` → `_setRadiusIfChanged` |
| 分屏格间距 | 全屏 **0**，否则 `SPLIT_METRICS.paneGap` | `_placeSplitPanes` |

- 数值同源：布局与圆角都吃 `_isEdgeToEdge()` / `_pageRadius()`，**不在调用点各写一份
  `isFullScreen()`** —— 否则某天只改了一边，就出现"贴边了但还带圆角"。
- 全屏进出的事件流：`enter-full-screen` / `leave-full-screen` → `setTabFullscreenFromWindow()`
  → `setTabFullscreen()` → `resetTabBounds()` + `applyInitialLayout({ immediate: true })`；
  HTML5 全屏由 Electron 默认让宿主窗口全屏，走的是同一条链（无需单独监听）。
- 圆角只能走原生：`WebContentsView` 的 `setBorderRadius` 是唯一落点，外壳 CSS
  的 `border-radius` 裁不到原生视图（`.webview-container` 只是个透明洞）。

**有意不改的部分**：面板（`_placePanelSlot`：书签 / 历史 / 设置等抽屉）仍是主题圆角与主题内缩 ——
它是浏览器 UI，不是"铺满的网页"。

**跟随贴边派生的部分**：主视图、分屏格、独立侧栏里的网页（连聚焦框），以及**速览卡片**
（`_placeGlanceCards` / `_syncGlanceDeck`）全都吃同一个 `_pageRadius()` 与同一份 `paneGap` ——
全屏时一起归零，否则会出现"网页贴边、浮层还带圆角缺口"的错位。

### 6.2 chrome 玻璃：带壁纸时工具栏透出壁纸（Vivaldi 的 Transparency / Blur）

**结论先说**：主题带**窗口背景**时，navbar / tabbar / rail / 侧栏面板 / 标题栏
全部变成玻璃 —— 看得见壁纸，且**各处深浅完全一致**；`style.transparency` 控制再透多少，
`style.blur` 只控制 **UI 玻璃层**的毛玻璃（**有下限 10px**，见 `MIN_UI_BLUR`）。
壁纸自身的模糊是 `background.blur`，范围 0–60px，**不受 UI 下限夹取**。
无背景时一切照旧（与改造前逐字一致）。

三条落点：

1. **染色与 UI 模糊都按区域分片，背景模糊独立留在壁纸层**：

   | 区域（外壳 DOM / 视图） | 底色（染色） | 毛玻璃 |
   | --- | --- | --- |
   | `#chrome-theme-background`（壁纸层，全窗一块） | 壁纸本体 | `background.blur`（只糊壁纸，0 可关） |
   | `#chrome-top` / `#chrome-bottom`（工具栏、底部条） | `--hira-chrome-bg` | `--hira-ui-blur` |
   | `#chrome-body`（侧栏区 + 主列内容洞，一块合成） | 子区域各自 `--hira-chrome-bg` | `--hira-ui-blur` |
   | 面板视图（`panel`，下载 / 历史 / 书签…） | `--hira-panel-bg`（叠在外壳那层之上） | 透明视图透出外壳的 UI 玻璃结果 |

   前四行里外壳那三处**互不重叠**（top/bottom 在 mid 之外，side 与 content 是 mid 里
   并排的两个孩子），所以每处恰好一层。
   面板是例外：它是**独立 WebContentsView**，跨视图拿不到外壳那层染色，所以自己铺
   一层（`ui-common#injectPanelStyles` 的 `#root`）—— 语义是"**叠在 UI 遮罩之上**"，
   这也正是"面板要读内容 → 默认更实"的来源（0% = 与工具栏同厚）。

   > **范围必须拆开**：`style.blur` 的 10px 下限属于 UI 可读性，不属于壁纸外观。
   > 如果把 UI 模糊挂到 `#chrome-theme-background`，这个下限就会隐式变成"整张背景
   > 至少糊 10px"，`background.blur = 0` 也就失去意义。现在壁纸层只做壁纸自身的
   > `background.blur`，UI 模糊只参与 chrome 玻璃面的 backdrop 合成。

   > ⚠ **面板为什么没有自己的毛玻璃旋钮**：`backdrop-filter` 只作用于**同一份文档**内的
   > 背景，而面板背后是**另一条原生视图**（外壳）—— 跨视图拿不到任何东西，写了也不会糊。
   > 更糟的是：给一个透明视图挂 `backdrop-filter`，它就会去求解一份说不清来自哪儿的
   > backdrop，**别的图层一变（例如 hover 预览卡的阴影）面板的背景就跟着变色**
   > （用户实测到过）。所以那根「面板毛玻璃」已删；面板的毛玻璃观感由外壳
   > UI 玻璃层（`--hira-ui-blur`）统一控制。
   > 真要做"面板独立模糊"，唯一的路是**让外壳来画面板那一块**（同文档才有 backdrop），
   > 那要把面板位的几何从主进程下发给外壳，还要让外壳在那一块**再叠一份**模糊 ——
   > 那本身就是"各自糊各自的"，与本节第 1 条的口径相冲。记为后做项，不假装已支持。

   > ⚠ **"面板"专指面板视图**（下载 / 历史 / 书签…那几条侧栏面板），
   > **不是** rail、**也不是**侧栏区（垂直标签栏）—— 后两者是 chrome UI，跟随
   > `--hira-chrome-bg`。曾经把 `--hira-panel-bg` 铺在 `#chrome-side` 上，
   > 于是"调面板旋钮把垂直标签栏也改了"（用户明确指正过）。


2. **内部一律 `transparent`**（关键，也是最容易做错的一步）：
   `--main-bg-color` 被 navbar → tabbar → 标签条这样**多层嵌套**引用（十来处）。
   带壁纸时把它设成"半透明"会让半透明层**逐层叠加**（0.55 两层 ≈ 0.80，
   三层 ≈ 0.91）—— 嵌套越深越不透明，标签条比地址栏深、rail 比面板深，
   正是要避免的"深浅不一"。所以它给的是 `transparent`：
   所有 chrome 面自己不再挡背景，染色由第 1 条那一层负责。
   附带好处：rail / 面板是**独立的 WebContentsView**，它们自己的页面透明之后
   直接透出外壳那一层，跨视图的颜色也完全一致。

3. **UI 模糊与背景模糊各走一条链**。
   `style.blur` → `--hira-ui-blur`，只用于 chrome 玻璃区域；`background.blur` →
   背景渲染器的 `filter`，只作用于壁纸内层。两者共享视觉素材，但参数、范围与
   默认值完全独立，UI 的最低值不会再把背景一起抬高。

   > ⚠ **需要 `backdrop-filter` 采样背景的元素，别带 `contain` / `container`（血泪教训）**：
   > containment 会截断那个元素自己的 backdrop 采样 —— 它静默退化成"遮罩压在
   > **没糊的**背景上"，看起来就是"这一块的模糊/颜色和别处对不上"。
   > 侧栏区（`#chrome-side`）踩过这个：它为了"窄栏只留图标"的容器查询写了
   > `container: side-column / inline-size`，而同一条带又用 backdrop-filter 采壁纸，
   > 结果用户一眼看出"垂直标签侧栏的模糊效果颜色和其他界面分裂根本不一样"。
   > **结论**：容器（以及 `contain`）只挂在**同宽、不带玻璃**的内层元素上
   > （现在挂侧栏骨架 `.vtabs` 与 `.navbar-side-header`，常驻与浮出共用同一条声明）；
   > 而 chrome 各带**根本不用 backdrop-filter**（模糊只在壁纸层），也就没有这个隐患了。

4. **附属规矩：in-shell 的 chrome 面必须用 `--main-bg-color`（chrome 底色），
   不能用 `--hira-bg-surface`**。两者在不带壁纸时是同一个值（主题主背景），
   但带壁纸时前者是 `transparent` —— 用错的那个会自己留一块不透明色块
   （书签固定栏踩过：整条工具栏就它一截挡着壁纸）。判据很简单：
   **它是 chrome（工具栏/侧栏/固定栏/状态条）还是内容（卡片/浮层/内部页）？**
   前者用 chrome 底色，后者用 surface 系列。

   同一判据顺手清掉的一批**没接进主题体系的遗留 token**（原先只有硬编码浅色兜底，
   于是深色主题下是白块）：下载栏的 `--downloadbar-bg`（chrome → 玻璃色）、
   `--panel-bg` / `--surface-muted`（内容 → 抬升面）、`--progress-bg` (轨道)、
   `--list-hover-bg` / `--button-hover-bg` (hover)、`--accent-primary(-hover)` (强调色 ——
   弹窗与密码管理器的按钮也吃它)。

   **同类的还有"根本没设颜色"的地方**：rail 渲染页此前一个字都没写 `color`，
   而 rail 的图标是 SVG 且用 `stroke="currentColor"` —— 于是 `currentColor` 一直回落到
   初始值（黑），深色主题下就是"黑图标压在深色 rail 上"。修法是在 rail 页的根上
   `color: var(--text-color)`（= 主题前景色）。**通用规矩：凡是靠 `currentColor` 取色的
   层，它的祖先必须显式给 color。**

**取值链**（唯一一处，`shared-types/theme.mjs` 的 `resolveChromeOverlay*`）：

```
glassesWindow = background.kind !== 'none' && applyTo 含 'window'
chromeAlpha   = !glassesWindow                                   ? 1        （无壁纸：不透明，与改造前逐字一致）
              : style.chromeOverlay != null                      ? 它       （作者显式声明，0 也是有效值）
              : CHROME_GLASS_ALPHA * (1 - style.transparency)                （老字段回退）
chromeBg      = chromeAlpha >= 1 ? 主题底色 : rgba(resolveChromeOverlayColor(theme), chromeAlpha)
```

`CHROME_GLASS_ALPHA = 0.55` —— 带壁纸时默认就有 45% 的透视。
**为什么给默认值而不是"作者不说就完全不透明"**：主题带了壁纸却不透出来，
用户看到的仍是"主题换了、界面没变"，而那正是这条特性存在的意义。
0.55 是"壁纸明显可见、标签标题仍读得清"的折中。

### 6.2.1 UI 遮罩 vs 壁纸遮罩：**两组旋钮，各自独立**

这是主题编辑器里最容易混淆的一处，所以把边界写死：

| | 管什么 | 字段 | 编辑器控件 |
| --- | --- | --- | --- |
| **UI 前景** | 工具栏 / 标签栏 / **rail** 及其组件的图标与文字 | `colors.chromeFg`（默认 = `colors.fg`）**可写 `"auto"`** | 颜色区：「UI 前景」（受顶部「前景自动」总开关锁死/解锁） |
| **面板前景** | **面板视图**（下载 / 历史 / 书签…）里的字与图标 | `colors.panelFg`（默认跟随 UI 前景）**可写 `"auto"`** | 颜色区：「面板前景」（同上，随总开关） |
| **侧栏网页标题栏前景** | **独立侧栏（网页浏览）顶部那条标题栏**的字与按钮 | `colors.webSidebarFg`（默认跟随 UI 前景）**可写 `"auto"`** | 颜色区：「侧栏网页标题栏前景」（同上，随总开关） |
| **UI 遮罩** | 工具栏 / 底部条 / 内容缝 / 侧栏区压在**壁纸**上的那一层 | `style.chromeOverlayColor` + `style.chromeOverlay` | 外观区：「UI 遮罩颜色」+「UI 遮罩不透明度」 |
| **面板遮罩** | **面板视图**上**再叠**的那一层，所以默认更实 | `style.panelOverlay`（默认跟随 UI 遮罩） | 外观区：「面板遮罩不透明度」 |
| **壁纸遮罩** | **壁纸本身**（网页四周 / 新标签页）上面那一层 | `background.overlayColor` + `background.overlay` | 背景区：「遮罩颜色」+「遮罩不透明度」 |

- **三档前景的分工（一处调、一层生效）**：`chromeFg`（UI）/ `panelFg`（面板）/
  `webSidebarFg`（侧栏网页标题栏）**各管一层**，后两者留空 = 跟随 UI 前景。
  落点全在**子树根**上重算三档文字色（`--hira-text-primary/secondary/tertiary`）：
  · 面板 —— `ui-common#injectPanelStyles` 的 `#root`
  · 侧栏网页标题栏 —— `ui-common#webSidebarHeader` 的 `.hira-ws-header`
  于是那一层里**共享组件**也一起跟上，不必逐个组件去接。
  ⚠ **三档必须一起重算**：只改主文字会让"次要/辅助文字"半截留在旧色上
  （深色面板配浅色前景时那几行直接看不见）。派生值由令牌给
  （`--hira-panel-fg-soft/-muted`，`color-mix(fg 72%/55%, transparent)`）——
  作者**没设**那一档时它们就是主题原本的 `textSoft` / `textMuted` ⇒ 默认逐字不变。
- **rail 的图标属于 UI 前景**（用户报过："rail 的图标还是狗屎一样的纯灰不跟一起调节"）：
  图标是 `stroke="currentColor"`，所以颜色完全由 CSS 的 `color` 决定 ——
  它曾经写的是 `--hira-text-secondary`（**内容面**的一档灰），于是那列图标永远死灰、
  跟前景旋钮毫无关系。现在(`ui-taskoverlay`)用 `--hira-chrome-fg`，与 navbar / tabbar
  一起被同一根旋钮调；悬停只给底色（不再"提亮"——已是前景色，没有可提的），
  选中态仍走强调色。
- **UI 前景为什么能"不影响其他界面"**：`--hira-text-primary` / `--text-color` 绑的是
  `colors.chromeFg`，而内容面读的是 `--text`（= 内容前景 `colors.fg`）。
  但**光靠"两套令牌分着"是不够的** —— 这两个名字太通用，跨场景共用件（`ui-modal`、
  通用列表…）自然会引用它，于是"只调浏览器 UI 前景"也会顺带改掉内部页 / 子窗口的文字
  （用户明确指正过："为什么还是会波及到其他界面使其变色"）。
  所以**内容面在各自的令牌应用点上主动剪断**（`--hira-text-primary = --text`）：
  · 内部页 —— `pages/_shared/runtime.js#initTheme`
  · 子窗口 —— `renderer/subwindow/index.html`（所有简单子窗口共用这一个入口）
  浏览器 UI 侧一个字不动；主题编辑器的**预览子树**例外（它就是要显示草稿的 UI 前景，
  令牌直接写在子树根上，压得住）。
- **「面板」的边界（用户明确指正过）**：面板遮罩 / 面板前景**只作用于面板视图**
  （下载 / 历史 / 书签…），**不作用于 rail、也不作用于侧栏区（垂直标签栏）** ——
  后两者是 chrome UI，走 UI 遮罩 / UI 前景。见 §6.2 第 1 条的表。
  面板**没有**自己那根毛玻璃旋钮（跨视图做不到，且会引出不可预测的 backdrop 求解 ——
  见 §6.2 第 1 条那段说明）。
- **颜色都可单独设**，不是"只能跟着主题底色走"：UI/面板遮罩色默认跟随底色（保持改造前的观感），
  但**可以改成白/任何色**；壁纸遮罩色默认白。
- 未声明与"明确要 0"**必须分得开**：`chromeOverlay` / `panelOverlay` 的
  `null`（没说过）与 `0`（明确要求全透）分别走不同分支 —— 写成 `num(x, 0)`
  会把这两件事混成一个。
- `style.transparency`（Vivaldi 的 `alpha`）**保留为兼容回退**：作者没给 `chromeOverlay` 时
  才用它换算，所以导入的 Vivaldi 主题行为不变；编辑器不再单独暴露它
  （否则又变成"两个滑杆调同一件事"）。

#### 「自动」前景：按壁纸明暗自动选黑 / 白

壁纸是会变的（「每日一图」**每天换一张**），而前景色写死在主题里 —— 一张亮照片配白字 =
什么都看不见。所以上面三档前景都接受**哨兵值** `"auto"`（唯一真源：`shared-types#AUTO_FG`），
由一条公式算出该用黑还是白：

```
有效亮度 lum = 遮罩色 ⊕ 壁纸亮度        （在**亮度空间**做 alpha 合成）
面板再叠一层：lum = 遮罩色 ⊕ lum        （面板比工具栏实，见 resolvePanelOverlay）
lum ≥ 0.5 → #111111（深字）    否则 → #ffffff（浅字）
```

- **公式只有一处**（`shared-types#autoFgFor`）；判黑/白的阈值与"品牌色上该放黑字还是白字"
  共用同一条（`AUTO_FG_THRESHOLD`）—— 阈值只此一处，改这里两处一起改。
- **壁纸亮度从哪来**：主进程 `theme-luminance.js` —— `nativeImage.createFromBuffer`
  → `resize({ width: 64 })` → `toBitmap()`（BGRA）逐像素算 WCAG 相对亮度取**平均**
  （跳过全透明像素）。一张 4K 照片也只遍历约 3k 像素。按**图片身份**缓存
  （`user:<key>` / `plugin:<id>:<path>` / `daily:<当天 URL>`）—— 跨天换图 ⇒ 身份变了 ⇒ 自然重新量。
  `theme-service` **同步读缓存**（`peek`），没量过就顺手起一次后台测量，量**成功**后发一次
  `background` 主题事件 —— 与「每日一图」图到了再重发一次是**同一条路**，所以"自动前景"
  会在图到位后的下一拍自动跟上，不需要任何额外机制（也正因此 `ensure` 在缓存命中时
  **不能**回调 `onReady`，否则会 emit ↔ 读缓存死循环）。
- **为什么在主进程量**：资产图在本地（主进程拿得到字节）；「每日一图」是**远程**图，
  渲染侧 `<img>` + canvas `getImageData` 会被 CORS 挡掉（tainted canvas），
  而主进程的 `net.fetch` 不受同源策略约束。
- **拿不到实测值时**退回"按主题底色判"（`palette.bg`），仍然是个确定的值 —— 不会出现空令牌，
  且与渲染侧（编辑器的"自动"行）**跑的是同一条 `autoFgFor`**，于是"显示的自动色 = 真会生效的色"。
- **壁纸只有一份、且只在窗口面**：`applyTo` 里出现 `newtab` 时归一化必然补上 `window`
  （`normalizeThemeBackground`），所以"有壁纸但 chrome 是实底"这种状态已不存在 ——
  判据仍是 `glassSurface`（= `applyTo` 含 `window` 且背景不是 `none`）。
- **侧栏网页标题栏那一档**压在**实底**上（`.hira-ws-header` 的 `background: --hira-bg-surface`），
  所以它只按 `palette.bg` 判，不受照片明暗影响。
- 编辑器：颜色区顶部一个**「前景自动」总开关**（三档一个入口，不逐行给按钮 —— 三档压在
  同一张壁纸上，判据是同一份亮度，逐行开关只会产生互相矛盾的状态）。开 = 三档一起写
  `auto`，取色器 / hex **禁用并显示生效值**（读取口是 `field.getAuto()` → `autoColorFor()`，
  与 `EFFECTIVE_VALUE` 同一纪律：显示值必须来自共享层 resolver）；关 = 三档写回**此刻自动
  算出来的那个色**，于是用户看得见自己从哪儿开始手调。开关本身不新增字段：状态由数据推
  （`anyForegroundAuto`：三档里有 `auto` 就算开，于是导入包 / 老数据里只锁了一档时也能解开）。
- 开关只在 `supportsAutoFg` 为真的来源（**图片 / 每日一图** —— 主进程能拿到字节量亮度的两种）
  或主题里已存 `auto` 时出现。视频（画面在动，没有单一亮度）、纯色 / 渐变（没有壁纸）、
  桌面壁纸（暂时没有取系统壁纸字节的通道）都不出现 —— 摆一个必然退回底色判定的开关
  只会误导作者。
- ⚠ 量的是**平均**亮度、且在**亮度空间**做合成：对白/黑这类中性遮罩是精确的，
  彩色遮罩会有一点色相偏差（可接受）。

> 为什么这一节值得单独写：这两组旋钮曾经分别叫「透明度」与「遮罩浓度」，
> 用户调错那一根后得到的是"调不透明度没反应"，而根因只是**命名与显示没对齐**。
> 规则：**任何"生效值可能与作者声明不同"的控件，显示值必须取自共享层的 resolver**，
> 不允许视图自己算（`resolveVeilColor` / `resolveChromeOverlay*` 就是那三处 resolver）。


### 6.2.2 覆盖式视图（跨视图浮层）的底色：**别做**，或者自己画壁纸镜像

**先说结论**：侧栏**只有 Edge 型自动隐藏**才有一条独立覆盖视图 —— `renderer/sidebar-float`
（静止是 56px 图标 rail 照常占位；指针贴边展开时由主进程把这条浮层盖在网页上，网页不缩进、
不重排）。全功能型仍然是「同一块 `#chrome-side` 在 `restWidth`(0) ↔ `revealWidth` 之间改宽」，
玻璃由外壳那一层统一铺。
而那条浮层确实**拿不到 backdrop**（见下面的约束），所以它的底色是**不透明**的 theme 表面色
（`renderer/sidebar-float/index.html` 的 critical CSS + `--main-bg-color`），不做毛玻璃。

**约束为什么成立**：任何"盖在网页之上"的独立 `WebContentsView` 都**拿不到 backdrop** ——
它背后是另一条原生视图，而 `backdrop-filter` 只作用于**同一份文档**内的背景
（Chromium 合成器上跨视图不可见；这也是 rail / 面板那几处只能靠外壳铺一片的原因）。
于是它只有两条路：

1. **不做独立视图**（全功能型 / 侧栏主体）—— 把要画的 UI 留在 chrome 本体里，靠"改宽 / 改显隐"实现，
   玻璃跟着外壳走。副作用最小，也是侧栏主体选它的原因；
2. **自己画一份窗口壁纸的镜像**，再按外壳那套玻璃染色（`backdrop-filter: blur(--hira-ui-blur)` +
   镜像图内层 + `--hira-chrome-bg` 染色层，与 `#chrome-theme-background` 逐字同构）。
   镜像必须按**窗口尺寸 + 整体平移**画（`background-size: cover` 得由浏览器按窗口算，
   否则拼缝两侧颜色对不上），几何事实只有主进程有（`#getWindowContentSize` 等）——
   渲染层只落 CSS 变量，不复刻轨道算术。

   **反例（已移除）**：新标签页曾按这条画过一份镜像 —— `LayoutCoordinator#getWallpaperFrame(wc)`
   返回 `{ left: -offset.x, top: -offset.y, width, height }`，经 `layout:wallpaper-frame` 下发，
   页面把矩形写到背景层外层。静态截图里接缝是对的，但**面板 / 侧栏动画每帧都在改标签视图的
   bounds**，而镜像几何只能事后经 IPC 取回，永远慢半拍 —— 表现就是壁纸跟着界面一起动、
   接缝补不上、然后闪一下。新标签页已改为**透明画布**（视图 `#00000000` + body 透明）
   直接露出窗口外壳那一份，页里一个背景图层都没有，自然无从跟着动。
   只有"盖在网页之上、又必须显示壁纸"的覆盖视图才轮到这条镜像画法。

⚠ 走第 1 条时**别再补遮罩**：覆盖物盖住的那些 chrome 带底下**已经有外壳铺过的同一层玻璃**，
再铺就是半透明**叠加**（0.55 叠 0.55 ≈ 0.80）—— 表现是"覆盖物左边比它盖住网页的那一段明显更实"。

> ⚠ **别指望覆盖视图显示"网页的模糊"**：那是跨视图模糊，Chromium 做不到。
> Edge / HiraRT 的覆盖侧栏都只能"近不透明"（纯色 / 90%），这也是第 1 条更划算的原因。
> ⚠ **不要给 rail 渲染页（`#hira-task-overlay`）也补一层**：它是**常驻**在 rail 那一列
> （不是覆盖态），底下的 `#chrome-content` 已经铺了玻璃 —— 它铺一层就会变成"rail 比
> navbar 更实"。rail 的**贴边唤出态**（`setRailReveal`）现在与全功能侧栏的占位型
> 自动隐藏一致：唤出时进入正常轨道并推挤网页，不绘制第二层覆盖背景。

### 6.2.3 窗口材质（亚克力 / Mica）：窗口级系统模糊，不是"再叠一层假玻璃"

**结论先说**：主题新增 `style.material`，取值 `none` / `acrylic` / `mica`。开启后由 **DWM** 把窗口
背后的内容模糊后画进窗口，chrome 各层只负责"不挡路"—— 没有第二层假毛玻璃、也没有不透明底板。

| 材质 | 原生取值 | 观感 |
| --- | --- | --- |
| `none` | — | 不启用系统材质，窗口不透明；玻璃效果只来自壁纸 + 染色 |
| `acrylic` | `acrylic` | 窗口**后方内容实时模糊**：最透、最"磨砂" |
| `mica` | `mica` | 模糊的是**桌面壁纸**（静态、更克制），更接近 Win11 原生窗口 |

| 问题 | 结论 |
| --- | --- |
| 系统 API 有吗 | **Win11 22H2（Build 22621）及以上**有官方能力：`BrowserWindow#setBackgroundMaterial(material)`（`@platform win32`）。它内部已完成 `DwmExtendFrameIntoClientArea(-1, …)` 与窗口透明设置，**不需要 `transparent: true`**，`frame: false` 即可 |
| Win10 呢 | **没有公开 API**。Win10 的 `SetWindowCompositionAttribute + ACCENT_ENABLE_ACRYLICBLURBEHIND` 是非公开 FFI，且要求窗口 `transparent: true`；本项目主窗是 `transparent: false` ⇒ 那条路**永远不可能生效**，判定为死代码、**不实现**（不引 koffi、不建透明窗）。Win10 上诚实降级为**染色玻璃**（§6.2 那一套） |
| 为什么不自己做 CSS 毛玻璃 | `backdrop-filter` 只能采样**同一份文档**，糊不到桌面。要透出桌面只有系统 DWM 一条路 |
| 两种材质能调染色 / 透明度吗 | **原生层没有这两个参数**（`setBackgroundMaterial` 只认材质名）。可调的只有 chrome 层既有字段：`style.chromeOverlayColor`（染色）+ `chromeOverlay` / `panelOverlay`（浓度）+ `blur`（壁纸模糊）—— 见下面的「材质微调」 |

**三条判据各自唯一**（`packages/shared-types/src/theme.mjs`）：

```
glassSurface(theme)       = style.material !== 'none' || glassesWindow(theme)   // "这一面是不是玻璃"
windowMaterialSpec(theme) = { material, active: material !== 'none' }          // 交给原生的规格
resolveChromeOverlay*     = chromeAlpha 的不透明/半透明判据改为吃 glassSurface
```

- `glassSurface` 是**唯一**判据，替换了原先三处 `glassesWindow(...)`。于是"开了亚克力但没选壁纸"
  同样得到 0.55 的 chrome 半透明与 `--main-bg-color: transparent` —— 材质与壁纸共用同一条玻璃链，
  而不是"材质模式再写一套规则"。
- 材质**不进** `background.kind`：它不是"背景图"，是窗口表面属性；混进背景模型会污染壁纸的
  资产库 / 应用范围 / 遮罩语义。

**原生落点只有三处**：

| 层 | 做什么 |
| --- | --- |
| `infra-window/src/backdrop/capabilities.js` | 能力探测（纯函数、结果缓存）：`platform` / `build`（解析 `os.release()`）/ `nativeMaterial`（`win32 && build >= 22621`） |
| `infra-window/src/backdrop/index.js` | 门面：`applyWindowBackdrop(win, { material })` / `releaseWindowBackdrop` / `getWindowBackdrop`；`MATERIAL_TO_NATIVE` 是**主题词汇 → Electron 词汇**的唯一映射表（现为 `{ acrylic: 'acrylic', mica: 'mica' }`），加 `tabbed` 或让某个 id 落成别的原生值只改这张表 |
| `LayoutCoordinator#_applyWindowMaterial` | `setTabTheme({ windowMaterial })` 里的唯一落点：**材质生效时不写 `win.setBackgroundColor`**（写了就把 DWM 的透明盖死），未生效 / 退回时才把 `frameBackgroundColor` 写回去 |

**幂等是硬要求**：主题每次发布都会重放 `setTabTheme`，若每次都真的调 `setBackgroundMaterial(...)`，
DWM 会整窗重绘（无材质模式下表现为闪一下）。所以两端都做了短路：
`backdrop` 用 `WeakMap<win, { material, applied }>`；`LayoutCoordinator` 用 `_paintedFrameColor`
（空串 = 材质态，窗口底色归 DWM）记住"上一次真的写了什么"。

**渲染层怎么知道要变玻璃**：`surface` 载荷。`theme-runtime#applyNativeSurface` 返回
`{ material, applied, supported, reason, message }`，随 `theme:changed` 广播的 `payload.surface`
下发；`theme-controller#applyBackground(background, surface)` 只要 `material !== 'none'` 就置
`documentElement.dataset.themeBackground = '1'` —— 与壁纸**同一个开关**，外壳各带随即铺
`--hira-chrome-bg`、`--main-bg-color` 变 `transparent`。

> ⚠ **晚加载页面必须补同一口径**：`theme:tokens` / `theme:preview` 是"页面起来后主动取"的读口，
> 它们不经过 `publish()`，拿不到 `lastPayload.surface`。少了这一格，晚加载的 rail / 面板会
> 以为"没开材质"而铺不透明底，把亚克力自己盖住。所以 `ipc/theme.js` 用
> `themeRuntime.describeSurface(theme)` 统一回答（`supported` 永远来自能力探测、草稿的
> `applied` 恒假 —— 草稿并没有应用到窗口上）。

> ⚠ **Win10 上"选了材质"的显示**：`surface.supported === false` 时编辑器显示
> `WINDOW_MATERIAL_UNSUPPORTED_HINT`；实际视觉退回染色玻璃 —— **不谎报已生效**。

**"没有不透明垃圾层"的链路依据**（逐层核对过）：

1. 外壳就是窗口本体：`ChromeView` 是包 `win.webContents` 的**假视图**，天然位于所有
   `WebContentsView` 之下；外壳的 `html / body / #root` 全透明 ⇒ DWM 的模糊直接可见。
2. `#chrome-theme-background` 只承担 `filter`；材质期不铺壁纸时它**没有**任何底色。
3. chrome 各带只铺 `--hira-chrome-bg`（0.55 的半透明染色），`--main-bg-color` 为 `transparent`；
   `#chrome-content` 的玻璃态被更高特异性规则覆盖为透明 —— 不存在"两层半透明叠加变实"。
4. rail / 面板是独立视图，`surfaceBackgroundColor` 在 `glassSurface` 成立时是 `#00000000`
   （`theme-runtime#applyNativeSurface`），它们的页面自身也是透明底。
5. 标签视图不参与：画布固定 `#ffffff`（§6.1.1），它被 4px 内缩圈在 `#chrome-content` 里，
   不覆盖 chrome 的玻璃区域。

**材质微调（编辑器「材质与玻璃」分组）**：原生层只认材质名，所以"更透一点 / 更实一点"全部落在
chrome 层那几项上 —— 它们本来就是玻璃链的既有字段，**没有为材质新增任何 schema 字段、也没有新增图层**：

| 控件 | 字段 | 对材质的作用 |
| --- | --- | --- |
| UI 遮罩颜色 | `style.chromeOverlayColor` | 玻璃的**染色**（默认跟随主题底色，浅色主题上不会变脏） |
| UI 遮罩不透明度 | `style.chromeOverlay` | 工具栏的浓度：越低越透 |
| 面板遮罩不透明度 | `style.panelOverlay` | 面板（侧栏 / 浮层）的浓度，叠在 UI 遮罩之上 |
| UI 模糊 | `style.blur` | 只糊 chrome 玻璃面，不是系统模糊；下限 10px，不夹取背景图 |

「套用推荐值」把这三个浓度**一次**写进草稿（`format.js#MATERIAL_RECOMMENDED`，
经 `patch-many` 意图 → `core.js#patchDraftMany`，只触发一次预览）：

- `acrylic` → `chromeOverlay 0.28` / `panelOverlay 0.5` / `blur 20`（更透，让实时模糊看得出来）
- `mica` → `chromeOverlay 0.42` / `panelOverlay 0.6` / `blur 10`（更实，贴近原生窗口的克制感）

只给**浓度**不给**颜色**：染色色默认跟随主题底色，硬写一个色会在浅色主题上显脏。
套完仍可继续拖滑杆（推荐值只是起点，不是锁死的开关）；`material === 'none'` 时这一行不出现，
下拉下方的说明文案由 `format.js#materialHint` 按材质给出。

**内置的四条材质预设**：`hira-acrylic-light` / `hira-acrylic-dark` /
`hira-mica-light` / `hira-mica-dark`（`theme-builtins.js`）。

- 四条都由 `materialVariant(HIRA_LIGHT | HIRA_DARK, { material })` **派生**，不再手抄四份配色 ——
  手抄只要有一份忘了改，"切换预设时画面上只有材质在变"这条不变式就悄悄破了。
- 除 `style.material` 外与 `hira-light` / `hira-dark` **逐值相同**（两份 Mica 例外：
  `style.chromeOverlay` 钉 0%，见下条）—— 卖点是材质本身，配色若也一起变，
  就分不清"这是材质的效果"还是"我换了配色"。
- 两份 Mica 的 **UI 遮罩不透明度钉在 0%**（`chromeOverlay: 0`）：Mica 卖的就是系统材质，
  再压一层 55% 主题色等于把材质盖掉一半。面板遮罩**显式钉住** `panelOverlay: 0.6`
  （`format.js#MATERIAL_PRESETS` 的 mica 推荐值）—— 面板是独立视图、盖在网页之上，
  若跟随 UI 遮罩一起归零会直接读不清。注意取值判据必须是 `!= null`：
  `0` 是有效值，"自动透出"就是靠它。
- `background.kind` 保持 `none`：材质与壁纸是**两条路**（壁纸是自己画一层，材质是把窗口交给
  DWM），挂上壁纸反而会把系统模糊盖住。
- `style.blur` 在材质预设里保持 0：材质本身没有壁纸可糊，UI 下限只影响玻璃面，
  对系统材质观感无影响。
- 库里靠卡片角标「亚克力」区分（`ui-panel-themes/window/parts.js` +
  `shared/format.js#materialBadge`）：两条预设与基础款的配色完全相同，只靠渐变卡面分不出来。
  `MATERIAL_BADGES` 同时给了 `mica →「Mica」`（自建主题切到 Mica 也带角标），
  卡面左上角那枚 `thm-card__flag` 会把「视频」与材质角标合并成一行。
- 用户自建主题切到 Mica 时不需要预设：它不改配色，直接在编辑器里把「窗口材质」
  切到 Mica 即可（内置的两条 Mica 预设只是把"浅/深 + Mica + UI 遮罩 0%"一次给全）。

### 6.3 遮罩（veil）：**颜色 × 不透明度**，两件事正交

背景之上那一层遮罩由两个字段决定，**必须各自独立生效**：

| 字段 | 作用 | 编辑器控件 |
| --- | --- | --- |
| `background.overlayColor` | 遮罩是什么色：**白 = 提亮**（默认）、黑 = 压暗（浅色文字更清楚） | 「遮罩颜色」取色器 |
| `background.overlay` | 不透明度 0~1，**始终**作为 alpha | 「遮罩不透明度」滑杆 |

口径只有一处（`shared-types/theme.mjs`）：`resolveVeilColor(bg) = bg.overlayColor || '#ffffff'`，
输出 `withAlpha(resolveVeilColor(bg), bg.overlay)`。**主进程算 CSS 与编辑器的取色器共用它** ——
编辑器显示的就是实际生效的那个色。

> **一个界面命名上的坑（已修）**：主题编辑器里曾经有两个都能被叫成"透明度"的滑杆 ——
> 外观区的「透明度」管的是 **chrome 玻璃**（navbar/tabbar/rail，见 §6.2），
> 背景区的「遮罩浓度」管的是**壁纸上的遮罩**。用户调错了那一根，就会以为
> "调不透明度没反应"。现在两个名字各自说清范围：**「工具栏透明度」**（hint: 只影响工具栏）
> 与 **「遮罩不透明度」**（hint: 只影响遮罩层）。

> ⚠ **已经踩过的两处坑**（都在 `themeBackgroundCss` 里）：
> ① "显式给了 `overlayColor` 就直接用它（alpha=1）"→ 选了白色、不透明度拉到 0
>    仍会盖出一片不透明纯白，把壁纸整个吃掉；
> ② 没给色时回落到"背景色"→ 深色主题下**实际生效的是近黑色**，而编辑器显示白
>    （显示 ≠ 生效），于是"调不透明度没反应、永远是黑的"。
> 两处都修了：**颜色与不透明度正交，且默认色固定为白**（内置主题都显式给了色，不受影响）。

### 6.4 视频背景（动态壁纸）：**与图片同一条链，只有"怎么画"不同**

`background.kind` 新增 `'video'`。**它复用图片那一条链的每一个环节** ——
选文件 → 拷进资产库 → `background.path` 存 key → 协议把它变成可加载地址 →
主进程算好"这一面该画什么" → 渲染侧纯赋值。新增的东西只有三处：

| 环节 | 图片 | 视频 | 为什么必须不同 |
| --- | --- | --- | --- |
| 协议响应 | 一整块 `200` | **必须支持 `Range` → `206`** | `<video>` 的媒体管线按段取流；对 Range 请求回 200 会直接被拒（见下） |
| 体积额度 | 8MB | **64MB** | 一张照片几 MB，一段十几秒的循环视频几十 MB 是常态 |
| 画法 | `background-image` | **一个 `<video>` 元素** | 视频不是 CSS 能表达的东西 |

**其余全部**沿用：`path` / `position`（映射到 `object-fit`）/ `opacity` / `blur` /
`overlay` + `overlayColor` / `applyTo` / 资产库 / 导出导入 / 插件主题同样可声明。

#### 6.4.1 `Range` 是硬要求，不是优化

`<video>` 在加载时会发 `Range: bytes=0-`，并且**在拿到 200 全量响应时可能直接停止** ——
Chromium 的 `MultiBufferDataSource` 期待的是 `206 + Content-Range`。
所以两个资产协议（`hira-theme://` / `hira-plugin://`）都改成走**同一个响应构造器**
（`main/asset-response.js`），它：

- 解析 `Range` 头 → 用 `fs.createReadStream(abs, { start, end })` **流式**返回 `206`；
- 没有 Range → `200` + 正确 `Content-Length`；
- 一律带 `Accept-Ranges: bytes`（不发这个头，Chromium 连"能不能分段取"都不试）。

**为什么手写而不是把 `net.fetch(file://…)` 的结果透传**：透传就得赌 Chromium 的
file 协议实现是否支持 Range、以及它返回的头能不能原样用；而这里是**安全边界所在的文件**，
"文件怎么发出去"这件事只该有一份实现、且必须是确定的。

#### 6.4.2 一个共享的「背景层渲染器」：`shared-types/src/theme-background.mjs`

背景要画到**四个地方**（外壳 / 新标签页 / 编辑器迷你预览 / 内部页），
它们里有两个（外壳与预览）是打包的 ESM，两个（内部页）是**未打包的静态页**。
所以渲染逻辑不能各写一份 —— 新建一个 canonical 模块，导出**一个函数**：

```
applyThemeBackground(container, spec)   // spec = themeBackgroundStyle(bg, scope) 的产物
```

- `spec.mode` 为 `'css'` 时走 `background-image` 三元组（图片 / 渐变 / 纯色，与改造前逐字相同）；
- 为 `'video'` 时在容器里**就地复用**一个 `<video class="hira-bg-video">`（改 `src` 不重建 ——
  重建会让浏览器重新拉一遍整个文件），并把它自己的样式（`position/inset/object-fit`）
  用一份自注入的 `<style>` 带上；
- 为 `'none'` 时清空并**销毁**视频元素（`pause()` + 摘 `src` + `load()`，把解码器还回去）。

内部页靠 `electron.vite.config.js` 的 `sync-shared-contracts` 把这份文件复制成
`hira://shared/theme-background.mjs`（与 `favicon-src.mjs` 同一条机制）——
于是「外壳怎么画背景」与「内部页怎么画背景」是**同一份代码**，不可能漂移。

`opacity` / `filter` 仍写在**容器**上（不动），视频是它的子元素 ⇒ 两档照旧一起生效。

#### 6.4.3 刻意不做的事（把话说死）

- **不做声音开关**：动态壁纸出声是骚扰，且自动播放策略本来就要求 `muted`。
  所以 `muted` / `loop` / `playsinline` **硬编码**，不进 schema ——
  少两个字段就少两处要同步的地方。想要声音的人应该去用网页，而不是壁纸。
- **不做「自动前景」判定**：`colors.*Fg = "auto"` 依赖"这张壁纸有多亮"这一个数，
  而**动态画面没有单一亮度**（首帧亮、中段可能全黑）。取首帧反而会给出一个
  错误的安全感 —— 这比不给更糟。所以视频背景时自动档**退回按主题底色判**，
  编辑器在选中视频来源时给一句明确提示，让作者手选前景色。
- **不做视频缩略图**：主题卡片不抽首帧（那要么进主进程解码、要么进渲染层 canvas）。
  卡片用主题自己的配色渐变 + 一个「视频」角标，够区分。
- **不做「跟随时长/倍速」**：壁纸循环播放是唯一合理行为。

#### 6.4.4 体积额度的分档（安全边界一条不动）

| 通道 | 图片 | 视频 |
| --- | --- | --- |
| 资产库（`theme-assets.js`） | 8MB | **64MB** |
| `hira-theme://` / `hira-plugin://` 单文件 | 8MB | **64MB** |
| 主题包（zip）单资产 | 8MB | **64MB** |
| 主题包（zip）总量 / 包本身 | 24MB / 32MB | **128MB / 160MB** |

放宽的**只有体积**：扩展名白名单、目录穿越守卫、目录前缀比较、"只有已启用的插件
才读得到" —— 一条不动。视频（mp4/webm/ogv）是**不可执行**的容器，作为 media
加载不会跑脚本；这也是它敢拿 8 倍额度的前提。

## 7. 调度：四种策略（合并 Vivaldi 与旧 Hira）

设置键 `app.theme.schedule`：

| 模式 | 语义 | 来源 |
| --- | --- | --- |
| `none` | 固定使用当前主题 | Vivaldi "不切换" |
| `system` | 跟随系统深浅（在 light 主题与 dark 主题各指定一个） | Vivaldi "跟随系统" + 旧 Hira `darkMode=2` |
| `night` | 白天/夜间两个主题，**21:00–06:00 为夜间**（沿用旧 Hira 的 `isNightTime`） | 旧 Hira `darkMode=0` |
| `manual` | 任意条 `{ theme, from, to }` 时段表 | Vivaldi "手动定时" |

落地：`theme-schedule.js` 在主进程跑（`setInterval` 每 10s 判定，对齐旧 Hira），
命中变化时调 `themeService.setActive(themeId, { reason: 'schedule' })` → 走同一条广播链路。
**调度只改"当前主题"，不改配置文件**（用户手动选择即自动切回 `none`，避免"我选的又被调度顶掉"）。

## 8. UI 规划

### 8.1 主题库（`hira://themes` 主题页的默认视图，学 Vivaldi「资源库」）

- 网格列出现有主题，按来源分组：**缩略图（配色/渐变底）+ 名称 + 明暗徽标 + 来源 + 配色条**，
  当前主题带勾选角标。
- **点卡片 = 应用（即时生效，不用重启）+ 把它送进右侧编辑器** —— 用户点一张卡片想表达的
  就是"我想用这个（并看看它）"，分成两个入口只会让人先点错一次。
- 顶部工具条：`新建主题`（以当前主题为起点，**另起一份 id 为空的草稿**）/ `导入主题…`（.zip，兼容 Vivaldi 主题包）/
  `重新扫描`（装了主题插件后不必重启）。
  > 「新建主题」的两条硬要求（都踩过）：① 必须先把视图切回「主题库」—— 编辑器挂在那一页，
  > 停在「调度 / 私密窗口」时草稿会画进 `display:none` 的容器，表现就是按钮没反应；
  > ② 必须派生**新**草稿（`theme:draft` 的 `asNew`）—— 起点若是自建主题，不带它会被当成
  > "原地编辑同一份"，界面看起来毫无变化。成功后状态条还会写一句"已新建草稿…"。
- 编辑器页脚另有 `导出…`：**导出编辑中的那条主题**（未保存的草稿不显示它 —— 草稿没有
  id，导出去也没有身份）。导入/导出都在主进程弹系统对话框，渲染层不碰本地路径。

### 8.2 编辑器（学 Vivaldi「编辑器」，左右分栏 + 实时预览）

- **同屏**：左边主题卡片列表、右边预览 + 编辑器。编辑主题时最需要的是"改一下、看一眼"，
  分页会逼用户来回切，而切换本身不产生任何信息（Vivaldi 分两页是因为它的库是全屏网格）。
- **颜色页**：背景 / 前景 / 表面 / 强调 / 高亮 / 边框 六个取色器（`<input type=color>` +
  hex 输入双向同步；`rgba(...)` 会被转成 `#rrggbb` 交给控件，见 `format.js#toHexInput`）。
- **背景页**：来源（无 / 纯色 / 渐变 / 图片 / 每日一图 / 桌面壁纸）+ 位置 + 不透明度 /
  模糊 / 遮罩 + 应用到哪几个面。**只显示与当前来源有关的控件**（来源=无时摆一堆滑杆
  只会让人以为设置没生效）。逐条"不许写代码"的口径见 §6.0 / §6.0.2：
  渐变 = 两个取色器、图片 = 文件管理器选择、每日一图 = 一键（不用填任何 URL）。
- **外观页**：着色模式（只剩「全部统一着色」一档，渲染为只读事实行而非下拉）+ 「材质与玻璃」（窗口材质 selector、材质说明、UI 遮罩颜色、
  UI 遮罩 / 面板遮罩不透明度、模糊、套用推荐值）+ 「其它外观」（对比度 / 圆角 / 视图边距）。
  分组**由数据驱动**：`STYLE_SLIDERS` 每项自带 `group`（`material` / `shape`），
  视图只按 group 排两次 —— 加一条玻璃参数只改 `format.js`，不动视图。
- **实时预览**：预览是一个**迷你浏览器窗口缩略**（标签栏 / 地址栏 / 页面区 / 背景层四块
  真实结构），颜色全部来自 `theme:preview` 返回的令牌 —— 与真实窗口同一份取值口径，
  不存在"预览一套、实际一套"。令牌写在预览**子树的根**上（内联变量），不碰
  `documentElement`，所以管理窗口自己的皮肤不会被编辑中的草稿污染。
- **保存语义**：草稿只在内存里；「保存」落盘、「保存并应用」保存后立刻切过去。
  内置 / 插件主题**不可覆盖**（`isUserThemeId` 判定）——对它们的编辑永远走"另存为副本"，
  于是"恢复出厂主题"不可能被改坏、插件更新也不会悄悄改掉用户的配色。

### 8.3 侧栏面板（`ui-panel-themes`，轻量）

只放三样：**当前主题**（色点 + 名字 + 明暗）、**色卡网格**（一格一个主题，点一下即换）、
「管理主题…」（开独立窗口）。**不放**编辑器——侧栏两三百像素宽，编辑器进去就是灾难
（见 `扫码器插件设计.md` §8.1 同一条原则）。

> **偏离原计划的一处（已定案）**：原写"最近使用 3~5 个色卡"，实际做成**全部主题的
> 色卡网格**。理由：① "最近使用"要额外维护一份历史，而主题总量通常只有个位数到
> 十几个，省下的空间换不来"翻半天找不到"；② 网格同时表达了分组（顺序即 内置 → 我的
> → 插件），不需要再插小标题把网格切碎；③ 与主题库同一份数据、同一套排序，两处不会
> 出现"面板里有、库里没有"。**不引入历史状态**也少一处要持久化的东西。

### 8.4 私密窗口主题（Vivaldi 特性）

`app.theme.privateTheme` 指定一个主题，私密窗口始终使用它 —— 一眼能分辨。

落地方式：**主题解析按窗口语境**（`themeService.getActiveThemeFor({ incognito })`），
`theme-runtime.publish()` 先全局广播普通那份，再对每个私密窗口**定向**广播私密那份
（后到者胜）。请求方向同样按发起窗口解析（`theme:active` / `theme:tokens`），
所以新开的私密窗口在加载那一刻拿到的就是它自己那份。

> **已知边界**：原生表面色（`layout.setTabTheme`）与 `nativeTheme.themeSource` 是**进程级**
> 的（fanout 不支持按窗口定位），因此私密窗口的差异体现在**令牌与背景**上 —— 那才是
> "一眼能分辨"的部分。按窗口的原生表面属"后做"（见 §12）。

### 8.5 主题页的三个视图

`hira://themes`（整屏工作区，带公共左侧导航）顶部三段控件切换：

| 视图 | 内容 |
| --- | --- |
| 主题库 | 分组卡片（内置 / 我的主题 / 插件主题，各带数量）+ 右侧预览与编辑器 |
| 调度 | 切换方式（不切换 / 跟随系统 / 白天夜间 21:00–06:00 / 手动时段表）；系统与夜间档各指定一个浅色/深色主题；手动档是一张 `主题 + 起 + 止` 的时段表 |
| 私密窗口 | 私密窗口专用主题（选「与普通窗口相同」= 跟随普通主题） |

主题库页是**两栏 + 可拖**：左栏（主题库）默认 **380px** 定宽，右栏（预览 + 编辑器）吃剩余 ——
编辑器是"要动手"的那一半（六格取色器 + 一排滑杆 + 背景设置），给它更多空间才不用上下滚着调；
两栏之间那条竖线就是拖拽把手（`flex-basis` 走 `--thm-list-w`，240~720 之间夹取，
每帧最多写一次）。宽度**不持久化**（下次打开回到默认）—— 它是一时的排版偏好，
不值得为它单开一个设置键。

## 9. 持久化与 Profile 隔离

- 用户主题：**`settings['app.theme.user_themes']`（数组）**，不是插件目录。
  理由：用户主题是**用户资产**，不该走"装/卸插件"那条链路 —— 装一个插件只为了改三个
  颜色，而且它会出现在插件列表里、可能被误卸载。放 settings 同时也自动获得落盘与
  既有的一切读取路径（`themeService.readUserThemes()` 在读目录时现取，不额外开表）。
  目录优先级：**内置 > 用户 > 插件**（内置不可顶、用户压插件）。
- 激活状态：`settings.app.theme` 由 `'light'|'dark'|'system'` **改为主题 id**（旧的三个值做兼容映射，
  见 §11 迁移）。
- 调度表：`settings['app.theme.schedule']`（对象，四档）。
- 私密窗口主题：`settings['app.theme.private_theme']`（id 或 `''`）。
- **按空间隔离**：原计划的"主题键加入 profile 快照键集合"**当前落不了地** ——
  NG 没有空间级的设置快照机制（旧 Hira `profileStore#createNewProfileSnapshot` 的对应物
  不存在）。改列为"后做"：等空间快照机制本身落地后，把这三个键加进快照集合即可，
  主题侧不需要额外改动（它读的就是 settings）。见 §12。

> 生成的 manifest **完全由我们重建**（只取主题定义），绝不照抄包里的清单 ——
> 否则第三方包的 `main` / `requestedPermissions` 会连同代码一起被带进来，
> 而"导入一个主题"用户预期的是换套颜色，不是装一段程序。

> 起始页是"背景层 + 遮罩层"两层（调遮罩浓度不该连图一起改，旧 Hira 踩过这个坑）。

## 11. 迁移与兼容

`app.theme` 从三态字符串改成主题 id，必须做一次**一次性迁移**（放在 `migration/runner`）：

| 旧值 | 新值 |
| --- | --- |
| `light` | `hira-light`（内置浅色） |
| `dark` | `hira-dark`（内置深色） |
| `system` | `hira-light`，**并把调度设为 `system`**（白天 `hira-light`、夜间 `hira-dark`） |

> `system` 之所以不是"一个会自己变色的主题"，而是"调度的一档"：Vivaldi 也是这么做的。
> 一个主题内部再分白天/夜间两套配色，等于把"主题"与"调度"两件事揉在一起 ——
> 而用户真正想表达的往往就是"白天用这个、晚上用那个"。

**默认值 ≠ 保底值**（唯一真源 `shared-types/src/theme.mjs`）：

| 常量 | 回答的问题 | 值 |
| --- | --- | --- |
| `DEFAULT_THEME_ID` | "用户还没选"时给什么 —— OOBE 首启、设置项缺失、当前主题被删除、引用的主题已不存在 | `hira-acrylic-light`（亚克力浅） |
| `DEFAULT_THEME_IDS` | 调度里"没配过的"浅 / 深档 | `{ light: 'hira-acrylic-light', dark: 'hira-acrylic-dark' }` |
| `BUILTIN_THEME_IDS` | 插件全军覆没时哪些配色仍然在场（保底可读） | `['hira-light', 'hira-dark']` |

为什么默认落到**亚克力浅**而不是 `hira-light`：系统级模糊窗口是本项目的招牌，首启就该看见；
默认给不透明的浅色，用户第一眼只会以为"毛玻璃根本没做"。不支持材质的机器
（< Win11 22H2 / 非 Windows）原生层会静默降级为不透明，观感等同「浅色」，不会透不出来。

未识别的值（用户手改过配置）一律落到 `DEFAULT_THEME_ID` 并留一条 warn 日志 —— 不能因为一个坏值让界面白屏。
空值（从没设置过）同样落到 `DEFAULT_THEME_ID`；而 `light` / `dark` / `system` 这类**曾经显式选过**的旧值
仍按上表迁移，不受默认值影响。

## 12. 明确不做 / 后做（先把话说死，避免越做越散）

- **不做**主题市场服务端：`plugin-market` 的多源索引复用即可，索引里收录主题条目。
- **不做**网页内容强制深色（Vivaldi 的 Force Dark Mode）：那是网页层能力，属 `webview` 域，
  不塞进主题系统（否则主题系统会同时管界面与网页两件事）。
- **后做**主题图标集（P4 未做项）：需要先确认 `ui-common/src/icons.ts` 的图标 id 命名能被
  主题稳定引用，并给图标解析加一个"主题资产优先"的钩子（`iconByName` 目前只认内置
  构造函数）。这是唯一一项跨到 `ui-common` 的改动，与主题系统本身解耦，故单列。
- **后做**主题的"按空间自动切换"（数据层已支持：主题读的就是 settings；
  **卡在前提**：NG 当前没有空间级的设置快照机制，见 §9）。
- **后做**私密窗口的**原生表面色**：`layout.setTabTheme` / `nativeTheme.themeSource` 是
  进程级的（fanout 不支持按窗口定位），当前私密窗口只在令牌与背景上不同。
  要按窗口定位得先给 fanout 加窗口维度 —— 属另一个基础设施改动，不塞进主题系统。
- **已做**chrome 玻璃（`style.transparency` / `style.blur` 作用到工具栏）—— 见 §6.2：
  有壁纸时 chrome 变玻璃（**一层**染色 + 内层透明），`style.blur` 只作用于 UI 玻璃层；
  壁纸自身由 `background.blur` 独立控制，两者互不套用下限。
  背景遮罩（白/黑 × 浓度）见 §6.3。
- **已做**窗口材质（亚克力 / Mica，`style.material = 'acrylic' | 'mica'`）：Win11 22H2+ 走官方
  `BrowserWindow#setBackgroundMaterial(material)`，DWM 直接把桌面（亚克力是实时内容、Mica 是壁纸）
  模糊画进窗口透明区；chrome 与壁纸共用同一条 `glassSurface` 玻璃链，不再叠第二层假毛玻璃。
  材质词汇 → 原生名的映射只在 `MATERIAL_TO_NATIVE` 一处。见 §6.2.3。
- **不做**Win10 的亚克力 FFI 路径（`SetWindowCompositionAttribute +
  ACCENT_ENABLE_ACRYLICBLURBEHIND`）：非公开 API、要求 `transparent: true`，而主窗
  `transparent: false` ⇒ 写了也永远不生效。Win10 上诚实降级为染色玻璃并如实告知（§6.2.3）。
- **已做**「自动」前景（`colors.*Fg = "auto"`）：按壁纸平均亮度 + 现有遮罩设置自动选黑 / 白，
  于是「每日一图」这种**每天换图**的壁纸不会出现"亮照片配白字"。见 §6.2.1 的
  「自动前景」小节（亮度在主进程量，`theme-luminance.js`）。
- **已做**视频背景（动态壁纸，`background.kind = 'video'`）：与图片同一条链，
  多出来的只有"协议必须支持 `Range`"（`main/asset-response.js`）与"渲染侧要一个 `<video>`"
  （`shared-types/src/theme-background.mjs`）。见 §6.4。
- **后做**背景图自身的 `opacity` / `blur`：代码路径已全通（编辑器的滑杆 → 令牌 → 三处消费面），
  但只在 `kind:'css'` 的内置主题上实测过；等有一张真实的图片主题（导入包或主题插件）
  再确认 `filter: blur()` 与不透明度在**图片**上的观感，必要时再调默认值。

## 13. 风险与取舍

| 风险 | 取舍 |
| --- | --- |
| 三套令牌的覆盖不全会出现"半换肤"（外壳变了、内部页没变） | P1 的验收标准就是"三处同时变"；宁可先只支持完整主题，也不做局部染色 |
| 主题变量直接写进 `documentElement.style` 会整棵文档重算样式 | 只在**切主题**时写一次，不做连续动画；编辑器实时预览走 `element.style` 局部作用域 |
| 背景图 8MB 上限放宽 | 只放宽图片/字体的**单文件**上限，其余安全边界（白名单/穿越守卫/仅启用可读）一条不动，并在文件头写明原因 |
| 导入的 zip 里带 `../../` 的条目名（zip-slip） | `plugin-archive` 只负责读字节，**路径守卫在消费方**：`theme-package#safeEntryName` 拒绝绝对路径/盘符/`..`，落临时目录时再逐个 `resolve` 校验一次。两处都做是因为"条目名是攻击者可控输入" |
| 导入的包夹带 `main` / 权限声明（等于装了一段程序） | 生成的 manifest **完全由我们重建**：只有 id/name/version/type/contributes.themes，`main` 与 `requestedPermissions` 一个字都不抄。导入一个主题 = 换套颜色 |
| 主题 id 化会动到 `app.theme` 的所有消费方 | 先做 P0 真源 + 一次性迁移，再逐个改消费方；每一处都保留"旧值兜底"直到全部改完 |
| 导入沿用包里的主题 id 会与用户主题撞 id（被优先级压住、看不见） | 导入**总是**新生成 `theme-<slug>-<base36 时间>`；"覆盖更新"语义留给插件市场（它才有版本与来源） |
| 主题插件与"面板插件"混在一起会污染插件中心 | `type` 分组 + 主题专属信息卡片；插件中心不为主题破例改结构 |
| Vivaldi 字段名映射"看着对、实际打不开" | 明确标注**未在真实 Vivaldi 上验证**，承诺范围收缩到"字段名对得上 + 我们能原样读回"（见 §2 末尾） |
| 半透明 chrome 会**逐层叠加**（`--main-bg-color` 被十来处嵌套引用） | 带壁纸时该变量给 `transparent`（不是半透明），染色由外壳**按区域各铺一片**（工具栏/内容洞/侧栏区），**每片只有一层** —— 见 §6.2。这是"各处深浅一致"的唯一保证 |
| UI 模糊与背景模糊共用一根值 → UI 的 10px 下限把整个背景也锁死 | **拆成两条链**：`style.blur` 只进 `--hira-ui-blur`，`background.blur` 只进壁纸渲染器；背景可到 0，UI 仍保底 10px。见 §6.2 第 3 条 |
| 毛玻璃只对**同一文档**生效，而 rail / 面板是独立视图 | 那两个视图透明之后，透出的就是外壳那一份**糊好的**壁纸 + 同一层染色（颜色与模糊都同源）。只有**盖在网页之上的浮出层**那一段拿不到（背后是网页、不是外壳），它自己画一份**壁纸镜像**并按同一构造糊 —— 见 §6.2.2 |
| chrome 面误用 surface 系列令牌 → 留一块不透明"色块" | 判据写进 §6.2 第 4 条：**chrome 用 `--main-bg-color`，内容用 surface 系列**；两者无壁纸时同值，所以改起来是零风险的（书签固定栏已按此修） |
| 「自动」前景依赖**实测**的壁纸亮度，而测量是异步 / 可能失败（离线、图挂了、格式解不出） | 全链**尽力而为**：`peek` 同步读缓存，量不到就退回"按主题底色判"—— 仍是个确定的值，不会出现空令牌或闪空的文字。量**成功**后发一次 `background` 事件自动跟上。失败记 5 分钟冷却，避免"离线时请求风暴"。见 §6.2.1 的「自动前景」 |
| 动态壁纸（视频）要**持续解码**，比一张静态图贵得多；而且侧栏浮出层的镜像层会**再开一份**同一个视频 | 三处补偿：① `muted / loop` 硬编码 = Chromium 最省的播放路径；② 浮出层镜像那份是**瞬时**的（只在 hover 浮出时可见），且浮层视图本身有 2 分钟**闲置回收**（`FLOAT_IDLE_RECLAIM_MS`，整棵 renderer 一起销毁）；③ `background.blur` 与 UI 层 `backdrop-filter` 对视频都是逐帧合成，作者可按需取舍（默认背景 0）。见 §6.4 |
