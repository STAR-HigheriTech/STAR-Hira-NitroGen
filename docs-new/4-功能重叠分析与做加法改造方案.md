## §1 四条总原则

1. **能加不建**：NG 的面板体系是插件驱动的（manifest `contributes.panels` → `panel-catalog` → 渲染层 `import.meta.glob('ui/ui-panel-*/src/index.js')` 自动发现），且列表类面板共用 `ui-common#createTabListHost`、插槽有 `side-panel.*` / `tabbar.context-menu-item` 等 31 个。**新增一个面板 = 加一个插件包 + 一行 manifest**；新建一个 overlay 则要动 `LayerManager`/z 层/新窗口类型。**能用现有机制承载的，一律走加法。**
2. **同一能力只留一条通道**：如"网页注入"（Boosts / 强制深色 / UserScripts）本质是同一件事，做**一条注入通道**，不要三套。
3. **已有取色/排序/列表/音频等基建的，优先复用**，不要另起一套。
4. **收益 < 成本的不做**：没有后端、平台受限、或纯"看起来酷"的，直接砍或降级。

## §3 原本想 overlay，改用 panel（或直接复用面板）

> 判断依据：NG 面板体系已插件化、且列表类共用 `createTabListHost`；而 overlay 要动 `LayerManager`/z 层/新窗口类型。**能用面板承载的，不开 overlay。**

| 项 | 原计划 | 改为 | 理由 |
| --- | --- | --- | --- |
| 归档区 A2 | 新视图 | **面板插件**（`contributes.panels`） | 列表类，复用 `createTabListHost` |
| 阅读清单 D6 | 新面板 | **notes 面板的一个视图** | 已有 notes 面板与文件夹 |
| 截图 C6/N16 | 面板 | **面板 / 命令**（二选一即可） | 已有截帧能力 |
| 媒体控制 N4 | 浮层 | **面板 或 rail 底部区** | 无独立交互复杂度 |
| Live Folders E5 | 新面板 | **面板**（复用 news providers） | 已有订阅源 |
| Easel D4 | 独立窗 | **面板 + 独立窗双形态**（学 `ui-panel-themes` 的 `panel/` 与 `window/` 双形态） | 已有成熟双形态先例 |

## §7 profile 隔离（L2）的前置补全 —— 要先补的设置项

> 结论：**有几项现在根本没有"设置项"，隔离前必须先补**，否则"隔离"无处施加。

| 前置项 | 现状 | 必须先补什么 |
| --- | --- | --- |
| **代理** | **完全没有**（NG 与 RT 都无 `session.setProxy`） | 先补"代理设置项 + `session.setProxy`"，再谈"按 profile 独立" |
| **UA** | 只有**全局清洗**（`user-agent.ts`），**无用户可设项** | 先补"UA 设置项（预设列表 + 自定义）"，再做 per-profile |
| **主题** | 主题数据存 settings（覆盖层） | 迁移时把"主题相关键"一并纳入 profile 快照 |
| **临时 profile 清理** | NG **缺**（`apps/app-main/src/main` 无 `ephemeral` 清理） | 补"启动清理残留 ephemeral profile"（RT 有 `profiles-controller/ephemeral.ts#cleanupStaleEphemeralProfiles`）—— 属 profile 生命周期，L2 前应有 |
| **`kv` 表归属** | 无 `profile_id`（当前无活跃使用方） | 明确归"全局元数据库"（插件状态已钉 default） |

**顺序**：先补"缺失的设置项/能力"（作为普通功能落地）→ 再做 L2 拆库/快照（详见 PART16）。否则隔离时"无值可迁"。

## §9 修订后的落地优先级（加法优先）

> **⚠⚠ 踩坑记录（本轮最重要的教训，比功能本身更值钱）：页面右键菜单命令的"接线"有四处要动，漏一处就是"点了毫无反应"。**
> 现象：新加的「截取选区…」「在小窗中预览」「为此站点创建规则」全都点了没反应；「截取选区」更离谱 —— **截出来的是整页**。
> 排查结论：**既不是 IPC 问题，也不是图层问题，也不是图层层级问题**（它们连那三步都没走到）。是两处**接线层**缺陷：
> 1. **契约被改坏（截图三项）**：标签页右键菜单的 options **不是** runtime 那份 handler 对象，而是由 `infra-window/src/tabEvents.js` 的 `wc.on('context-menu')` **另拼**的（侧栏那条链在 `apps/app-main/src/main/web-sidebar.js` 又拼了一份）。`tabEvents` 对 `onCapturePage` 的约定是**位置参数 mode 字符串**，由它补齐 `tabId` 与 `webContents` 后组装成对象交给宿主 hooks。我误以为"payload 丢了 webContents 是 bug"，将其改成传 `{ webContents, mode }` → 那个对象被当成 `mode` 收下 → 宿主认不出任何合法模式 → **落到兜底分支 `'fullpage'`** → 表现就是"点选区、截整页"。**结论：infra 层只报 mode，`webContents` 由胶水层补**（infra 既没有 tabId，也不该替宿主决定截谁）。
> 2. **新命令漏了转发键（小窗 / 注入规则）**：handler 我加在 runtime 的 hooks 上（位置是对的，`TabManager._hooks` 就是它），但 `tabEvents` 的 options 里没有 `onPeekPreview` / `onInjectRuleForSite` → 命令体里 `options.onXxx &&` **直接短路** → 静默什么都不做。已补两条转发，并给 `web-sidebar` 也补上（为此让 runtime 在 return 里暴露 `hooks`，供侧栏复用同一份实现，避免"标签好使、侧栏没反应"）。

> **⚠⚠ 追加第三条规则（2026-10-11，速览"没反应"的真因）：标签行右键菜单的动作表必须走「整包直送」。**

## §11 接入时序与 UI 归属（能力 → 接口 → 设置项 → UI → 联动）

> **为什么要有这一节**：§2 只回答"用什么基座、怎么加"，**不回答"谁在什么时候把它接到设置页 / 菜单 / 面板上"**。
> 缺了这层，就会出现「能力有了、接口通了，用户却找不到入口」的半成品 —— 这正是本次要补的断档。

### 11.1 NG 的接入机制（接入 = 改一处，不是另起工程）

| 接入形态 | **唯一落点** | 说明 |
| --- | --- | --- |
| **设置项** | `apps/app-main/src/main/settings/registry.js` | 设置页**由注册表自动生成**（`toggle`/`select`/`text`/`number`/`list`/`order`/`action`）。写一条 = 同时得到 UI + 持久化 + 变更广播；`effect: 'live'｜'restart'`、`group: 'advanced'`。默认值写在 `domain-settings/src/index.js` 的 `DEFAULT_SETTINGS`。 |
| **右键菜单项** | `ui-common` 的菜单模板（`tabContextMenu.ts` / `bookmarkContextMenu.ts` …） | **单一事实源**，所有宿主自动生效；宿主只声明"能不能"（`can*` 判据）。 |
| **地址栏命令** | `ui-searchbar/src/suggestors/pedals.js` + `TabManager#omniboxAction` 动作表 | 加一条命令 = 两处各一行。 |
| **面板** | 插件 manifest `contributes.panels` | `panel-catalog` 自动发现，**不动核心**。 |
| **浮层** | `LayerManager` + `--hira-z-*` token | 需过 §4 准入检查表。 |
| **入口联动** | `feature-map.js` 一行 | 引擎被禁用 → 对应入口自动隐藏。 |

> **结论**：「接入」在本项目里从来不是独立的"第二期工程"——**落盘能力的那一次改动里，就该把设置项/UI 一并接上**（能复用既有渲染链的甚至零额外代码）。这正是第一批的实际情况。

### 11.3 J2 的 UI 缺口（已按方案 A 消除）

原缺口：用户配置的引擎（`search.engine-*`）**已经能用 `!名字` 搜**，但设置页只声明了 4 个固定引擎 —— **用户没有地方填**，"自定义"只对开发者可用。两个方案：

- **方案 A（✅ 已落地，零新 UI 代码）**：在 `registry.js` 的 `search` 段加 3 个「自定义搜索引擎」文本槽（`search.engine-custom1..3`，留空即不启用），并把 `search.default_engine` 的 `options` 补上这 3 项（否则填了模板却无法设为默认）；`domain-settings` 默认值补 3 个空串。**生效器未改** —— `appliers/search.js` 本就是遍历式（`search.engine-` 前缀），新键自动生效；`search-controller` 的 `RELOAD_KEYS` 也本就覆盖该前缀 → 改完即时生效。地址栏 `!custom1 关键词` 可直接调起。
- **方案 B（可选后续，一次到位）**：给设置页新增**可编辑 list 控件类型**（现有 `type: 'list'` 是**只读** route 列表，不能增删），支持任意增删引擎。
  代价：新控件类型 + 校验 + `settings:*` 契约联动；好处是该控件可**复用于后续所有"键值列表"型设置**（如 J10 的站点规则表）。

> A 已消除断点；B 不作为阻塞项，待 J10（站点规则表）需要时一并沉淀为通用控件。
