# PART16 · 空间 / 配置文件「完全独立」方案（L2 物理独立）

> **需求原文**：完整的多用户形态 —— 每个配置文件**完全不一样、完全独立的设置、数据等所有**。
> **决策（已定 2026-10-08）**：做到 **L2 物理独立**。
> **划分**：**全局** = 插件（系统本身 + 启用状态）与**界面外观布局**；**其余全部**按 profile 独立 —— 数据、**主题、UA、代理**、以及其它一切设置。
> 口径：现状结论全部以本仓源码为准；本文件是**规划文档**，不含代码改动。

## §2 为什么会这样（不是漏做，是有意取舍）

1. **设置覆盖层**（`profileOverlay.js` 文件头）：*升级不丢*（新设置项有基线兜底）、*磁盘小*、*写入隔离*。
2. **插件开关全局**（`plugin-state-store.js`）：隔离最小单位应是"能力面"而非"插件"；一个插件常混有该隔离的（面板/主题）与无法隔离的（全局快捷键/托盘/资源目录/自指前置）。

这两条是经过论证的决定，但与"每个配置文件完全独立"冲突，故本方案要正面解决它们（见 §5、§6）。

## §3 决策与范围（已定）

### 3.1 级别：L2 物理独立
每个 profile 一套**独立存储**（独立 `hira.db` + 独立 `settings.json` + 独立 `spaces/<sid>/session.json` + 独立 Chromium session）。一个库损坏不牵连别人。

### 3.2 全局（跨 profile 共享）—— 只有这两类

**A. 插件**
- 插件系统本身：`PluginRegistryV2`、`plugin-host`、`plugin-market`、`plugin-installer`、`plugin-protocol`、`plugin-archive`。
- 插件启用/禁用状态：`plugins.disabled`、出厂播种标记（`plugin-state-store.js`）。
- 理由：进程级单例 + 「能力面 vs 插件」的既有论证；用户确认保留全局。

**B. 界面外观布局（`layout.*` 一类"与设备/屏幕绑定"的偏好）**
- `layout.preset` · `layout.mode` · `layout.immersiveMode` · `layout.titlebarEnabled`
- `layout.rowPosition.*` · `layout.rowOrder` · `layout.sideOrder`
- `layout.windowControlsHost` · `layout.windowControlsStyle`
- `layout.sideColumnVisibility` · `layout.sideColumnWidth` · `layout.sideColumnCollapsed`
- `app.sidebar_position` · `sideColumnPosition` · `webSidebarPosition`
- `app.bookmarkbar_visible`（书签栏显隐 —— 属"界面布局"）
- 理由：这些是"这台机器/这块屏怎么摆"，不是"这个用户是谁"。

> ⚠ 若你其实想让"界面布局"也按 profile 独立，只需把这份清单从 §3.2 移到 §3.3（见 §10 的开关设计，一处可翻转）。

### 3.3 按 profile 独立 —— 其余**全部**

- **数据**：书签 / 历史 / 下载 / 笔记(+文件夹) / TOTP / favicon / 密码元数据 / 永不保存 / 权限 / 搜索历史 / **空间** / **标签会话** / 扩展（已独立）。
- **设置（除布局外的一切）**：
  - **主题**：`app.theme`、用户主题数组、私密主题、主题调度、每日一图。
  - **UA**：浏览器 UA 伪装（每 profile 一套）。
  - **代理**：新增，每 profile 一套。
  - **通用**：启动模式/启动页/主页、默认搜索引擎。
  - **搜索**：自定义 bang/引擎、搜索建议行为。
  - **隐私**：拦截开关、DNT、密码保存提示、表单填充、退出时清理各项。
  - **下载**：默认目录、是否询问、通知、安全浏览、限速、多线程与连接数。
  - **扩展设置**：开发者模式、允许未打包、自动更新（扩展本身已 per-profile）。
  - **性能**：内存节省、后台节流、平滑滚动（**硬件加速除外**，见 §7.3）。
  - **无障碍**、**语言/翻译**、**PDF**、**外观（主题色等，非布局）**、**外部应用关联**、`app.zoom_levels`（按 origin 的缩放记忆 → 随用户）。

### 3.4 目标物理布局

```
<userData>/
├── settings.global.json          # ★新：全局设置（插件状态 + layout.* + 启动期必需键）
├── window-state.json             # 保留：窗口几何（全局）

        ├── hira.db                # ★新：该 profile 的业务数据（独立库）

        ├── spaces/<spaceId>/session.json   # 已有形态
        ├── Extensions/…           # 已有：扩展存储
        └── (Chromium session：Cookies / Cache / Local Storage / … 已有)
```

## §4 关键设计点（先定这些，再谈改文件）

### 4.1 全局元数据库 vs 每 profile 数据库
`profiles` 表**枚举所有 profile**，必须住在**全局库** `global.db`；而 `spaces` 属于某 profile → 迁到**该 profile 的库**。于是：
- `global.db`：`profiles`（+ 可选 `kv`）。
- `profiles/<id>/hira.db`：`bookmarks / history / downloads / notes / note_folders / totp_entries / favicons / passwords_meta / passwords_never_save / permissions / search_history / spaces`。

> 副产物：每 profile 库里的 `profile_id` 列**变成冗余** —— 保留（无害、便于将来"单库模式"回退），但查询不再需要它。

### 4.2 服务如何"跟着 profile 换库"
现状：域服务在启动时 `createXService(db, { getProfileId: currentProfileId })`（`main.js:1397/1418/1421/1426/766`），`db` 是**一个固定句柄**，靠 `getProfileId()` 在查询里过滤。
L2 后 `db` 必须**随当前 profile 变**。两种做法：

| 方案 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **A. 重建服务** | 切 profile 时 dispose 旧服务、用新库重建全部域服务 | 改动小、语义清晰 | 重建 ~12 个服务，切换时有一次开销 |
| **B. 延迟解析库** | 服务持有 `getDb()` 端口，每次查询现取当前 profile 的库 | 切换零重建 | 每个域服务都要改内部（多处 `db.xxx` → `getDb().xxx`） |

**建议：A 为主 + B 的轻量版** —— 让 `infra-db` 暴露 `dbProvider.forProfile(id)`（带连接缓存），`main.js` 在 profile 切换钩子上**重建域服务**（切 profile 本就是低频重动作）；单库模式下 `forProfile` 恒返回同一句柄，行为不变。

### 4.3 连接生命周期与并发
- 打开新 profile 库时**不立即关闭**旧库（可能有未落盘事务）；延迟关闭（如 30s 空闲）或保留 LRU（上限 3 个）。
- 切 profile 流程：`flush 当前 profile（settings/db）→ 切 spaceRuntime → 打开目标库 → 重建服务 → 应用 session(UA/代理) → 通知 UI 重载`。
- WAL 已开（`infra-db/index.js` `journal_mode = WAL`）；每库各自一份 `-wal/-shm`。

### 4.4 设置的"完整快照"如何不退化成"升级丢设置"
当初选覆盖层的核心理由是"升级新增设置项要有默认值兜底"。完整快照方案必须正面解决：
- 快照文件**只存偏离出厂默认的键**（等于"一个人的覆盖层"，但基线是**出厂默认**而非"全局共享基线"）；
- 读取时 `出厂默认 ← 快照` 合并 → 新增设置项自动有默认值，无需迁移；
- 提供"跟随出厂默认"= 清空快照（等价 `reset()`）。
> 这样既是"完整独立"（不与他人共享任何值），又不丢升级兜底。

### 4.5 启动期设置的两难（必须记）
部分设置在 **app ready 之前**就要读（`hardware_acceleration`、是否开同步滚动等），而"当前 profile"要到能读 DB 之后才知道。对策：
- 在 `settings.global.json` 里放一个 **`boot` 小节**（硬件加速、上次激活 profile id 等极少数键）；
- 启动流程：读 `settings.global.json` → 定位"上次激活 profile" → 用 `boot` 值初始化 → app ready → 打开该 profile 库与快照 → 其余设置在窗口创建前应用。

## §5 详细执行计划（文件级）

> 分 6 步，每步可独立落地与回滚。标注 **改哪个文件 / 改什么 / 为什么 / 注意**。

### 步骤 1 · `infra-db` 支持"按 profile 开库"
- **文件**：`infra/infra-db/src/index.js`
- **改什么**：新增 `createDbProvider({ rootDir, profileDirOf, logger })`：
  - `forProfile(profileId)` → 缓存并返回该 profile 的 `createDb(<profiles/<id>/hira.db>)` 结果；
  - `global()` → `createDb(<rootDir>/global.db)`（只含 `profiles` 表）；
  - `evict(profileId)` / `closeAll()`；
  - 迁移记账表 `_schema_migrations` 变为**每库一份**（`applyMigrations` 已按 sqlite 句柄记账，天然支持）。
- **注意**：`SCHEMA_DDL` 需拆成「全局 DDL（profiles）」与「profile DDL（业务表）」两份；`ensureSchema` 相应拆两个入口。

### 步骤 2 · `main.js` 装配层切换为 db-provider
- **文件**：`apps/app-main/src/main/main.js`（`:306` 当前 profile 端口；`:766/1397/1418/1421/1426` 服务创建；`:3049` session 取）
- **改什么**：
  - 用 `dbProvider.global()` 建 profileService；
  - 新增 `bindProfileServices(profileId)`：用 `dbProvider.forProfile(profileId)` 重建 bookmarks/history/downloads/notes/totp/favicon/password/permission/search/space/session 等服务；
  - profile 切换钩子（`space-commit` / `LoadedProfilesController`）里调用它；
  - `currentProfileId` 不变（已是唯一解析点）。
- **注意**：IPC 注册器持有的是服务引用 → 需保证"重建后引用被替换"（注册器改为通过 getter/proxy 取服务，或重建后重挂）。这是本步唯一较重的接线。

### 步骤 3 · `domain-settings` 改"完整快照 + 全局设置"
- **文件**：`domain/domain-settings/src/profileOverlay.js` → 演进为 `profileSettings.js`；新增 `globalSettings.js`；`domain/domain-settings/src/index.js` 导出调整。
- **改什么**：
  - `createProfileSettings({ defaults, filePort, profileDirOf, getProfileId })`：每 profile 一份 `settings.json`（**只存偏离默认的键**，读取时与 `defaults` 合并，见 §4.4）；
  - `createGlobalSettings({ filePort, rootDir })`：读写 `settings.global.json`，承载 §3.2 的**全局键**（插件状态 + `layout.*` + `boot`）；
  - **键位路由**：一个中间层按**键 → 全局 / 按 profile** 分派 `get/set/subscribe`（`GLOBAL_KEYS` 集合来自 §3.2）。
- **注意**：`theme-service` / `keybindings` 目前直接吃 settings，**无需改**（它们照旧读写"当前 profile 的那份"）；只有 `layout.*` 命中的键会路由到全局。

### 步骤 4 · 数据迁移器（一次性）
- **文件**：`apps/app-main/src/main/migration/`（沿用现有 runner/adapters/datasets 结构）。
- **改什么**：新增迁移 `split-db-per-profile`：
  1. 读旧 `hira.db` 的 `profiles` 表 → 迁入 `global.db`；
  2. `SELECT DISTINCT profile_id FROM <each table>` → 对每个 profile 建 `profiles/<id>/hira.db` 并把该 profile 的行 `INSERT` 过去（`bookmarks/history/downloads/notes/note_folders/totp_entries/favicons/passwords_meta/passwords_never_save/permissions/search_history/spaces`）；
  3. 迁移 `settings`：`base ∩ 各 overlay` 合并出每个 profile 的完整快照 → 写 `profiles/<id>/settings.json`；把 `layout.*` 与插件键抽出写 `settings.global.json`；
  4. 旧 `hira.db` **保留**为只读备份（改名 `hira.db.pre-l2`），不删。
- **注意**：迁移必须**幂等 + 可重入**（用 `_schema_migrations` 记账或全局标记文件）；失败可回落"单库模式"。

### 步骤 5 · UA / 代理按 profile
- **文件**：`apps/app-main/src/main/user-agent.ts`、`main.js`（session 装配 `:3049`）、新增 `main/proxy.js`。
- **改什么**：
  - UA：从 `app.userAgentFallback`（全局）改为**每 profile 对其 session 设 UA**（`session.setUserAgent`）；全局 fallback 仅作兜底（用中性值）。
  - 代理：新增设置键（§3.3）+ `session.setProxy(...)`，绑定到当前 profile 的 session；切换 profile 时重新应用。
- **注意**：`web-sidebar.js` 的移动/桌面 UA 是**运行态**（视图模式），其**偏好**应随 profile。

### 步骤 6 · 全局项白名单落地
- **文件**：`plugin-state-store.js`（保持 `default` 全局 —— 但注释更新为"L2 下明确保留"）、`window-state-store.js`（保持全局）、`shared-ui-tokens`/`layout.mjs`（`GLOBAL_KEYS` 来源）。
- **改什么**：把"哪些键全局"集中成**一处** `GLOBAL_KEYS`（单一事实源），供 §3 路由与文档共用，避免"这里一个规则那里一个变化"。

## §6 运行时：profile 切换的完整时序（L2）

```
1. 用户切 profile（space-commit / LoadedProfilesController）
2. flush：当前 profile 的 settings 落盘 + db WAL checkpoint
3. spaceRuntime.set(currentProfileId = 目标)
4. dbProvider.forProfile(目标)         # 命中缓存则复用
5. bindProfileServices(目标)            # 重建域服务
6. settings 路由切到目标（profileSettings 读目标快照；global 不变）
7. 应用 session：UA / 代理（session.setUserAgent / setProxy）
8. 通知渲染层：profile:changed → 各面板/标签栏重新拉数据
9. 旧 profile 的库延迟关闭（LRU 上限 3）
```

**边界**：
- **internal（无痕）/ ephemeral（临时）**：库建在临时目录，退出即删；不写 `profiles/<id>/`。
- **default**：与普通 profile 同样对待（有独立库与快照）。
- **新建 profile**：建目录 → 建空库（跑 `ensureSchema(profile DDL)`）→ 生成空快照（= 出厂默认）；可选"复制自某 profile"。
- **删除 profile**：关闭其库 → 删除 `profiles/<id>/` 整目录 → 删 `global.db.profiles` 行。
- **跨 profile 全局搜索**（若有）：改为并行查各库后合并（当前无此功能，登记为潜在影响）。

## §7 风险与对策

| 风险 | 说明 | 对策 |
| --- | --- | --- |
| **接线成本**（步骤 2） | 域服务被 ~40 个 IPC 注册器持有，重建后引用要更新 | 注册器改用 getter 取服务；或保持"单库模式"兼容路径 |
| **迁移正确性** | 拆库丢数据 / 分区错 | 迁移前自动备份整库；迁移后跑完整性校验（`migration/integrity.js` 已有先例）；保留旧库 |
| **启动期设置** | 硬件加速等需在 ready 前读 | `settings.global.json` 的 `boot` 小节 + "上次激活 profile" |
| **升级新增设置项** | 完整快照可能缺新键 | 快照只存偏离默认的键，读取与出厂默认合并（§4.4） |
| **FTS5 每库** | 书签 FTS 要每库各建 | `ensureSchema` 已含 `ensureBookmarkFts`，每库建时自动执行 |
| **回退** | 上线后需能退回单库 | 保留"单库列分区"旧路径 + `profiles.physical_isolation` 开关；迁移为复制语义 |
| **插件开关** | 用户虽确认全局，但个别用户可能想要 per-profile | 记入 §3.2 白名单；将来若改，只动 `plugin-state-store.js` 一处 |

## §8 验收清单（L2 达成判据）

1. 新建 profile B 后，B 的**主题 / UA / 代理 / 启动页 / 下载目录 / 隐私开关**与 A 完全独立，互不影响。
2. A 与 B 的**书签 / 历史 / 下载 / 笔记 / 密码 / 权限 / 空间 / 会话**各自独立；删 A 的目录不影响 B。
3. 每个 profile 的**数据落在各自的 `profiles/<id>/hira.db`**；`userData/global.db` 只有 `profiles` 表。
4. 每个 profile 有**自己的 `settings.json`（完整快照）**；改 A 的设置不写入 B 的任何文件。
5. **插件启停**与**界面布局**跨 profile 一致（全局），符合 §3.2。
6. 迁移后**旧数据零丢失**；断开/恢复"单库模式"开关可用。
7. 无痕/临时 profile 退出即清；default profile 行为与升级前一致。

## §9 不做 / 保留全局（及理由）

| 保留全局 | 理由 |
| --- | --- |
| 插件系统 + 插件启用状态 | 进程级单例 + 「能力面 vs 插件」既有论证（`plugin-state-store.js`） |
| 界面外观布局（`layout.*`、侧栏位置、窗口控件、书签栏显隐） | 用户确认；本质是"设备/屏幕"级偏好 |
| 窗口几何 | 与屏幕绑定；多窗口下按窗口而非按用户 |
| 全局快捷键激活 / 托盘 / 外置资源目录 / 崩溃上报 / 更新 | 进程级单例，天然无"某个 profile"这个状态 |
| 硬件加速等启动期开关 | 需在 profile 可知之前生效（放 `settings.global.json` 的 `boot`） |

## §10 一处可翻转的开关（留给未来）

§3.2 的"全局键集合"集中定义在**单一事实源 `GLOBAL_KEYS`**（由 `shared-types/src/layout.mjs` + `domain-settings` 共用）。于是：
- 想把**界面布局**也改成 per-profile：把 `layout.*` 从 `GLOBAL_KEYS` 移出即可，路由与迁移逻辑自动跟随，**不散落**；
- 想把**插件开关**改成 per-profile：只动 `plugin-state-store.js` 一处 + `GLOBAL_KEYS` 减一项。

> 这条"集中一处"的要求来自既有纪律：**同一个规则不能这里写一个、那里写一个**（参见 `feature-map.js` / `split-layout.mjs` / `layout.mjs` 的一贯做法）。
